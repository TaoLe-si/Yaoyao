# 22 · 学习能力缺陷定位：顺序、计数、集合容量三分

> 本文是 doc 21「退化重复」的**精确化**。原判断（"重复吸引子"）**不准确**：
> 解码端施加重复惩罚后输出**一字不变**，证明问题不在解码。
> 真正的缺陷是**顺序信息根本没有被存储**。

---

## 一、解码端干预全部无效（排除解码假设）

用新增的 `decode_diag.cpp`（可访问完整 logits，支持重复惩罚 / n-gram 阻断 / top-k / 温度）
在收敛检查点 `h2r_l6_long/step_500` 上做网格实验：

| 配置 | 完全正确 |
|---|---:|
| 基线（默认参数） | 2/8 |
| `--rep-penalty 1.3` | 2/8 |
| `--rep-penalty 1.6` | 2/8 |
| `--ngram 3` | 2/8 |
| `--ngram 2` | 2/8 |
| `--rep-penalty 1.3 --ngram 3` | 2/8 |
| `--rep-penalty 1.6 --ngram 2` | 2/8 |

**重复惩罚 1.3 / 1.6 完全没有改变任何一条输出**。说明重复 token 的 logit 优势极大，
且模型确实"想要"输出那个 token——不是采样抖动。

> **基线等价性已验证**：`decode_diag` 在默认参数下与 `h2r_cpu.exe` **5/5 逐字一致**。
> （首次比对 0/5 是因为直接用 `char(t)` 解码，而文本 token 有 `<256` 原始字节与 `>=261` BPE 合并两种，
> 必须走 `tokenizer.decode`。这是工具缺陷，非模型缺陷。）

## 二、三分测量（关键实验）

30 条测试，长度 1..8，物品取自语料中的 42 项池，每条内不重复：

| 长度 | 样本 | 完全正确 | **集合正确**（忽略顺序） | 项数正确 |
|---|---:|---:|---:|---:|
| 1 | 5 | 0 | 4 | 1 |
| 2 | 5 | 2 | 4 | 3 |
| 3 | 5 | 1 | 4 | 1 |
| 4 | 5 | 0 | 4 | 2 |
| 5 | 5 | 0 | 1 | 1 |
| 6 | 5 | 0 | 0 | 0 |
| **合计** | **30** | **3 (10%)** | **17 (57%)** | **8 (27%)** |

**集合 57% vs 完全 10%** —— 差距全部来自顺序。

典型失败：

| 期望 | 模型输出 | 性质 |
|---|---|---|
| `黄色、橡皮、雨伞` | `黄色、雨伞、橡皮、橡皮、橡皮` | 集合完整，**顺序错** |
| `鱼、马、葡萄、黄色、橡皮、雨伞` | `鱼、橡皮、马、黄色、葡萄、雨伞` | **6 项全在，顺序打乱** |
| `北京` | `北京、黄色` | **不终止**，多输出 |
| `武汉、狗、蓝色、草莓` | `武汉、草莓、蓝色` | 集合缺项 |

### 三个独立缺陷

1. **顺序**：几乎从不正确（3/30），且集合正确时顺序仍错 → **顺序未被存储**
2. **计数/终止**：连长度 1 都失败（`北京`→`北京、黄色`）→ 不知道列表何时结束，只学到"典型长度"
3. **集合容量**：长度 ≤4 时 4/5 稳定，≥5 崩塌 → 记忆的**项数容量**约 4

## 三、架构层根因

`greedy_pipeline_grouped_model.hpp` 的 H2R 记忆实现：

```cpp
auto kt=group<2>({p+"mem.key",p+"mem.query"},{&xn,&xn},dk);
auto k = kt[0], q = kt[1];          // k,q = W·xn
auto v = linear(p+"mem.value", xn, dv);
// 归一化 k，算 beta，delta 规则更新 M (dv x dk)，读出 o = M' q
```

**`k` 完全由内容导出（`W_key·xn`），没有任何显式位置分量。**

因此 `M` 的寻址是 **内容寻址 = 集合语义**：
- 写入第 i 项 → 地址由该项内容决定
- 读出 → 按内容匹配
- **没有任何机制记录"第 i 项"这个事实**

顺序只能间接落在 128 维循环状态 `s` 上（`s += sigmoid(a)·(tanh(u)−s)`），
而 `s` 同时还要承载其他信息，几项之后就被覆盖。

> 这解释了为什么**集合能取回、顺序取不回**——正是内容寻址存储的定义性质。

## 四、受控实验：架构容量 vs 数据配比

L6 语料中列表类仅 3000/19520 篇（15%），且长度集中在 3-5。
**在下结论"架构缺陷"前，必须排除数据配比。**

**实验设计**（已执行）：

- 语料：`data/copy_order/conversations.txt`，**6000 篇纯有序复制**，长度 1..8 **均匀分布**
  （745/683/727/816/728/734/781/786），每条内物品不重复 → 顺序是唯一解
- 导出：`build/copy_order/train.bin`（6000 docs / 284390 tokens / 91195 supervised）
- 训练：`build/copy_order_run`，800 步，与 L6 完全相同的 flag
- 判据：
  - **若顺序正确率显著上升（>50%）** → 数据配比问题，架构无需改动
  - **若顺序仍接近 0** → 架构缺陷，需引入位置通道

## 五、若判定为架构缺陷：候选修复

> **前提**：必须等 §四 实验结果。不得在数据问题未排除时改架构。

| # | 方案 | 代价 | 说明 |
|---|---|---|---|
| A | 记忆键/查询加入**位置分量**：`k_i = W_k·x_i + P_i`，`q_i = W_q·x_i + P_i` | 中（需改 Config/schema/训练器/解码器/bundle，且触碰冻结校验契约） | 使 M 成为**按位置寻址**的存储，直接补上缺失的顺序通道 |
| B | 增大 `s` 容量（128 → 512） | 低（仅 Config） | 若顺序本可存于 `s` 只是容量不足 |
| C | 显式有序缓冲（队列/栈） | 高 | 引入新算子，偏离"双状态"设计 |
| D | 训练端加**计数信号**（prompt 里给出项数） | 低 | 只治缺陷 2（终止），不治顺序 |

**注意**：方案 D 单独使用会作弊式地绕开计数问题，不能作为最终方案，
但可作为**诊断工具**——若给出项数后顺序仍错，则进一步确认顺序是独立缺陷。
