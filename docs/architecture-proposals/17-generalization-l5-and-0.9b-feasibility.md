## 一、泛化修正：真实缺陷是「多问句的回合终止」，不是记忆容量

### 1.1 doc 16 的诊断被推翻（决定性对照）

同一份 H2R `step_400` 权重、同一批 12 个 held-out 名字，只改**问法**：

| 问法 | 名字抄对 | 颜色抄对 |
|---|---:|---:|
| `我叫什么名字？` | **9/12** | 0/12 |
| `我喜欢什么？` | 0/12 | **12/12** |
| `我叫什么名字？喜欢什么？`（两问合一） | 9/12 | **0/12** |
| **同一会话分两轮问**（先名字、再喜好） | **9/12** | **10/12** |

**结论**：
1. **两个槽位都在**，且**查询有选择性**——问名字只出名字、问喜好只出颜色（12/12 全对）。
2. 唯一失败的是**两问挤在同一轮**：模型答完第一槽位就发出回合结束（`end=259`），
   输出 `邬晓东。` 而非 `邬晓东，紫色。`。
3. 所以 doc 16 提出的「读前写 / 加大 dk / 多槽位」是**针对不存在的问题**——
   H2R 的记忆容量够用，`dk=64` 也够用。

对照 `dual-state-3`（同一测试）：

| 问法 | ds3 名字 | ds3 颜色 |
|---|---:|---:|
| 只问名字 | 3/12 | 0/12 |
| 只问喜好 | 0/12 | 6/12 |
| 两问合一 | 2/12 | 5/12 |

ds3 **单问也读不准**（3/12、6/12），且从不产出「两者都对」（0/12）——
这印证 doc 16 的主结论：**H2R 的寻址是架构里唯一能把内容读出来的机制**。

### 1.2 为什么不是数据缺失

L4 语料中 `我叫什么名字？喜欢什么？` 出现 **1728** 次，且**答案格式 100% 正确**：

```
U 我叫什么名字？喜欢什么？
A 郝子墨，牛奶。          ← 1728/1728 都是「X，Y。」
```

但**单问形式更多**：`我叫什么名字？` 有 **4231** 条。两者共享前缀
`我叫什么名字？`，且单问的样本量是合一的 2.4 倍 ——
模型学到「看到这个前缀 → 答一个名字 → 结束回合」的先验，压过了合一问法的正确续写。

**这是语料配比问题，可以用语料修。**

### 1.3 L5 语料（修法）

`scripts/gen_corpus_l5.mjs` → `data/noffn_l5/conversations.txt`

| 类别 | L4 | **L5** | 说明 |
|---|---:|---:|---|
| **多问合一** | 1 728 | **7 200** | **6 种问法**各 1200，防止前缀匹配 |
| 单问 | 4 231 + 1 731 | 1 600 | 下调，削弱「答一个就停」的先验 |
| 一问一答交替 | 0 | 1 200 | 教会「只问一半就只答一半」的边界 |
| 列表复制 | 3 500 | 3 000 | |
| 原样复制 | 1 500 | 1 200 | |
| 算术 | 2 500 | 2 000 | |
| 静态事实 | 720 | 720 | |
| 话题承接 | 400 | 400 | |
| **合计** | 18 038 | **17 320** | |

多问合一的 6 种问法（各 1200 条）：

```
我叫什么名字？喜欢什么？
我叫什么名字？我喜欢什么？
我叫什么？喜欢什么？
我叫什么名字，喜欢什么？
请说出我的名字和喜好。
我的名字和喜好分别是什么？
```

答案一律 `名字，喜好。`（与 L4 一致）。held-out 名字集与 L4 **完全相同**并继续排除在训练之外
（马超/郭静/孙丽/小林/小马/小孙/刘洋/小树 + 本轮 12 个：邬晓东/鲁刚/毛小华/魏娜/梁华/罗明轩/孔桂英/谢小虎/任小凤/柏小军/夏勇/高然）。

### 1.4 预登记判据

用 L5 训练 H2R，与 L4 的 H2R `step_400`（NLL 0.346）在**匹配 NLL** 下比较：

| 指标 | L4 H2R @400 | L5 目标 |
|---|---:|---|

| **两问合一：两者都对** | **0/12** | **≥ 8/12**（首要） |
| 单问名字 / 单问喜好 | 9/12 / 12/12 | 不劣化 |
| 列表复制 | 1/3 | ≥ 2/3 |
| 原样复制（语料外） | 0/5 | ≥ 1/5 |

## 二、0.9B 对标的硬件可行性

### 2.1 硬件实测

| 项 | 值 |
|---|---|
| GPU | **NVIDIA GeForce RTX 4070 Laptop**（wmic 报 4 293 918 720 B，32 位字段上限；实际 **8 GB**） |
| 核显 | AMD Radeon 780M |
| 系统内存 | **47.2 GiB**（50 692 796 416 B） |
| `nvidia-smi` | **NVML 初始化失败**（`Unknown Error`）→ 监控不可用，但 CUDA 训练本身正常（H2R 400 步已跑完） |

### 2.2 参数量口径（精确）

本模型参数 = `embedding` + 每层 12 个三值矩阵 + 少量 bias/norm。

```
embedding + vocab.bias + final.norm = 8 405 504
每层（含 bias/norm）                = 1 673 472
每层（仅三值矩阵）                  = 1 671 168
```

| 配置 | 三值矩阵元素 | 全参数 | 核对 |
|---|---:|---:|---|
| **当前 2 层** | **11 730 944** | 11 752 448 | |
| 8 层（上一轮） | **21 757 952** | 21 793 280 | 与记录一致 ✓（97 个三值矩阵 = 1 + 12×8） |

### 2.3 0.9B 的几种放法

| 配置 | 全参数 | 每层 |
|---|---:|---:|
| d=2048 s=512 m=2048 vocab=65536 **L=28** | **0.883 B** | 26.75 M |
| d=2048 s=512 m=2048 vocab=65536 **L=29** | **0.910 B** | 26.75 M |
| d=1024 s=256 m=1024 vocab=32768 L=64 | 0.462 B | 6.69 M |
| d=512 s=128 m=512 vocab=16384 L=534 | 0.902 B | 1.67 M |

> 注意最后一行：**靠堆层数到 534 层**在本架构里不可行——它是**逐层串行的递归**
> （每 token 必须依次过完所有层），534 层会让单 token 延迟线性爆炸。
> 所以 0.9B 必须**加宽**（d/m/vocab），不能只加深。

### 2.4 显存账（关键约束）——**按代码实际口径重算**

> ⚠️ 本节初版按「AdamW 12 B/参数」估算，**低估了实际占用**。核对
> `src/dual_state_sorted_trainer.cuh` 与 `src/gpu_adam_device.cuh` 后，真实口径是：

`SortedGpuTrainer` 对**每个张量**持有 5 份 fp32 缓冲：

| 缓冲 | 来源 | 字节/参数 |
|---|---|---:|
| `master` | `SortedGpuTrainer` 成员（fp32 主权重） | 4 |
| `moment` | 同上（Adam 一阶） | 4 |
| `variance` | 同上（Adam 二阶） | 4 |
| `grad` | `graph.w[name]->grad`（fp32 梯度） | 4 |
| **生效权重** | `graph.w[name]->value`（三值投影后的 fp32 权重，前向/反向都要用） | 4 |
| **合计** | | **20 B/参数** |

（另有 `scales`，每行 1 个 float，可忽略。）

| 配置 | 参数 | 实际显存（20 B/参数） | 8 GB 卡 |
|---|---:|---:|---|
| 当前 2 层 | 11.75 M | 0.24 GB | ✅ |
| 上一轮 8 层 | 21.79 M | 0.44 GB | ✅ |
| **0.883 B** | 883 M | **17.7 GB** | ❌ |
| **0.910 B** | 910 M | **18.2 GB** | ❌ |
| 0.462 B（d=1024 L=64） | 462 M | 9.2 GB | ❌ 仍不够 |

**结论：按现有 20 B/参数口径，连 0.46 B 都装不下 8 GB 卡。**
激活不是瓶颈（本架构是 per-token 递归 + slot 分块，激活只有 `slots×d` 量级）；
**瓶颈全在参数与优化器状态。**

### 2.5 可行的四条路（重新排序）

| 方案 | 做法 | 0.9B 显存 | 代价 |
|---|---|---|---|
| **A. 优化器状态 CPU offload**（**推荐**） | `master`/`moment`/`variance` 放 47 GB 主机内存；GPU 只留生效权重 + 梯度 | **3.6 GB**（bf16 权重+梯度 4 B/参数） | 每步 PCIe 往返 ≈ 0.9B×8 B = 7.2 GB → 笔记本 PCIe4 x8 下约 1 s/步；改动**局部**（只动 `update()`/`project()`） |
| **B. 混合精度 + 去 variance**（原 C1） | master/moment/grad/生效权重全改 bf16 → 8 B/参数 | **7.2 GB** | 单独做**仍装不下**（可用显存约 7.5 GB，无余量）；需与 A 叠加才稳 |
| **C. 降规模** | d=1024 s=256 m=1024 vocab=32768 **L=64 ≈ 0.46 B** | 9.2 GB（现状）/ 3.7 GB（配 A） | 不是 0.9B |
| **D. 分层扩宽** | 先训小模型，再 net2net 扩宽 | 分阶段可控 | 需实现扩宽逻辑 |

**修正后的推荐：A 为主，B 为辅。**
- 只做原 C1（去 variance，12→8 B/参数）**不够**——0.9B 仍需 7.2 GB，无余量；
- **A（CPU offload）是唯一能让 0.9B 在 8 GB 卡上跑起来的路**，且它不改变数值语义（R4 安全）；
- A+B 叠加后 GPU 侧仅 3.6 GB，留出充足余量给投影缓冲与碎片。

> 注：原 doc 06 的 C1 目标是**训练吞吐/质量**（Muon 风格更新），
> 与「省显存」是两件事，不应混为一谈。省显存靠 offload，不靠换优化器。

### 2.6 数据侧的缺口（比显存更严重）

当前全部语料是**程序化生成的合成任务**（L4 17 320 篇 / 750 K token）。
0.9B 模型按 Chinchilla 比例需要 **≈ 18 B token**。即使按「小模型可多训几轮」放宽到 20× 参数，
也需要 **≈ 18 B token**；而现有语料是 **0.75 M token**——**差 4 个数量级**。

真实训练必须解决数据来源，选项：

1. **放大合成器**：L5 生成器是程序化的，可无成本扩到任意规模（但**多样性上限=模板数**，
   纯合成数据训出的 0.9B 只会更擅长合成任务，不能「对标」真实大模型）
2. **接入真实语料**：仓库里已有 `export_repair_bpe_train.cpp`（读 parquet）与
   `build/repair_export_20260909_v2/train.bin`（**5 953 644 token**）——仍是 0.75 B 的 1/3000
3. **公开语料**：需要联网下载（当前 `web_search` 不可用，且下载 TB 级数据受磁盘/带宽限制）

> **这是必须先与用户确认的关键点**：0.9B「对标 transformer」的**数据从哪来、对标什么基线**。
