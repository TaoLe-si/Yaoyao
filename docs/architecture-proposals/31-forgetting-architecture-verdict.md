# 31 · 「学新忘旧」是架构问题吗？——实测判定

> 2026-09-12。由用户提问"底层架构是否存在问题，学了新的就很容易忘了旧的"驱动。
> 全部数字为本机实测：权重 NLL 探针 + 训练日志分片统计。

## 零、结论

**有遗忘，实测存在。但主因不是架构，而是训练方式 + 计算容量。**

| 成分 | 证据 | 判定 |
|---|---|---|
| 零排练的顺序课程 | 25 片互不重叠、每片只过一遍、LR 恒定 5e-5 | **主因** |
| 计算容量极小 | 88.3% 参数是查表；真正的计算层只有 1,114,112 ternary = **216 KB** 信息量 | **主因** |
| ~~读出无 query~~ | **已不适用**：交付模型是 `delta-mem`，读出本为 `o = M q` | doc 10 测的是旧算子 ds3，见 doc 32 §三 |
| 计数/终止通道 | doc 26 | **唯一已确认的架构性缺陷，与遗忘无关** |

## 一、遗忘的实测值

用低 LR（1.1e-6）在旧语料上跑 2 步，`train_preupdate_NLL` 即**原始权重**上的损失，
与训练日志同口径可比。两个模型对照：

| 模型 | 维基 NLL | 推理 NLL | alpaca NLL |
|---|---|---|---|
| `s2_wiki_phase`（维基训练刚结束，step 27659）| **4.6502** | 4.8663 | 5.1369 |
| `s2_night1`（最终，step 50659）| **5.3586** | **3.5185** | **4.2083** |

- 学会推理：4.8663 → 3.5185（**−27.7%**）
- 学会 alpaca：5.1369 → 4.2083（**−18.1%**）
- 忘掉维基：4.6502 → 5.3586（**+15.2%**，ΔNLL = +0.7085）

**这是同一个模型、同一批权重**：新技能涨、旧技能退，典型的灾难性遗忘。

## 二、但域内完全不遗忘 → 遗忘由「换域」触发，不是持续漂移

按分片统计 NLL（前 50 步均值 → 后 50 步均值）：

```
shard  范围            首50     末50     降幅    域
 0    21625–25660    5.888    4.810   −1.079   维基（起步快降）
 1    23543–26660    4.906    4.767   −0.140   维基
 2    26661–28659    4.828    4.756   −0.072   维基
 3    28660–29659    4.768    4.770    0.002   维基
 4    29660–30659    4.733    4.728   −0.004   维基
 …    5–12          全部在 4.63–4.77 之间小幅震荡，无上升趋势
13    38660–39659    2.414    1.193   −1.221   ★推理（起步快降）
14–16 39660–42659    1.2→1.01            推理
17    42660–43659    5.342    4.511   −0.831   alpaca（起步快降）
18–24 43660–50659    4.50→4.28            alpaca
```

**关键**：每进入一个新域，NLL 从该域的起点快速下降然后**平台化**；
**域内完全不上升**。遗忘只在**切域**时发生。

这说明模型有能力保持已学技能（权重不会自己漂），遗忘是**新域梯度把旧域解推走**。

## 三、为什么说主因是训练方式：零排练

`data/stage2_reason` 的 25 个分片：

- **互不重叠**（13 维基 + 4 推理 + 8 alpaca，不同语料）
- 每片**只过一遍**（`steps_per_shard=1000`，无 epoch 循环）
- 维基→推理→alpaca **纯顺序**，旧数据不再出现
- LR **恒定 5e-5**（无衰减、无 warmup 之外的第二阶段）

这是灾难性遗忘的教科书设置：**没有任何排练（rehearsal），没有任何巩固机制**。
任何架构在这个设置下都会遗忘 —— 遗忘不是架构的特征，是"只喂新数据"的必然结果。

## 四、架构确实贡献了什么：容量

参数账目（`src/dual_state_config.hpp` 的 schema 精确计算）：

```
embedding(vocab×d)     8,388,608 ternary   ← 88.3%
两层计算权重            1,114,112 ternary   ← 11.7%
float 张量(偏置/norm)       20,482
合计                    9,523,202

ternary 每权重 1.585 bit（log2(3)）：
  全部权重信息量   ≈ 1.80 MB
  **计算层信息量   ≈ 216 KB**（1,114,112 × 1.585 / 8 / 1024）
```

**216 KB 要装下维基事实 + 数学推理 + 指令遵循 + 中文生成。**
这是遗忘的结构性放大器：容量越紧，新旧解越互相挤占。

（embedding 占 88% 不能算"浪费"——它是词表查表，vocab=16384 × d=512 的数学必然。）

## 五、~~读出无 query~~：更正 —— 交付模型已有 query 读出

> **2026-09-12 更正**：本节原称"读出 `r = W_rs·s + W_rm·m` 无 query"。经核对交付模型
> `build/s2_night1/final.dsb` 的 DSB2 头部，算子身份为 `dual-state-4-noffn-delta-mem-input-sqrt-d`，
> schema 含 `layer.*.mem.key / mem.query / mem.value`，读出实为 `o = M q`（**带 query**）。
> doc 10 的"无 query"结论出自**旧算子 dual-state-3**，不适用于当前模型。详见 doc 32 §三。
>
> 下文保留原文以便追溯。

doc 10 实测：读出 `r = W_rs·s + W_rm·m` 是**与问题无关的固定线性投影**，
于是"信息在状态里但取不出来"（状态 LOO 可解码 33–81%，交叉注入绑定率 0/18）。

**但 doc 10 §6.1 已自我推翻该结论的架构归因**：
probe3 用 361 篇绑定样本（probe2 的 19 倍）重跑，**同一套算子**：

| | probe2 @113 步 | probe3 @100 步 |
|---|---:|---:|
| 两者都对 | **0/18** | **10/18**（其中 8/14 是语料外新组合）|

**→ 判定：是数据问题，不是架构问题。** 相同算子给了足够数据就学会了绑定。

所以"读出无 query"是一个**容量/数据效率**上的弱点，不是遗忘的成因。

## 六、结论与处置建议

**回答用户的问题**：架构**不是**遗忘的主因。实测遗忘 +15.2%，发生在纯顺序、零排练、
恒定 LR、且计算层只有 216 KB 的设置下 —— 这是训练方式的必然结果，换任何架构都一样。

**代价最低、最可能有效的处置（按性价比排序）**：

1. **加排练**：每个新阶段混入 5–10% 的旧域数据。改课程顺序即可，**不需改架构、不需重训**。
   这是对抗遗忘的标准手段，且我们的 `steps_per_shard` 全局机制让"每 k 片插 1 片旧数据"很容易实现。
2. **LR 衰减**：末段降 LR 让权重收敛（现为恒定 5e-5）。同样零架构改动。
3. **扩计算容量**：加深/加宽 `layers` 或 `d`，或引入真正的记忆寻址（doc 04 engram）。
   代价最高，建议在 1、2 之后仍不足时再做。
4. **不要为遗忘去动读出结构** —— doc 10 §6.1 已证那是数据问题。

## 七、本次测量的限制

- 遗忘值是**单点对照**（两个模型 × 一个语料），不是完整遗忘曲线。
  `step_*` 检查点只含 `final.dsb`（`DSB2` 格式），而续训需 `opt_state`（不同 magic），
  已实测 `opt state magic mismatch` → **无法从中间检查点做遗忘曲线**，除非改导出格式。
- 旧语料 NLL 探针用 `build/alp_big` 与训练用的同 2 份文件，不能反映 alpaca 全集。
- 维基对照模型 `s2_wiki_phase` 是**另一次运行的暂停点**，与 `s2_night1` 的维基段不完全同源。
