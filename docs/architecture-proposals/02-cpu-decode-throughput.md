# CPU 解码吞吐路线书：从 680 到 10 000 token/s

> 目标（待 D1 拍板）：CPU 单会话解码吞吐达到「同量级」以上。参考：大模型服务端单用户 decode 通常 20–100 token/s（数量级 10²），**夭夭当前实测已是 680 token/s（同为 10²）**，因此真正的目标档位需要显式定义：
> **T1 ≥1 000**（≈已达成）／**T2 3 000–5 000**（高一个数量级）／**T3 ≥10 000**（高两个数量级）。

---

## 一、口径约定（不遵守会得出错误结论）

| 口径 | 含义 | 本项目数值 |
|---|---|---|
| **DSB 打包口径** | 磁盘/传输：2 bit/权重 + 每行 float32 α | 5,798,167 B |
| **解码器常驻口径** | 运行时 RAM：`read_compact_bundle` 展开为 int8，**1 字节/权重** | **22,112,256 B ≈ 22.1 MB** |

**内存与带宽的一切结论都必须用常驻口径。** 早期版本曾按 DSB 口径断言「整模型可常驻 16 MB L3」，该结论**作废**（22.1 MB > 16 MB）。

复现：`node docs/architecture-proposals/tools/dsb_ledger.mjs build/noffn_fresh/step_1512/final.dsb`

## 二、诊断

### 2.1 实测基线（2026-09-10）

| 项 | 值 |
|---|---|
| 解码吞吐 | 正常回复 **680.8 token/s**（20 次平均）；强制贪心 512 步 572–681 token/s；1.47–1.75 ms/token |
| 并行度 | **2 线程**（`CpuRowParallelExecutor`：caller + 1 常驻 worker，触发阈值 262 144 元素） |
| 每 token MAC | 21,757,952（输出头 38.6 %；8 层 61.4 %） |
| 每 token 权重字节（常驻） | 22.1 MB |
| 加载 | 约 105 ms |

### 2.2 Roofline：当前很可能压在内存带宽墙上

- 实测吞吐 680 token/s ⇒ 22.1 MB × 680 ≈ **15.0 GB/s** 的权重流量；
- 实测算力 21.76 M MAC / 1.47 ms ≈ **14.8 G MAC/s**；
- 由于当前内核是 **1 字节权重 / 1 次 MAC**，两个数字**几乎重合**——这是「带宽受限」的典型特征，而非巧合。

### 2.3 假设判定（S3 已完成 → **H-BW 成立**）

| 假设 | 判据（线程 2→8） | 实测 | 结论 |
|---|---|---|---|
| **H-BW：带宽受限** | 吞吐涨 <2×，且每 token 字节数不变 | **1.113×**（844.8 vs 747.6），带宽封顶 18.68 GB/s | ✅ **成立** |
| **H-UOP：指令受限** | 近线性增长但每线程 MAC 率不升 | 每线程 MAC 率**崩塌** 8.13 → 4.60 → 2.26 G MAC/s；4→8 线程 0.99×；16 线程 0.96× | ❌ 不成立 |

补充否证（都指向带宽）：

- 把并行分发阈值从 262 144 降到 **1**（连串行的 s 组也并行）**无收益**：845.9 → 825.6 tps（复测 834.5 → 814.7）。
- 关键恒等式：`18.68 GB/s ÷ 22.112 MB/token = 845 tps`，与 4 线程实测 **844.8 tps** 吻合到 3 位有效——整条曲线由 `tps = 带宽墙 / 每 token 常驻字节` 完全解释。

> 因此 **S6（减指令）降级**，S1（减字节）升为第一位。完整证据、相位分解与诚实边角见 **08 号文档**。
> 另有实测副产物：**词表头 27.67 G MAC/s（embedding 8.39 MB 命中 L3）远高于 m 更新组 18.07 G MAC/s（层 13.37 MB 走 DRAM）**——这实测加强了 S4「把唯一工作集压进 16 MB L3」的理由。

## 四、杠杆清单

### S1 · 2-bit 打包常驻 + 内核内展开（**最高优先级**）

- **动机**：常驻布局从 int8（1 B/权重）改回 2-bit 打包，每 token 权重字节 22.1 MB → **5.8 MB**（−74 %）。
- **做法**：
  1. `CompactBundleData::Matrix` / `PipelineRows` 保留打包码（每行 `ceil(cols/4)` 字节）而不是展开成 int8；
  2. `dot()` 内按 16/64 列一组：`vpmultishiftqb` 抽字段 → `vpermb`（64 项 LUT）→ int8 `{0,+1,-1}`；
  3. 之后**沿用现有 float 路径与累加顺序**（同样 16 列一组、同样的 lane 折叠），**保证与现网结果 bitwise 一致**；无 AVX-512 时回退到 `vpshufb`/查表实现。
- **预期**：若 H-BW 成立 → **1 700–2 600 token/s**（约 2.5–3.8×）。
- **验收**：① 与现网 int8 路径在 32 步贪心上 **bitwise 一致的 logits/状态/argmax**；② 常驻字节实测 ≈5.8 MB；③ token/s ≥1 700。
- **风险**：低（纯布局+内核改造，数值不变，可一键回退）。

### S2 · N 线程行池（**第二优先级**）

- **动机**：当前只用 2/16 线程；每个投影的**行之间完全独立**，按整行切分不改变任何一行的浮点加法顺序 → **bitwise 不变**。
- **做法**：把「caller + 1 worker」的 `CpuRowParallelExecutor` 泛化为 N-worker 行池（新文件 `src/cpu_row_parallel_pool.hpp`），阈值改为「每线程最少行数」（例如每线程 ≥32 行才并行，避免小块投影的同步开销），并用亲和性绑定到 8 个物理核。
- **预期**：5.8 MB/token 下 **3 000–6 000 token/s**（上限由 DRAM ~40–50 GB/s 或 L3 决定）。
- **验收**：多线程与单线程 bitwise 一致（复用现有 identity 测试）；1/2/4/8/16 线程扫描曲线入档。
- **风险**：低；注意只有 ≥最小行数的投影才并行，RMSNorm 归约与状态更新仍是串行段。

### S3 · 判定实验（1 天，**决定后续投入方向**）

线程扫描 + 带宽估算，回答 §2.3 的两个假设。附带产出：RMSNorm / s 更新 / m 更新 / read+残差 / 词表头各自的毫秒分解（把 `benchmark_noffn_decode.exe` 扩成分解计时）。

### S4 · 层维复用（详见 03 号文档）

唯一 int8 权重 21.76 MB → **11.74 MB**（+ 尺度与浮点 ≈ 11.9 MB）→ **装进 16 MB L3**；每 token 字节 ~11.9 MB 且大部分命中 L3。需要重训与新算子身份。
  > 【口径更正，DOC7】原文「预期 8 000–15 000 token/s」**只在叠加 S1 之后成立**。分开算：
  > - **S4 单独（仍是 int8 常驻）**：R3 唯一 11.73 MB → 按 DRAM 墙 18.68 GB/s 得 **1593 tps**，按头实测的 L3 速率 27.7 GB/s 得 **2360 tps**。
  > - **S1 + S4（打包）**：R3 唯一元素 11,730,944 → 打包约 **3.0 MB** → **6227 tps**（DRAM 墙）～**9220 tps**（L3 速率）。
  > 即 8000+ 是「S1 已做 + 工作集真的进了 L3」两个条件同时成立时才有的数字。

### S5 · 候选池词表头（详见 03/06 号文档的评测纪律）

输出头占 **38.6 % MAC / 37.3 % 字节**；两段式（簇分数 → top 簇内精算）可把 8.39 M MAC 降到 ~0.5 M、头部流式字节降到 ~20 KB 量级。**必须在训练期使用同一受限域**（论文纪律），并保留全词表诊断路径。

### S6 · int8 激活 + `vpdpbusd`（**仅在 S3 判定为 H-UOP 时才做**）

- 做法：激活量化成 uint8（零点 128，按 32/64 分块带 scale）；权重 2-bit 打包、内核内展开成 int8；`vpdpbusd` 每指令累加 64 个 MAC；结果按「每行 α × 激活块 scale」反量化。
- 代价：**数值改变** → 新算子身份 + **激活 QAT**（训练期施加同样量化，I4）+ CPU/CUDA 双路径同步。
- 预期：点积段 3–6×；与 S1/S2 叠加后进入 T3 区间。

### S7 · Engram 记忆表（详见 04 号文档）

每 token 只增加约 1.5 KB 稀疏访问，**与表大小无关**，因此「参数量增长」可以放在表里而不拖慢解码。前提：确定性寻址 + 预取流水线 + 大页。

### S-extra · s→m 依赖错位（mHC 类比，可选）

当前每层 m 分支读**更新后的 s_t**，使 s 段与 m 段必须串行、两次遍历。把 m 改为读 **s_{t−1}**（错位一步）可让两段融合成一遍遍历（对应 Mega-mHC 的 (2n+2)d 访存）。论文经验：性能损失可忽略。收益估计 5–15 %，风险是需要同步改 README 的数学定义与 CPU/CUDA 两条路径。

## 五、死路清单（已用实测否掉，勿再尝试）

| 死路 | 实测依据 |
|---|---|
| **索引式稀疏存储**（只存非零 + 索引/符号） | 三值零元素占 45.82 %，但逐行密度中位 54.3 %（范围 27.3–73.4 %），**没有极稀疏行子群体**；索引+符号 ≥10 bit 远差于 2 bit/元素。 |
| **Cauchy–Schwarz 上界精确剪枝**（词表头/任何线性层） | 行尺度 α 全体极差 3.61×、**仅 embedding 2.16×**；用 RMS 归一化随机 x 模拟，**可剪枝比例 0 %**；且分数顶端很平（top1/top2 差约 5.6 %）→ 精确剪枝不可能，只能「近似 + 训练期同域」。 |
| **「整模型常驻 L3」** | 那是 DSB 打包口径的错觉；解码器常驻是 22.1 MB > 16 MB L3。 |
| **token 级投机解码（DSpark 类比）** | 顺序递归：验证 k 个 draft 仍需 k 次串行状态更新，零收益。 |
| **盲目加大 AVX2 展开/线程数** | 【已实测】4 线程即饱和：2→4 线程 +11.1 %，**4→8 线程 0.99×**，8→16 线程 0.96×，每线程 MAC 率从 8.13 崩到 2.26 G MAC/s。加线程已到顶。 |
| **把三值权重换成 int8 存储来提速** | 方向相反：那会把常驻体积从 5.4 MB（打包）抬到 21.8 MB。 |

- **2 位打包减字节**：内核速率从 L1 到 8.39 MB 完全平坦（§14.2），**不是带宽受限**，减字节收益为 0。

## 附录 A · 「14 000 t/s 能否达到」的定量回答（2026-09-11）

> 问题：引入论文（V4.1）的架构优化方式（Engram + 层维复用），CPU 解码能否达到 **14 000 t/s**？
>
> **结论：不能。论文那两项架构优化单独最多给约 1.9–2.0×，叠加内核优化后约 5 000–8 000 t/s；
> 14 000 t/s 需要额外攻「输出头」和「多核扩展」两项，二者都不在论文的架构优化范围内。**

### A.1 已知事实（全部实测）

| 事实 | 数值 | 来源 |
|---|---|---|
| 基线 CPU 解码（4 线程） | **932.8 tps** | §十一 交错测量 |
| R3 层共享 | 1183.2 tps（1.269×） | §十一 |
| **R3 + R4** | **1637.0 tps（1.755×）** | §十一 |
| 耗时与层数关系 | 8→4 = 2.018×，8→2 = 2.980× | §十一（近线性） |
| 线程扩展 | 2→4 = 1.32×，4→8 = 0.99×（饱和） | §9.5 |

### A.2 架构路线的上限（MAC 账）

每 token MAC：输出头 8,388,608（38.6%）+ 8 层 × 1,671,168。
每层拆解：`s` 分支 163,840 / **`m` 分支 1,179,648** / 读出 327,680。

| 配置 | 每 token MAC | 相对 | 实测 |
|---|---:|---:|---:|
| 现状 R0 | 21,757,952 | 1.000 | 932.8 tps |
| R3+R4（2 组） | 14,680,064 | 0.675 | 1637.0 tps（1.755×） |
| **极限**：1 组全共享 + R4 | **13,500,416** | **0.620** | 未测，预估 ≈1.9× |

**⇒ 架构路线的天花板约 1.9–2.0×（≈1 800 tps）。**
原因：**输出头占 38.6% 且完全不随层数/共享缩小**（Amdahl 下限）。
R3+R4 实测 1.755× **已经吃到架构余量的大部分**。

### A.3 内核路线（本次新测）

`src/microbench_dot_kernels.cpp` / `build/microbench_dot_kernels.exe`：

| 内核 | 形状 | ms/pass | G MAC/s |
|---|---|---:|---:|
| AVX2 float（现状 `PipelineRows::dot`） | 16384×512 | 0.613 | **13.7** |
| VNNI int8（`vpdpbusd`） | 16384×512 | 0.229 | **36.6** |
| AVX2 float | 512×512 | 0.019 | 13.8 |
| VNNI int8 | 512×512 | 0.006 | 42.8 |

**⇒ 内核余量 = 2.67×（头形状）/ 3.10×（m 形状）。**

> **修正一处我自己的错误估算**：现状内核每 16 权重用约 10 条指令（1.6 MAC/指令），
> 而 VNNI 是 64 MAC/指令，据此我一度估出「约 40× 余量」。
> **实测只有约 3×** —— 说明瓶颈不在指令发射（与 02 号 §2.3 的带宽判断方向一致）。
> **教训：指令数之比不能当作吞吐之比。**

### A.4 把各项相乘

| 杠杆 | 倍数 | 依据 |
|---|---:|---|
| 架构（层共享 + R4，推到极限） | ≈1.9–2.0× | A.2 |
| 内核（VNNI int8 激活） | ≈2.7–3.1× | A.3 |
| 多核扩展 | **未知，目前 4→8 线程 = 0.99×** | §9.5 |

乐观连乘：`932.8 × 2.0 × 3.0 = 5 597 tps`；若线程扩展能再拿 1.4×，约 **7 800 tps**。

**⇒ 约 5 000–8 000 t/s，达不到 14 000。**

### A.5 要达到 14 000 t/s 还缺什么

反推所需算力：14 000 tps × 13.50 M MAC = **189 G MAC/s**。

| 来源 | 单核能力 | 需要 |
|---|---:|---|
| AVX2 float 现状 | 13.7 G MAC/s | 13.8 核 |
| VNNI int8 | 42.8 G MAC/s | **4.4 核（满效率）** |

即：**必须同时做到 ①VNNI 内核 ②架构压到 13.5 M MAC ③4.4 个核满效率并行**。
而当前 4 线程下实测只有 `1637 × 14.68 M = 24.0 G MAC/s`，
相对 4 核 VNNI 的 171 G MAC/s 只利用了 **14%** —— **并行效率才是最大的缺口，不是内核也不是架构。**

三个可能的缺口来源，按怀疑程度排序：

1. **层间串行依赖**（§11.2 已证）：`m` 的更新依赖上一层 `m`，层不能并行；
   线程只能并行层内行，且每层末的 RMS/残差是同步点。
2. **输出头与 embedding**：8.39 M MAC 且是单次大矩阵向量乘，行间可并行度高（2→4 线程 1.65×），值得单独优化。
3. **状态更新（`tanh`/`sigmoid` 逐元素）**：`m` 有 512 个元素 × 8 层，含超越函数，可能是隐藏的串行尾。

### A.6 一句话结论

**论文的 Engram 与层维复用是「容量/带宽」类优化，而实测瓶颈是「层内串行计算」——
两者不在同一维度上。** 它们值得做（R3+R4 实测 1.755×），但**指着它们达到 14 000 t/s 是不成立的**；
14 000 t/s 的主战场在**并行效率（层间串行、层内同步点）与输出头**，不在论文的架构优化里。

## 十二、并行分发是真正的瓶颈：自旋屏障（2026-09-11 续）

### 12.1 关键观测：R3+R4 的线程扩展只有 1.10×

| 线程 | 1 | 2 | 4 | 8 | 16 |
|---|---:|---:|---:|---:|---:|
| R3+R4 tps（睡眠屏障） | **1210** | 1148 | 1640 | 1631 | 1336 |

**单线程已 1210 tps，1→16 线程仅 1.10×。** 多线程几乎完全无效。
而单线程相位**完全由 MAC 数解释**：head 0.338 ms（8.39 M ÷ 24.8 G/s）、body 0.479 ms（6.29 M ÷ 13.7 G/s）。
⇒ **瓶颈不是内核，也不是架构，而是并行分发本身。**

### 12.2 根因：每次分发是一次条件变量 fork-join 屏障

`cpu_row_parallel_pool.hpp` 的 `run()` 每调用一次就：取两把锁 → `ready_.notify_all()` 唤醒全部 worker
→ 调用方做自己那份 → `done_.wait()` 等全部完成。**走 futex 睡眠/唤醒路径。**

**量化证据**（`s_update` 相位 = `group<4>`，真实工作量约 96 µs）：

| 线程 | 1 | 4 | 8 | 16 |
|---|---:|---:|---:|---:|
| s_update ms | 0.124 | 0.153 | 0.180 | 0.239 |

1 线程 124 µs ≈ 纯工作量 ✓；**4 线程反而 153 µs** ⇒ 8 次分发多出约 120 µs，即**每次屏障约 15 µs**。
每 token 约 32 次分发 ⇒ **约 480 µs 纯同步开销，而整个 token 才 610 µs**。

### 12.3 改动：原子自旋屏障（`TAO_POOL_SPIN=1`）

用 `std::atomic<unsigned>` 代次计数 + `_mm_pause()` 自旋替代条件变量。
**行划分 `bounds[k] = rows*k/n` 与同步机制无关 ⇒ 数值完全不变。**

**实测（交错 3 轮，R3+R4 中位 tps）：**

| 线程 | 睡眠 | 自旋 | 比 |
|---:|---:|---:|---:|
| 1 | 1244 | 1214 | 0.98× |
| 2 | 1154 | 1055 | 0.91× |
| 4 | 1493 | 1703 | **1.14×** |
| 8 | 1767 | **2153** | **1.22×** |

- **优势随线程数增长**（1.14× @4 → 1.22× @8）——正是"睡眠开销随线程数增加"的预期
- 1–2 线程略慢属预期（没有并行收益时自旋纯属浪费）
- **checksum 全程 = 259，与改动前一致 ⇒ I4「训练/推理同一算子」不变量未被破坏** ✓

**相位改善（4 线程，R3+R4）：**

| 相位 | 睡眠 | 自旋 | 改善 |
|---|---:|---:|---:|
| read_residual | 0.199 | **0.082** | **2.4×** |
| m_update | 0.157 | 0.102 | 1.54× |
| body_total | 0.502 | **0.320** | **1.57×** |
| head | 0.251 | 0.204 | 1.23× |

### 12.4 修复过程中踩到的两个真实 bug（均已修）

1. **停止竞态**：`stop_workers` 同时置 `spin_stop_` 并自增代次，worker 会先退出内层等待、
   **执行一次伪造任务**。修法：内层循环先判停止标志再读代次。
2. **代数未归零（导致 0xC0000005 访问违例）**：停止时自增代次后 `spin_gen_` 非 0，
   而 `set_threads` 新建的 worker 从 `seen=0` 开始 ⇒ **首轮即误判为新代次**，
   调用已销毁的 lambda（`context_` 悬垂）⇒ 崩溃。修法：停止后把 `spin_gen_` 归零。

## 十三、自旋屏障解锁阈值下调（2026-09-11 续）

### 13.1 病灶：`group<4>`（s 更新）从来没并行过

`min_elements_ = 262144` 是**元素总数**阈值，而判定用的是**行数**：
`rows < (min/cols + (min%cols != 0))`。

`s` 分支 `group<4>`：rows = c.s = **128**，cols = d+s+d+s = 1280 ⇒ 门槛 = 262144/1280+1 = **205**。
`128 < 205` 成立 ⇒ **永远走串行回退**。这解释了 §12 里 `s_update` 在 1→8 线程只有 0.87×。

### 13.2 自旋屏障让阈值下调第一次真正生效

| 阈值 | tps（8 线程，自旋，R3+R4） | s_update |
|---:|---:|---:|
| 262144（默认） | 2394 | 0.134 |
| 16384 | 2868 | 0.060 |
| **1** | **3127** | **0.052** |

**`s_update` 0.134 → 0.052（2.6×）。**

> **重要对照**：在**睡眠**屏障下，把阈值降到 1 是**无收益**的（02 号文档早期已实测）。
> 原因是每次分发约 15 µs 的固定成本吃掉了 128 行那点工作。
> **⇒「阈值该设多少」与「屏障有多贵」是耦合的**：只有把屏障做便宜（自旋），小分发才划算。
> 早期"降阈值无用"的结论**只在睡眠屏障下成立**，不能推广。

### 13.3 附带对照：R4 依然有效（8 线程，自旋，阈值 16384）

| 配置 | tps | m_update |
|---|---:|---:|
| R3 单独 | 2213 | 0.224 |
| **R3 + R4** | **2868** | 0.095 |

`m_update` 0.224 → 0.095（**2.36×**），与 §11 的 +38% 一致且更强。

### 13.4 线程上限：自旋在 SMT 超订时崩溃

阈值=1、自旋模式下的线程扫描：

| 线程 | 4 | 8 | 12 | **16** |
|---|---:|---:|---:|---:|
| tps | 2215 | 2947 | 3030 | **35** |

**16 线程 = 35 tps，灾难性崩溃。**
原因：本机 8 物理核 / 16 逻辑核（SMT），16 个**自旋**线程会互相饿死兄弟核的执行资源，
而睡眠屏障会让出 CPU。**⇒ 自旋模式的实用上限是 8–12 线程，必须显式设限，不能取 `hardware_concurrency`。**

### 13.5 累计成绩

| 阶段 | tps | 相对原始基线 |
|---|---:|---:|
| R0 基线（4 线程） | 932.8 | 1.00× |
| R3+R4（睡眠，4 线程） | 1637 | 1.76× |
| R3+R4 + 自旋（8 线程） | 2394 | 2.57× |
| **R3+R4 + 自旋 + 阈值 1（8–12 线程）** | **3030–3127** | **≈3.3×** |

**到 10 000 还差约 3.2×，到 14 000 还差约 4.5×。**

### 13.6 下一刀：融合分发（设计已定，未实施）

每 token 仍有约 **32 次分发**（每层：s / m / read / norm）。§13.2 证明**只要单次分发便宜，小分发也划算**，
那么反过来——**减少分发次数**是同一杠杆的另一半，且与屏障成本正交。

**融合方案**：一层内的三个 `group<>`（s 分支、m 分支、read）输出行互不重叠、
输入向量的关系也确定，可合成**一次 `run()`**：

- 总行数 = c.s + c.m + c.d = 128 + 512 + 512 = **1152 行**
- 给每行一张静态映射表：行 → (张量, 该张量的行号, 输入向量 s/m/xn)
- 一次屏障覆盖全部三层矩阵乘

**收益估算**：分发次数 32 → 8（每层 1 次），若固定成本占比仍显著，预期 1.3–1.8×。

**风险**：`m` 与 `read` 之间有依赖（`read` 读**更新后**的 `m`），因此一层只能融合到
「s 更新 + m 更新」两次，或把 `read` 留到下一层开头。需先确认依赖图。

### 13.7 仍未做

  这是 02 号 §2.3 带宽判断**唯一仍然成立**的地方（8.39 MB 超出 L2、流式读）
- 层间串行（§11.2）仍未拆解

## 十四、输出头不是带宽受限——否证 §13.7 的推断（2026-09-11 续）

### 14.1 我上一条的错误推断

§13.7 我写道：输出头 8 线程下 0.123 ms、字节率 68.3 GB/s，**"疑似带宽受限"**，并据此建议走「2 位打包减字节」路线。**这个推断是错的。**

### 14.2 否证实验：同一内核只改矩阵大小

`microbench_dot_kernels.exe <rows> 512 <reps>`，列固定 512（与真实 d 一致），只改行数——从远小于 L1 一直到输出头的真实大小：

| 行数 | 体积 | 驻留层级 | AVX2 float | VNNI int8 |
|---:|---:|---|---:|---:|
| 64 | 32 KB | L1 内 | 13.54 G MAC/s | 40.66 G MAC/s |
| 512 | 256 KB | L2 内 | 14.48 | 40.92 |
| 4096 | 2 MB | 超 L2 | 14.42 | 41.05 |
| **16384** | **8.39 MB** | 超 L3 压力 | **14.39** | **39.97** |

**内核速率从 L1 到 8.39 MB 完全平坦（13.5 → 14.4，波动<7%）。**

**⇒ 内核是计算受限，不是带宽受限。** 若真是带宽受限，8.39 MB 那一档必然显著掉速——**没有掉**。

### 14.3 错在哪里（同类错误第二次）

`68.3 GB/s` 只是 `14.4 G MAC/s（单核）× 1 字节/MAC × 4.74（8 线程扩展）` 的**数值巧合**，因为三值权重恰好是 1 字节 = 1 MAC。**我又一次把"数值相等"当成了"因果相等"。**

> 这与 §11.3 记录的错误完全同源：02 号文档的字节恒等式当年也只是**恰好**成立。
> **纪律：任何基于"每字节/每 MAC 比值"的推断，必须用一个只改该项的对照实验证伪一次才能采信。**

### 14.4 修正后的杠杆排序（以实测为准）

|---|---:|---|

### 14.5 对目标的可达性重估

输出头 0.123 ms 占 0.338 ms 的 36%；m_update / read / s_update 也是同类点积。**若全部点积换成 VNNI（2.78×）**：

```
点积部分   ≈ 0.123(head) + 0.089(m) + 0.066(read) + 0.054(s) = 0.332 ms
非点积部分 ≈ 0.007(norm) + 少量 elementwise                   ≈ 0.020 ms
VNNI 后    ≈ 0.332/2.78 + 0.020                              ≈ 0.139 ms
⇒ 约 7 200 t/s
```

**再叠加分发融合（1.3–1.8×）⇒ 约 9 400–13 000 t/s。**
**⇒ 10 000 t/s 可达；14 000 t/s 需融合接近上界或并行扩展进一步改善。**

### 14.6 VNNI 实施的已知障碍

`vpdpbusd` 是 **u8 × s8 → s32**，要求两个操作数都是 int8；而当前激活是 float32。两条路：

| 路线 | 精确性 | 代价 |
|---|---|---|
| **A. 激活量化到 int8** | **近似**——改变数值，checksum 变化 | 需量化 + 反量化标度 |
| **B. 利用三值结构做掩码求和** | **可保持精确** | dot = Σ(w=+1) x − Σ(w=−1) x，用 AVX-512 掩码寄存器；权重可存**位掩码**（每行 128 字节 vs int8 的 512 字节，**再省 4×**） |

**路线 B 更优**：既省指令又省字节，且不引入量化误差。
**但改变累加结构会改变浮点求和顺序 ⇒ checksum 仍可能变化。**
解决方向：保持现有「4 个独立 lane 累加器 + 相同归约顺序」，只把「取权重」从
`cvtepi8_epi32 + cvtdq2ps + mul` 换成 `maskz_mov`，使求和顺序与现在一致。

**下一步**：实现路线 B 的单行 `dot`，用微基准量倍数，并验证 checksum 与现状一致；一致才推入生产路径。

> **订正**：§13.7 末条「输出头……疑似带宽受限」已被本节否证，该条作废。

## 十五、内核路线的实测结论：B 死、A 只有 1.54×（2026-09-11 续）

### 15.1 路线 B（三值掩码求和）：逐位精确，但更慢

设计：`dot = Σ(w=+1) x − Σ(w=−1) x`，权重存两个位图（每行 128 字节 vs int8 的 512 字节，省 4×）。

- **逐位相等检查：0 / 16384 行不同** ⇒ 精确性设计成立（先算 `x*scale` 再掩码加减，
  因 `(±scale)*x == ±(scale*x)`，且 lane 累加顺序与参考一致）。

- **但速度只有 0.50×**（7.32 vs 14.59 G MAC/s）。原因：AVX-512 掩码加减在 Zen4 上是多 µop，
  且每 8 个权重需要一次位图字节载入，开销超过收益。

**⇒ 路线 B 判死。** 省下的字节无用（内核本就非带宽受限），省下的乘法被掩码开销吃掉。

### 15.2 路线 A（int8 量化激活 + VNNI 零点修正）：1.54× 且引入误差

6 次独立运行（每次内部两内核背靠背），G MAC/s：

| 内核 | 6 次采样 | 中位 | 相对 |
|---|---|---:|---:|
| 参考 AVX2 float | 14.4 14.2 14.9 14.0 14.9 14.6 | 14.59 | 1.00× |
| 路线 B 掩码 | 7.1 7.2 7.3 7.3 7.3 7.4 | 7.32 | **0.50×** |
| **路线 A VNNI int8** | 22.8 22.5 22.3 19.8 22.2 25.1 | **22.52** | **1.54×** |

**数值误差**（对 16384 行逐行比对参考内核）：中位 **3.884e-03**，90 分位 **2.395e-02**。
这是 int8 激活量化的固有噪声，是**真实的质量代价**，不是纯提速。

### 15.3 订正 §14.4：VNNI 不是 2.78×

§14.4 我写了「VNNI 2.78×（14.4 → 40 G MAC/s）」。**那个 40 G MAC/s 来自单次运行，是伪值。**
交错重复 6 次后稳定在 **22.52 G MAC/s = 1.54×**。

> **同类错误第三次**：单次采样 → 采信比值。已固化纪律：**任何倍数必须来自同一二进制内交错重复、取中位数**。

### 15.4 修正后的杠杆排序与可达性（诚实版）

| 杠杆 | 实测/预估 | 状态 |
|---|---:|---|
| **并行扩展**（当前 8 线程仅 2.5×，串行占比 31%） | 潜力最大，未攻 | **新第一优先** |
| 分发融合（32 → 8 次/token） | 预估 1.2–1.3× | 设计已定 |
| VNNI int8 内核 | **1.54×** 且有 0.4% 量化误差 | 已测，需质量评估 |
| ~~路线 B 掩码~~ | **0.50×** | **已否证** |
| ~~2 位打包减字节~~ | **0×** | **已否证** |

Amdahl 反推（8 线程 2.5×）：`2.5 = 1/(f+(1-f)/8)` ⇒ **f ≈ 0.31**，即 31% 是串行的。

**乐观连乘**：`3040 × 1.3（融合）× 1.54（VNNI）≈ 6 100 t/s`。

**⇒ 以目前已识别的杠杆，10 000 t/s 达不到。** 缺口约 1.6×，只能来自**把 31% 的串行占比压下去**，
即并行扩展本身——这与"融合分发"是同一件事的两面。

### 15.5 下一步（唯一有希望的方向）

**把串行占比从 31% 压下来。** 需要先**测出那 31% 具体是什么**，方法：
1. 逐层累加计时：把一层拆成「分发前 / 分发中 / 分发后」三段，量三段之和与总时间的差；
2. 用 `TAO_LAYER_LIMIT` 做层数外推：若 `T(N) = a + b·N`，则截距 `a` 就是层外串行部分；
3. 若串行主要是「32 次分发 × 每次固定开销」，则融合分发直接见效且与 VNNI 正交。

**在量出 31% 的构成之前，不再实现新内核。**

## 十六、层内并行效率约 0%：31% 串行占比的构成（2026-09-11 续）

### 16.1 层数外推（当前最佳配置：R3+R4 + 自旋 + 阈值1，8 线程）

| 层数 N | 中位 tps | ms/token |
|---:|---:|---:|
| 2 | 5271 | 0.1897 |
| 4 | 4480 | 0.2232 |
| 6 | 2913 | 0.3433 |
| 8 | 2719 | 0.3678 |

线性拟合 **`T(N) = 0.1174 + 0.0327·N`**（毫秒/token）：

- 层外固定部分 `a = 0.1174`（**31%**）
- 每层成本 `b = 0.0327`（合计 69%）

**与 §15.4 用 Amdahl 从 2.5× 线程扩展反推出的 f ≈ 0.31 完全吻合** ⇒ 两个独立方法互证。

### 16.2 关键发现：层计算在 8 线程下与单线程一样慢

R4 之后一个 **Reuse 层**只有 `s` 分支 163,840 + `read` 327,680 = **491,520 MAC**。
按单线程内核速率 14.59 G MAC/s，它**单线程**就该用 `0.4915/14.59 = 0.0337 ms`。

**实测每层 0.0327 ms —— 与单线程成本相同。** ⇒ **层的并行效率约 0%。**

每层约 2 次分发 ⇒ **每次分发约 14 µs 的固定开销**。
这说明**自旋屏障并没有把单次分发开销压下来**；§13 的收益来自「阈值下调让 `s_update` 得以并行」，不是屏障变便宜。

### 16.3 对目标的诚实结论

| 项 | 值 |
|---|---|
| 当前 | 2719–3127 tps（8–12 线程） |
| 层外（head） | 0.1174 ms，占 31%，1/0.1174 = **8 515 tps 的天花板** |
| 每层 | 0.0327 ms，**并行效率 0%**，其中约 28 µs 是 2 次分发的开销 |
| 若每层融合成 1 次分发 | 省约 112 µs/token ⇒ 0.256 ms ⇒ **约 3 900 tps** |
| 再叠加 VNNI 1.54× | ⇒ **约 6 000 tps** |

**⇒ 10 000 t/s 以目前已识别的杠杆仍达不到，缺口约 1.7×。**

### 16.4 唯一可能有数量级收益的方向

**不是融合，而是消除分发本身。** 每 token 约 32 次分发 × 14 µs ≈ **448 µs**，
而已知总时间只有 368 µs —— 说明分发开销与计算**部分重叠**，但仍是主导项。
融合（32→8）只减少次数，**每次 14 µs 的固定成本仍在**，最多拿回约 1.4×。

**真正要回答的问题**：为什么一次 spin 屏障要 14 µs？（spin 屏障理论上应是亚微秒级）
候选原因，下一步按序排查：
1. **`callers_` 互斥锁**：每次 `run()` 都取 `std::lock_guard<std::mutex>`，无竞争时约 20 ns，
   但若与工作线程的自旋形成缓存行乒乓（`callers_`/`mutex_` 与 `spin_*` 同处一条 cache line），代价会放大数个数量级；
2. **伪共享**：`slots_` 中相邻 `Slot`（各 24 字节）被多个 worker 写 `error` 字段，
   加上 `spin_done_` 的 `fetch_add`，都是同一 cache line 上的高频写；
3. **worker 未被真正并行调度**（亲和性/超订）。

**下一步只做一件事**：用「串行回退 vs 并行」的对照，量出**一次 `run()` 调用的纯开销**
（例如把阈值设为极大值强制串行，与阈值=1 对比，差值除以分发次数）。**在量出这个数之前不再改内核。**


### 16.5 已排查的一个串行来源（不足以解释 31%）

`group<N>`（`greedy_pipeline_grouped_model.hpp:97,106`）对每个输出做 `out[i].resize(rows)`——
堆分配 + **零初始化**，全部发生在**调用线程**上、在分发之前，因此是纯串行工作。

每层：s 分支 4×128 + m 分支 6×512 + read 2×512 = 4 608 float = **18.4 KB**；
每 token × 8 层 = **147 KB** 的 alloc + zero + free。

按常见分配+清零速率（约 10 GB/s）估算约 **15 µs/token**，占总时间 368 µs 的 **4%**。
**⇒ 是真实开销，但不足以解释 31% 的串行占比。** 该线索保留，不作为主攻方向。

### 16.6 本轮小结与下一步

**已完成（全部为实测）：**
- 路线 B（三值掩码）：逐位精确但 **0.50×**，判死
- 路线 A（VNNI int8）：**1.54×**（非此前误报的 2.78×），且中位量化误差 3.9e-3
- 层数外推：`T(N) = 0.1174 + 0.0327·N`，层外 31%，与 Amdahl 反推互证
- 层内并行效率 ≈ 0%；已排除"分配开销"为主要原因

**结论：10 000 t/s 以已识别杠杆达不到（乐观连乘约 6 000），缺口约 1.7×。**

**下一步（唯一有希望）：** 直接量出**一次 `dispatch_rows` 调用的纯开销**。
做法：在同一进程内对同一形状做「串行回退（阈值=极大）」与「并行（阈值=1）」的**交错重复**对比，
差值 ÷ 分发次数 = 单次开销。若该值确为微秒级，则瓶颈是**同步机制本身**，
需转向「每线程固定行区间 + 无每分发屏障」的持久化分区设计（而非融合）。
若该值很小，则层时间是**被非点积工作**（norm/状态更新/分配/访存模式）主导，方向完全不同。

**在量出这个数之前不再改动内核或分发。**

## 十七、订正 §16：屏障不是瓶颈，且串行占比无法用 s+p/n 模型分解（2026-09-11 续）

### 17.1 多线程层数外推（当前最佳配置：R3+R4 + 自旋 + 阈值1）

| 线程 n | 每层成本 b(n) | 层外(输出头) a(n) |
|---:|---:|---:|
| **1**（`n<=1` 时 `run()` 直接串行回退，**零分发**） | 0.0639 ms | 0.3671 ms |
| 2 | 0.0558 | 0.3745 |
| 4 | 0.0291 | 0.2246 |
| 8 | **0.0265** | **0.1403** |

**8 线程实际扩展：层 2.41×，输出头 2.62×。**

### 17.2 订正：自旋屏障的代价只有约 1 µs/次

用 n=2,4,8 三点拟合 `b(n) = s + p/n`：
- 层内串行 s = 0.0132 ms，层内可并行 p = 0.0820 ms
- **8 线程下每层残差（屏障开销）= 0.0031 ms，占 b(8) 的 12%**
- 每层约 3 次分发 ⇒ **单次约 1.03 µs**

**⇒ §16.2 的「每次分发约 14 µs、层内并行效率 0%、70% 是开销」全部作废。**
那个 14 µs 来自「实测每层 0.0327 ms ≈ 单线程内核理论值 0.0337 ms」这一**巧合比较**，
既没有做对照实验，也忽略了层内的非点积工作。**同类错误第四次。**

### 17.3 但 s+p/n 模型本身不成立——三种算法答案互相矛盾

| 分解方法 | 层内串行占比 |
|---|---:|
| 两点（n=1,8） | 33% |
| 三点拟合（n=2,4,8） | 14%，且预测 b(1)=0.0953 vs 实测 0.0639 |
| 含屏障修正 | 49% |

**矛盾说明 `b(n) = s + p/n` 这个模型对当前数据不成立。** 最可能的原因是
**单线程睿频远高于全核**：n=1 时单核可跑到 ~5 GHz，n=8 时全核只有 ~3.5–4 GHz，
这个 25–40% 的频率差被错误地吸收进了「串行部分」。

**⇒ 在无法控制频率的前提下，用线程数拟合来分离「串行 vs 并行」是不可靠的。**
该结论本身是本轮的重要产出：**不要再走这条路。**

### 17.4 仍然成立的事实（模型无关）

- 层 8 线程扩展 **2.41×**，输出头 **2.62×**，都远低于 8×
- 自旋屏障单次约 **1 µs**，只占 b(8) 的 12% ⇒ **不是主要瓶颈**
- 线程 2 时层成本 0.0558 几乎没比 1 线程的 0.0639 好（1.14×）——**2 线程扩展极差**
  这与频率无关（2 线程通常仍在睿频范围内），是**真实的并行实现问题**，值得单独查

### 17.5 新发现的确定性串行开销：字符串 map 查找

`packed` 与 `w` 都是 `std::map<std::string,...>`，而 `group<N>` / `norm` / `linear` 每次都要
`packed.at(p+name)`、`w.at(p+name)`。每 token 的查找次数（静态计数）：

| 层类型 | 查找次数 | 层数 | 小计 |
|---|---:|---:|---:|
| Full 层（含 `group<6>`） | ~17 | 2 | 34 |
| Reuse 层（R4 后无 `group<6>`） | ~11 | 6 | 66 |
| **合计** | | | **约 100 次/token** |

键名如 `"layer.0.m.candidate.x"`（21 字符）**超出 SSO 上限 ⇒ 每次都要堆分配 + 释放**，
再叠加 `std::map` 的红黑树遍历。按 100–200 ns/次估算约 **10–20 µs/token**（占 3–6%）。
**这是纯串行、纯机械、可安全消除的开销**：在构造时把名字解析成索引，热路径只做数组下标。

### 17.6 下一步（按性价比排序）

1. **消除字符串 map 查找**（纯机械改动，零数值风险，可立刻验证 checksum 不变）：
   把 `packed`/`w` 的键改为构造时预解析的整数索引。预期 3–6%，且**顺带减少分配**。
2. **查清 2 线程扩展极差（1.14×）的原因**——这是频率无关的真实缺陷，
   可能同样影响 4/8 线程。用一个只在一层内、工作量固定的微基准隔离测量。
3. **不再用线程数拟合分离串行/并行**（§17.3）。


### 17.7 字符串 map 查找：实测 2.1%，不值得重构

`src/microbench_string_map.cpp` / `build/microbench_string_map.exe`：键名与真实模型一致，
184 条目，每 token 100 次「前缀拼接 + `map.find`」，对照「整数索引」：

| 方案 | 3 次测量 |
|---|---|
| 拼接 + `map.find` | 7.724 / 7.212 / 7.161 µs/token |
| 整数索引 | 0.065 / 0.066 / 0.065 µs/token |
| **差值** | **约 7.1–7.7 µs/token = 2.1%** |

**⇒ 真实但太小。§17.5 估的 3–6% 方向对、幅度偏大。不值得为此做全量重构。**
（该线索关闭；若将来做别的大改时顺手改掉即可。）

### 17.8 本轮小结

**已订正（重要）：**
- ✅ §16 的「每次分发 14 µs、层内并行效率 0%、70% 是开销」**全部作废**；
  自旋屏障实测约 **1 µs/次**，只占每层 12% ⇒ **屏障不是瓶颈**
- ✅ 字符串 map 查找实测 **2.1%** ⇒ 关闭该线索

**本轮确立的模型无关事实：**
- 层 8 线程扩展 **2.41×**，输出头 **2.62×**，均远低于 8×
- **2 线程扩展仅 1.14×**（b(1)=0.0639 → b(2)=0.0558）——2 线程通常仍在睿频范围内，
  故这**不是频率伪影，是真实的并行实现缺陷**，是当前最有价值的线索
- `b(n) = s + p/n` 模型不成立（三种分解给出 33% / 14% / 49% 串行占比）⇒
  **用线程数拟合分离串行/并行不可靠**（频率是混淆变量）

### 17.9 下一步（明确、可执行）

**固定线程数、只变工作量**，避开频率混淆变量：

在 **n=2 固定**不变的前提下，用 `TAO_LAYER_LIMIT` 外推 `T(N) = A + B·N`：
- `B` = 每层成本（此时频率不变，可比）
- `A` = 层外固定成本

再用同一方法在 **n=1 固定**下测一次（n=1 无频率与并行混淆，是干净的基线），
比较 `B(n=1)` 与 `B(n=2)`：二者之比就是**真实的 2 线程扩展**，不含频率伪影。
若确为 ~2×，则问题只在 4/8 线程；若仍为 ~1.14×，则**分发实现本身有缺陷**，
应转向「每线程固定行区间 + 无每分发屏障」的持久化分区设计。

## 十八、频率不是瓶颈：全核惩罚仅 1.35×（2026-09-11 续）

### 18.1 实验设计（模型无关，无需改代码）

同一个**单线程**工作负载，分别在「机器空闲」与「全核满载（14 个忙等进程占满 16 逻辑核）」下测量。
两者之比即为**全核频率惩罚**——这直接隔离了睿频效应，不含任何并行算法因素。

| 场景 | 3 次采样 (tps) | 中位 |
|---|---|---:|
| 空闲 n=1 | 1285 1232 1139 | **1232** |
| 满载 n=1 | 885 956 915 | **915** |
| **频率惩罚** | | **1232/915 = 1.346×** |

**⇒ 全核满载时单核吞吐降到 74.3%。**

### 18.2 关键推论：并行扩展的损失主要不是频率

频率归一化后的真实 8 线程扩展：

```
原始       = 2858 / 1232 = 2.32×
频率归一化 = 2.32 × 1.346 = 3.12×
```

**⇒ 即使完全扣除频率因素，8 线程也只有约 3.1×，远低于 8×。
瓶颈是真实的并行实现缺陷，不是睿频。**

这同时**保住了 §17.4 的 2 线程异常**：2 线程时只有 2 个核在工作，频率几乎不受影响，
所以 `b(1)=0.0639 → b(2)=0.0558`（1.14×）**不含频率伪影，是真实的实现缺陷**。

> 注：本轮也在满载条件下测了 n=8，但 8 个模型线程 + 14 个忙等进程严重超订，
> 该数据无效，已弃用。**教训：频率对照实验必须保证被测负载自身的线程数不变。**

### 18.3 下一轮的攻击点（已收敛到单一问题）

**问题陈述**：`run()` 把行分成 2 块（caller 拿 [0,rows/2)，worker 拿 [rows/2,rows)），
屏障开销实测仅约 1 µs，却只换来 1.14×。**每层约有 0.008 ms 无法用「串行工作 + 屏障」解释。**

候选原因，按怀疑程度：
1. **`group<N>` 的分块是按「跨张量总元素数」切的**（`dispatch_rows(offsets[N],1,...)`），
   再由 `first = lo/cols + (lo%cols!=0)` 反推行号。若两块的**实际工作量分布不均**，
   快的那个线程只能空转等待。这是最可疑的一点，且可静态检查。
2. **caller 侧的准备/收尾**（`out[i].resize`、offsets 计算、`packed.at` 查找）全在分发之前，
   属纯串行；2 线程时它是总时间的显著部分，8 线程时占比更高（阿姆达尔）。
3. **worker 与 caller 落在 SMT 兄弟核上**（未做亲和性绑定），自旋会偷兄弟核的执行资源。

**下一步**：先做 (1) 的静态检查——把 `group<N>` 的实际分块边界算出来，
看 2 块/8 块时的元素数是否均衡。若明显不均，改为**按行数而非总元素数分块**即可，
这是个小而安全的改动。


### 18.4 静态检查：`group<N>` 的分块其实是均衡的（假设 1 被推翻）

`group<N>` 用 `dispatch_rows(offsets[N],1,...)`，即按**跨张量总元素数**切成 n 块，
再由 `first = lo/cols + (lo%cols!=0)` 反推行号。担心的是「元素数均分 ≠ 工作量均分」。
**但每个元素恰好就是一次 MAC**（点积长度 = cols，元素数 = rows×cols），所以按元素数切分
**天然就是按工作量切分**。逐一验算 n=2 的实际边界：

| 调用 | 总元素 | n=2 的两块 | 各块 MAC |
|---|---:|---|---:|
| `group<6>`（Full 层） | 1,179,648 | [0,589824) = candidate.x+s+m；[589824,…) = gate.x+s+m | 589,824 / 589,824 ✓ |
| `group<4>`（s 分支） | 163,840 | candidate.x+s；gate.x+s | 81,920 / 81,920 ✓ |
| `group<2>`（read） | 327,680 | read.s + read.m 前 192 行；read.m 后 320 行 | 163,840 / 163,840 ✓ |

**⇒ 三处都均衡。§18.3 的候选原因 (1) 排除。**

### 18.5 但 2 线程那个"异常"可能本身是噪声

§17 的每层成本序列：

| n | 1 | 2 | 4 | 8 |
|---|---:|---:|---:|---:|
| b(n) ms | 0.0639 | 0.0558 | 0.0291 | 0.0265 |
| 相邻改善 | — | 1.14× | 1.92× | 1.10× |

**b(1)→b(2) 只差 13%，而本次会话反复观测到的运行间噪声就有 ±20%**（§10 的 R0 采样 874–1204，§15 的 VNNI 19.8–25.1）。
因此 **「2 线程异常」在用作结论之前必须重新验证**——用同一二进制内 n=1 与 n=2 的**交错**重复，
而不是各自独立跑一批。

**本轮不再据此下结论。** 若重测后 n=1 与 n=2 的差仍在噪声内，则真实情况是
「并行扩展从 n=2 起就基本失效」，问题更集中、更值得攻。

### 18.6 本轮小结

**已确证（本轮净产出）：**
- ✅ **全核频率惩罚 = 1.346×**（空闲 1232 tps vs 满载 915 tps，模型无关的对照实验）
- ✅ 频率归一化后的 8 线程扩展仍只有 **约 3.1×** ⇒ **瓶颈是真实的并行实现缺陷，不是睿频**
- ✅ `group<N>` 的分块**按工作量是均衡的**（每个元素 = 一次 MAC）⇒ 排除分块不均

**待验证（不得直接采信）：**
- ⚠️ 「2 线程只有 1.14×」——差值 13% 在观测噪声（±20%）以内，需交错重测
- ⚠️ `s + p/n` 模型在 n=2 与 n=8 数据间自相矛盾（由 2 线程点推出 s=0.0477 > b(8)=0.0265），
  这本身就说明**至少有一个线程点是噪声**

### 18.7 下一步（收敛到测量方法本身）

**当前最大的障碍不是找不到优化，而是测量噪声 ±20% 淹没了 10–15% 的效应。**
在噪声降下来之前，任何 1.1–1.2× 的改动都无法被可信地验证——
这正是本轮和上一轮反复出现「结论被推翻」的根因。

**因此下一步先做测量基建，不做优化：**
1. 把 `benchmark_noffn_s3` 的 FORCED 轮次从 5 提到 ≥15，并**在同一进程内交错**不同配置，
   而不是靠多次独立进程；
2. 报告**中位数 + 四分位距**，而不是只报中位数；
3. 只有在某改动的效应 > 2×IQR 时才认定为真实。

## 十九、重大方法论错误：`n<=2` 根本不是 1 线程（2026-09-11 续）

### 19.1 发现

`greedy_pipeline_grouped_model.hpp:264`：

```cpp
void set_cpu_threads(unsigned n)const{
    if(n<=2u){pool.set_threads(1u);use_legacy=true;}
    else{pool.set_threads(n);use_legacy=false;}
}
```

而 `cpu_row_parallel_executor.hpp:10` 写明：**"Exactly two participating threads:
caller plus one persistent sleeping worker"**，第 52 行 `split=rows/2`。

**⇒ `set_cpu_threads(1)` 与 `set_cpu_threads(2)` 是同一个配置：2 线程 + 条件变量睡眠屏障。**

### 19.2 三个后果

1. **§17 所谓「1 线程、零分发、干净的串行基线」完全不存在** —— 那一列其实是 2 线程 legacy。
2. **「2 线程只有 1.14×」的异常是假的** —— 它在比较两个**完全相同的配置**，
   13% 的差就是运行间噪声。**§18.5 的怀疑得到证实。**
3. **`n<=2` 的数据点根本没用自旋屏障** —— §17 中把 b(1) 当作「无屏障基线」去反推屏障开销，
   这个推理链整体作废。

### 19.3 修正后的真实线程扩展（层外=输出头）

| 实际线程 n | 层 b(n) ms | 头 a(n) ms | 所用屏障 |
|---:|---:|---:|---|
| 2（`n<=2` 合并） | 0.060（0.0639 / 0.0558 两点，即噪声） | 0.371（0.3671 / 0.3745） | 睡眠 legacy |
| 4 | 0.0291 | 0.2246 | 自旋 |
| 8 | **0.0265** | **0.1403** | 自旋 |

| 区段 | 层扩展 | 头扩展 |
|---|---:|---:|
| 2→4 | **2.06×** | 1.65× |
| 4→8 | **1.10×** | **1.60×** |
| 2→8 | 2.26× | 2.64× |

### 19.4 由此得到的新结论（比之前更具体）

**层部分在 4 线程就饱和（4→8 只有 1.10×），而输出头一直扩展到 8 线程（4→8 仍有 1.60×）。**

两者结构上的差别很明确：
- **输出头**：每 token **一次**大分发（16384 行），行数多、块大、无层内串行段
- **层**：每层约 3 次**小**分发（`group<4>` 163,840 元素、`group<2>` 327,680 元素）
  + 若干**层内串行段**（RMS norm、`m`/`s` 状态更新、`add`、18.4 KB 分配与清零），× 8 层

**⇒ 层的 4 线程饱和指向「小块分发 + 层内串行段」，而不是屏障本身。**
这也说明 §16「分发融合」的方向**原则上是对的**（把 3 次小分发合成 1 次大分发，
向输出头那种形态靠拢），但此前给出的量化依据是错的，需要重新估算。

3. **更小的 m**：m=512 贡献 m 分支 1,179,648/层，是层内最大项。

### 22.2 逐相位线程扩展（1 → 8 线程，同一二进制）

### 22.3 串行段的定位：状态更新的超越函数（已实测，非推测）

`greedy_pipeline_grouped_model.hpp:170`：
```cpp
for(size_t j=0;j<m.size();++j) m[j]+=sigmoid(g[j])*(std::tanh(v[j])-m[j]);
```
**标量循环、每元素一个 `sigmoid` 加一个 `std::tanh`、完全串行。** 每 token 8 层 × 512 = 4096 次。

`src/microbench_state_update.cpp` 实测（3 次）：

| 项目 | µs/token |
|---|---:|
| 现状（sigmoid + tanh） | 41.47 / 41.08 / 42.22 |
| 仅 tanh | 29.04 / 28.46 / 29.29 |
| 无超越函数 | 8.64 / 8.69 / 8.57 |
| **超越函数开销** | **32.83 / 32.39 / 33.65** |

**⇒ 约 33 µs/token，占 369 µs 的 8.7%。**
这解释了 m 相位串行量（0.2630−0.0992×… 反推 ≈ 0.047 ms）中的绝大部分，**与相位数据吻合**。

**但它是真实但不足以单独构成 21% 串行**：s 相位的串行段另有约 0.027 ms（128 元素/层的 s 更新）。
合计串行 ≈ 0.068（状态更新）+ 0.009（norm）= **0.077 ms = 20.9%**。

> **订正**：我一度假设状态更新占 22%、是主因，实测只占 8.7%（m）+ s 的部分。
> **又一次「先量再做」避免了错误归因。**

### 22.4 决定性计算：为什么 10 000 t/s 在本机不可达

把实测数字拼起来：

```
8 线程单 token = 0.3692 ms
  其中串行        = 0.077 ms  (20.9%)   ← 状态更新 + norm，逐步元素相关，改不了
  其中点积        = 0.292 ms  (79.1%)   ← 14,680,064 MAC，实测 50.3 G MAC/s
```

**点积的绝对上限**：8 线程内核峰值 8 × 14.59 = 116.7 G MAC/s，
除以频率惩罚 1.346 ⇒ **86.7 G MAC/s**（AVX2）；VNNI 再 ×1.54 ⇒ **133.5 G MAC/s**。

| 情景 | 点积时间 | + 串行 | 总时间 | 吞吐 |
|---|---:|---:|---:|---:|
| 当前实测 | 0.292 | 0.077 | 0.369 | **2 765**（吻合） |
| 层效率提到输出头水平（62 G MAC/s） | 0.237 | 0.077 | 0.314 | 3 187 |
| 上述 + VNNI 1.54× | 0.154 | 0.077 | 0.231 | **4 333** |
| 理论极限：点积 0 成本 | 0 | 0.077 | 0.077 | 13 000 |

**⇒ 现实可达上界约 4 300 tps。10 000 需要总时间 ≤ 0.100 ms。**
即使串行部分一分不花，点积也要 ≤ 0.023 ms ⇒ **638 G MAC/s**，
是频率修正后 8 线程内核峰值（86.7 G）的 **7.4 倍**。**物理上不可能。**

### 22.5 唯一可能的出路：把 MAC 数砍掉 6 倍以上

设内核效率理想化到 98 G MAC/s（VNNI + 95% 效率），要总时间 ≤ 0.100 ms：

```
0.077（串行，不可压）+ MAC / 98e9 ≤ 0.100
⇒ MAC ≤ 2.25 M
```

**当前 14,680,064 MAC，需要砍到约 2.25 M —— 减少 6.5 倍。**

分项看：

| 项 | 当前 MAC | 占比 | 需要砍到 |
|---|---:|---:|---:|
| 输出头（16384×512） | 8,388,608 | 57.1% | ~1.0 M |
| 8 层（R3+R4） | 6,291,456 | 42.9% | ~1.2 M |

**这不是「优化」，是「换模型」。** 例如：
- 输出头低秩分解（16384×512 → 16384×64 + 64×512）可省约 4.4×，但**改变数值，必须重训**
- 真正意义上的单层（层 1–7 不工作）才够，但那不是层维复用

### 22.6 本轮的结论（负面的，但是决定性的）

**在本机（Ryzen 9 7940H，8 物理核）上，以当前模型规模（14.68 M MAC/token），
10 000 t/s 物理上不可达；现实可达上界约 4 300 tps。**

这不是「还没找到优化」，而是：**串行部分 0.077 ms 已经锁死了 13 000 tps 的绝对天花板，
而任何现实的点积成本都会把它压到 4 300 以下。**

**要达成目标，必须改变模型本身**（缩小输出头 / 大幅减少层 MAC），
而这需要重训 + 质量评估 —— 属于架构升级，不属于本轮能完成的范围。

### 22.7 建议的下一步（需用户确认方向）

三个可选方向，代价与风险递增：
1. **保持模型不变，接受 ~4 300 tps 的现实上限**，把 VNNI 与层效率做完（预期 4 000–4 400）
2. **输出头低秩/瘦身 + 重训**：vocab 投影从 512 维降到 64–128 维，
   可把总 MAC 降到约 7–9 M，配合 VNNI 预期 **6 000–7 500 tps**
3. **大幅缩小模型 + 重训**：同时砍头和层，才可能触及 10 000，但这是换一个模型

**⇒ 方向 2 是性价比最高的一步，但它需要训练资源，且有质量风险。**

## 二十三、廉价激活：+20.5%（用户提议，实测确认）（2026-09-11 续）

### 23.1 动机

§22 定位出**串行段才是最难突破的约束**（把绝对天花板锁在 13 000 tps），
其中主体是 `greedy_pipeline_grouped_model.hpp:148,170` 的状态更新：
```cpp
s[j]+=sigmoid(a[j])*(std::tanh(u[j])-s[j]);   // 128 元素/层
m[j]+=sigmoid(g[j])*(std::tanh(v[j])-m[j]);   // 512 元素/层
```
**标量循环、每元素一次 `std::exp` + 一次 `std::tanh`、完全串行。每 token 5120 次。**
**用户提议把 sigmoid 与 tanh 一起换成更现代的廉价激活** —— 这个方向攻击的是「串行」而非「MAC 数」，
是本会话最有价值的一条建议。

### 23.2 候选实测（`src/microbench_activation2.cpp`）

每 token 5120 次 sigmoid + 5120 次 tanh，单位 µs/token：

| 候选 | 速度 | 加速 | tanh 最大误差 | sigmoid 最大误差 |
|---|---:|---:|---:|---:|
| **现状 `std::exp` + `std::tanh`** | **53.51** | 1.00× | — | — |
| `x/(1+\|x\|)` 标量 | 10.09 | 5.69× | 0.306 ✗ | 0.082 |
| hard 标量 | 9.67 | 5.53× | 0.238 ✗ | 0.119 |
| Padé3 标量 | 11.11 | 4.82× | **0.0235** | 0.159 |
| Padé7 标量 | 22.36 | 2.39× | 0.0001 | 0.150 |
| rsqrt AVX2 | 1.31 | 40.9× | 0.0739 | 0.124 |
| **Padé3 AVX2（选用）** | **1.08** | **49.5×** | **0.0235** | 0.159 |
| hard AVX2 | 0.50 | 107.7× | 0.238 ✗ | 0.119 |

**选用三阶 Padé**：`tanh(x) ≈ x(27+x²)/(27+9x²)`（|x|>3 夹紧），`sigmoid(x)=0.5(1+tanh(x))`。
选择依据是 **tanh 精度最好（0.0235）且 AVX2 后仍有 49.5×**。
sigmoid 的 0.159 误差集中在过渡区，而**门控本就设计为饱和**，对重训后的模型可接受。

## 二十四、修复自旋屏障的生产级竞态：8 线程 60% 崩溃 → 0%（2026-09-11 续）

### 24.1 发现

在验证 §23 的改动时，`benchmark_noffn_s3` 在**自旋 + 8 线程**下开始间歇性崩溃（exit=3221225477 = `0xC0000005` 访问违例）。
最小化定位（同一二进制内重复）：

| 条件 | 结果 |
|---|---|
| 自旋 8 线程 | **3/5 崩溃**，2/5 成功（checksum 259） |
| 睡眠 8 线程 | **2/2 稳定** ✓ |
| 自旋 4 线程 | 1/1 稳定 ✓ |

**⇒ 与 `fast_act` 改动无关，是自旋屏障自身的竞态，且只在高线程数暴露。**

### 24.2 根因

`cpu_row_parallel_pool.hpp` worker 循环：
```cpp
for (;;) {
    for (;;) {
        if (spin_stop_.load(relaxed)) return;
        g = spin_gen_.load(acquire);
        if (g != seen) break;        // ← 跳出内层
        pause();
    }
    seen = g;
    ...读 slots_ / invoke_ / context_ 并执行任务...   // ← 此处没有再次检查 stop
}
```
而 `stop_workers()` 当时**同时**设置 stop 标志**并递增 generation**。竞态窗口：

1. worker 读到 `spin_stop_ == false`（通过检查）
2. worker 在读 generation **之前**被 OS 抢占
3. 调用方：`spin_stop_ = true`；`spin_gen_.fetch_add(1)`
4. worker 恢复，读到**新的** generation ≠ `seen` ⇒ `break`
5. worker **执行了一个伪任务**，而 `slots_` 已被 `slots_.clear()` 清空 ⇒ **访问违例**

原注释声称「stop 在 generation 之前检查，故不会执行伪任务」——**只在 stop 已对 worker 可见时成立**，
恰恰漏掉了上面第 1→2 步的窗口。

### 24.3 修复（两处）

1. **`stop_workers()` 不再递增 generation**。worker 的内层轮询本就会读到 stop 标志，
   `join()` 足以收敛。递增 generation 正是让 worker「看到新代号却已处于 stop 状态」的原因。
2. **跳出内层后增加防御性再检查** `if (spin_stop_.load(acquire)) return;`。

### 24.4 验证

| | 修复前 | 修复后 |
|---|---|---|
| 自旋 8 线程连跑 8 次 | 2/5 成功 | **8/8 成功，checksum 全部 259** ✓ |

**⇒ 生产配置从「60% 概率崩溃」变为稳定可用。**

> **这条比任何性能改动都重要**：此前所有基于 8 线程自旋的测量，
> 都是在「约 60% 概率崩溃」的构建上取得的。数字本身可复现（见 §24.5），
> 但**没有人会部署一个会崩溃的配置**。

## 二十五、预展开 float 权重：逐位精确，但慢 2.6 倍（2026-09-11 续）

### 25.1 动机（看似最有希望的一刀）

现有 `PipelineRows::dot`（`cpu_pipeline_rows.hpp`）每 16 个权重约 **14 条指令**：
2 加载 + 2 符号扩展(cvtepi8_epi32) + 2 转浮点(cvtdq2ps) + 2 乘 α + 2 加载 x + 2 乘 + 2 加
= **1.14 MAC/指令**。其中 int8→float 转换纯属开销。

而 `q[j]*scale[row]` 是**每行常量**，可在装载时预计算成 float32。循环内只剩 mul+add。

**关键：这样做是逐位精确的**，前提有两条，缺一不可：
1. `wf = float(q)*scale` 与内核内联算的 `(float(q)*scale)` 是同一个 float32 值；
2. **必须用 mul+add，不能用 FMA** —— FMA 不 round 中间乘积，会改变结果。

### 25.2 微基准结果（看似成立）

`src/microbench_floatweights.cpp`，逐位相等检查 **0 / 16384 行不同 ✓**，速度：

| 行数 | float 字节 | 现有 int8 | float 单行 | **float 4 行** |
|---:|---:|---:|---:|---:|
| 128 | 0.26 MB | 10.65 | 11.68 | **29.65 (2.78×)** |
| 512 | 1.05 MB | 11.06 | 13.68 | **25.47 (2.30×)** |
| 1024 | 2.10 MB | 12.11 | 12.30 | 20.82 (1.72×) |
| 2048 | 4.19 MB | 13.26 | 11.00 | 9.72 (0.73×) |
| 16384 | 33.55 MB | 13.13 | 4.36 | 2.74 (0.21×) |

**注意：float 单行几乎无收益（约 1.0×），只有 4 行同做才有 2.3×** ——
因为收益全在被摊薄的 x 加载上。交叉点约 1.7–2 MB。

据此判断：层内矩阵 ≤ 0.65 MB（s 分支）、1.31 MB（read）应获益，输出头 33.5 MB 必排除。

### 25.3 端到端结果：**0.39×，慢 2.6 倍**

| 配置 | 中位 tps | IQR | 最终 token |
|---|---:|---:|---:|
| R3+R4 t8 | 2 704.1 | 66.6 | 259 |
| **R3+R4 t8 + fast_act** | **3 225.5** | 45.9 | 259 |
| R3+R4 t8 + floatw | **1 053.0** | 26.3 | **259** |
| R3+R4 t8 + act + floatw | 1 126.0 | 7.7 | 259 |

**逐位精确性成立**（floatw 的 token 同样是 259，与推导一致 ✓），
**但吞吐从 2 704 掉到 1 053 = 0.39×。**

### 25.4 错在哪里（第 6 次同类错误，且是新的子类）

**我的微基准不模拟真实访问模式。** 它用 `reps=60` 反复跑**同一个矩阵**——
第一次之后数据全部驻留缓存，测的是「缓存内重复访问」。
**而真实模型每 token 只把每个矩阵扫一遍，纯流式、永不命中缓存。**

在流式场景下，float32 的 4 倍字节直接把内存流量翻两番，
而层内多个矩阵（m 分支组 4.7 MB float）+ 8 层累加，远超 L3(16 MB)。
**计算省下的指令远不足以抵消多出的内存流量。**

> **教训（第 6 条，新子类）**：微基准必须复现真实的**访问模式**（流式 vs 重复），
> 而不只是真实的数据**形状**。此前的教训都是「拿巧合比值当因果」，
> 这一次是「用错误的访问模式测出了正确的形状」。
> **纪律：任何以「可缓存」为前提的优化，必须在真实调用路径上测端到端，微基准只能用来定交叉点。**

### 25.5 处置

- `PipelineRows::wf` 与 `build_float_weights()` **保留但不启用**（`float_w_` 默认 false），
  作为已否证路线的记录，避免后人重走
- 默认路径 checksum 仍为 259 ✓，所有实验开关默认关闭 ✓
- **§25.2 的交叉点数据仍然有用**：它说明在本机上「4 倍字节换 2 倍指令」只在 <1.7 MB 且缓存驻留时划算

### 25.6 本轮净结果

**fast_act 复现稳定：3 225.5 tps（§24 为 3 224.1），IQR 45.9。**
float 权重路线否证。当前最优仍为 **3 225 tps（8 线程）**，为 R0 基线的 3.22×。

剩余可行杠杆（按 §23.5）：VNNI 内核（×1.54，需 int8 激活，改变数值）、

## 二十六、AVX-512 内核：假设成立与否待测（2026-09-11 续，测量被阻塞）

### 26.1 被我忽略的关键区别

§25 否证 float 权重后，我重新审视内核，发现一个此前混淆的性质差异：

| 改动 | 改变了什么 | 是否需要重训 |
|---|---|---|
| `fast_act`（tanh → Padé） | **函数语义** | **需要** |
| AVX-512 内核 | **只有浮点累加的分组** | **不需要** |

AVX-512 版把累加器从 8 lane（`__m256`）换成 16 lane（`__m512`），
**每个元素上的 IEEE 运算完全相同**，只是加法的结合顺序不同 —— 相对误差量级 ~1e-7。
**这不改变模型学到的函数，因此无需重训** —— 与 §25 的 float 权重路线（逐位精确但慢）和
`fast_act`（改变语义需重训）都不同。

### 26.2 为什么预期有收益：现有内核撞的是前端，不是浮点单元

现有 AVX2 内核每 16 权重约 14 条指令 = **1.14 MAC/指令**。
实测 14.59 G MAC/s，在 ~3.7 GHz 下 = **3.94 MAC/周期 ÷ 1.14 = 3.46 指令/周期**。

**3.46 指令/周期已经逼近 Zen4 的发射宽度上限（约 4–5）。**
⇒ **瓶颈是前端指令发射，不是 FPU 吞吐。** 而 Zen4 的 FPU 峰值是 16 MAC/周期（2×FMA），
现仅用到 3.94 —— **利用率 25%，说明前端确实卡住了。**

**推论：AVX-512 把向量宽度翻倍，同样权重所需指令数大致减半**
（每 32 权重：2 加载 + 2 cvtepi8 + 2 cvtdq2ps + 2 mul + 2 加载 x + 2 mul + 2 add = 14 条
= **2.29 MAC/指令**，对比 1.14）。
即便 Zen4 的 512-bit 运算在后端是双泵（每个占 2 周期），**前端发射次数减半仍应带来显著收益**，
乐观情形接近 2×。

**注意这与 §15 的 VNNI 路线性质不同**：VNNI 需要把激活量化成 int8（**改变数值，需重训**），
而本路线保持 float32 激活，**只是重排累加**。

## 二十七、AVX-512 内核：单线程 +12.5%，8 线程 −4.3%（否证）（2026-09-11 续）

### 27.1 假设与微基准

§26 的假设：现有 AVX2 内核实测 3.46 指令/周期，已逼近发射宽度，
而 FPU 利用率仅 25% ⇒ 判定为**前端受限**，故 AVX-512 把指令数减半应有近 2× 收益。

`src/microbench_avx512.cpp`（**按真实流式访问模式**测量，避免 §25.4 的坑）：

| 形状 | AVX2 G MAC/s | AVX-512 G MAC/s | 倍数 | **最大相对差** |
|---|---:|---:|---:|---:|
| 128×512 | 13.43 | 17.66 | **1.31×** | 1.39e-05 |
| 512×512 | 14.53 | 17.13 | **1.18×** | 4.73e-05 |
| 512×1280 | 13.31 | 18.42 | **1.38×** | 1.11e-04 |
| 16384×512 | 11.29 | 13.58 | **1.20×** | **1.62e-03** |

**两个假设都被修正：**
1. **不是 2×，而是 1.18–1.38×**。原因：**Zen4 的 512-bit 运算是双泵的**，
   FPU 吞吐不变。实测 AVX2 只用掉约 49% FP 吞吐 ⇒ 前端与 FPU 是**共同瓶颈**，
   指令数减半只解掉前端那一半。§26.2 的「纯前端受限」判断过于乐观。
2. **相对差不是 ~1e-7，而是 1.4e-5 ~ 1.6e-3** —— 比朴素估计大 4 个数量级。
   原因：点积存在**抵消**（各项 ~0.1、和 ~O(√n·0.1)），相对误差被放大。

### 27.2 端到端实测：单线程变快，8 线程变慢

同进程交错 9 轮（`bench_interleaved`，IQR 8–71，比首轮干净）：

| 配置 | 中位 tps | IQR | 对比 |
|---|---:|---:|---|
| R3+R4 t1 | 676.8 | 8.1 | — |
| **R3+R4 t1 + avx512** | **761.3** | 10.8 | **1.125×** ✓ Δ=84.6 > 2IQR=21.6 |
| R3+R4 t8 | 2 678.0 | 71.2 | — |
| R3+R4 t8 + avx512 | 2 592.1 | 70.6 | **0.97×**（Δ=−85.9，未达显著） |
| R3+R4 t8 + fast_act | **3 209.3** | 51.1 | — |
| R3+R4 t8 + act + 512 | **3 071.8** | 22.9 | **0.957×** Δ=−137.5 > 2IQR=102.2 **显著更慢** |

**单线程 1.125×（与微基准 1.18–1.38× 吻合），8 线程反而更慢。**

### 27.3 为什么 8 线程反转：AVX-512 的全核频率惩罚

最可能的机制是**频率**：单线程时核心有余量，512-bit 负载不触发明显降频；
**8 核同时持续跑 512-bit 时全核频率下降**，代价超过前端收益。

（§18 已独立测得本机**全核频率惩罚 1.346×**；AVX-512 会在此基础上再叠一层。
本轮未单独测 AVX-512 的频率惩罚，这是**尚未直接证实的机制解释**，仅作为最合理假设记录。）

### 27.4 教训（第 7 条，新子类）

> **单线程微基准在结构上无法捕捉多核频率/功耗交互。**
>
> §25.4 的教训是「微基准必须复现真实的**访问模式**」；
> 这一次是「微基准必须复现真实的**并发度与功耗状态**」。
> 微基准**正确预测了单线程的 1.125×**，却在 8 线程上给出相反的结论。
>
> **纪律：任何涉及频率/功耗/共享资源的改动（向量宽度、指令混合、占用率），
> 必须在目标线程数下测端到端。**

## 二十八、带宽不是约束；模型已无开销可除；8 线程微基准不可信（2026-09-11 续）

### 28.1 一个可能翻转的结论：带宽是否已成绑定约束？

当前 3 209 tps × 权重总量 21.76 MB ⇒ 约 70 GB/s。
而 §14 判定「输出头非带宽受限」时是在 1 371 tps（约 30 GB/s）下做的 ——
**吞吐翻了 2.3 倍，绑定约束可能已经翻转。** 若成立，2-bit 打包（逐位精确、不需重训）
将重新成为有效杠杆。

实测（`src/microbench_bandwidth.cpp`，256 MB 流式读）：

| 线程 | 1 | 2 | 4 | **8** |
|---|---:|---:|---:|---:|
| GB/s | 14.61 | 20.83 | 23.50 | **23.91** |

**R3+R4 在 3 209 tps 下的权重流量需求 = 47.11 GB/s —— 是 DRAM 带宽的两倍。**

**但它确实在跑。** 唯一解释：**权重全部驻留在 L3 中。**

R3+R4 工作集 = 2 Full 3.34 MB + 6 Reuse 2.95 MB + 输出头 8.39 MB = **14.68 MB**，
**恰好塞进 16 MB 的 L3**（§三）。

> **⇒ §14 的结论是对的，而且现在有了机制解释**：不是「带宽够用」，
> 而是**工作集根本不出 L3**。DRAM 带宽从未参与。

### 28.2 2-bit 打包：逐位精确，但仍慢

`src/microbench_kernel_scaling.cpp`，每字节存 4 个三元值：

- **逐位相等检查：0 处不同 ✓**（值完全相同，只是存储格式）
- **但速度只有 int8 的 0.51–0.64×**（8 线程 23.11 vs 38.40 G MAC/s）

解包（移位/掩码/逐元素还原）的成本**超过**省下的带宽。
**§五死路清单中「位打包 0×」的条目成立**，现在有了直接证据。

### 28.3 决定性发现：模型层面已无开销可除

| 来源 | 8 线程 G MAC/s |
|---|---:|
| 内核微基准（int8） | 38.40 ~ 47.40（**两次相差 23%**） |
| **模型实际有效吞吐** | **47.1**（14.68 M / 0.3116 ms） |

**模型达到甚至超过独立测得的内核速率。**

> **⇒ 串行段、分发开销、负载不均 —— 全都不是瓶颈。**
> 8 层串行、19 次分发/token、状态更新、norm……这些加起来的影响
> **已经小到测不出来**。唯一剩下的杠杆是**内核本身的每核效率**。

### 28.4 8 线程微基准不可信（第 8 条教训）

| 线程 | int8 AVX2 | 2-bit | **AVX-512** | 512/AVX2 |
|---|---:|---:|---:|---:|
| 1 | 8.60 | 6.12 | **13.98** | **1.62×** |
| 2 | 17.99 | 10.52 | 23.10 | 1.28× |
| 4 | 29.08 | 14.52 | 31.15 | 1.07× |
| 8 | 38.40 | 23.11 | **47.99** | **1.25×** |

**内核微基准说 AVX-512 在 8 线程快 25%；端到端交错 A/B（§27.2，IQR 22–71）说慢 4.3%。**

**线索**：该微基准 8 线程数字**极不稳定** —— int8 8 线程两轮分别测得 47.40 与 38.40 G，**相差 23%**；
而单线程稳定在 8.60 / 8.69（相差 1%）。

> **⇒ 无交错、无中位数纪律的多线程微基准不可信。**
> 这正是本目标从一开始就强制「同一二进制内交错 A/B 取中位数」的原因 ——
> 这条纪律在本轮**第一次真正救了场**：若信了微基准，会得出完全相反的结论。
>
> **第 8 条教训**：多线程微基准必须走与生产相同的测量纪律；
> 单线程数字可以信，8 线程数字在无交错时不可信。

### 28.5 对 VNNI 的直接影响（重要）

§15 测得 VNNI 内核量子 **1.54×**，但那是**单线程**数字。
VNNI 依赖 AVX-512，而 **AVX-512 在 8 线程的惩罚已在 §27.2 被端到端证实**。

**⇒ VNNI 的端到端收益大概率明显低于 1.54×，甚至可能如 AVX-512 一样被频率惩罚抵消。**
在实现 VNNI 之前，必须先做一件事：**用与 §27.2 相同的交错 A/B 纪律，
测出 AVX-512 在 8 线程的真实代价**，并据此折算 VNNI 的预期值。

### 28.6 本轮的净结论

**内核层的所有路线现已系统性穷尽，且各有明确的实测理由：**

| 路线 | 结论 | 依据 |
|---|---|---|
| 位打包 / 字节压缩 | **否证** | 逐位精确但 0.51–0.64×（§28.2） |
| 预展开 float 权重 | **否证** | 0.39×，工作集爆出 L3（§25） |
| AVX-512 | **否证** | 端到端 0.957×（§27.2） |
| 路由 B（mask 内核） | **否证** | 0.50×（§15） |
| 输出头带宽受限 | **否证** | 权重 L3 常驻，DRAM 从未参与（§28.1） |
| 模型层开销（串行/分发） | **无可除** | 已达内核速率的 ~100%（§28.3） |
| 2-bit + AVX2 / 其他宽度 | **否证** | §28.2 / §27 |
| **VNNI int8** | **唯一未否证，但预期需下调** | §28.5 |

**⇒ 在不动模型的前提下，3 209 tps 就是本机的实际上限。**
要达到 10 000 t/s 必须改变模型（MAC 需从 14.68 M 降到约 3 M），因而**必须重训**。

## 二十九、多累加器内核：单线程 +32%，8 线程归零；8 线程是硬件天花板（2026-09-11 续）

### 29.1 假说：依赖链，不是发射宽度

§28 之后我重新核算单线程内核：8.60 G MAC/s ÷ 单核 boost 约 4.5 GHz ⇒ **1.91 MAC/周期**，
而 AVX2 乘加峰值是 8 MAC/周期 —— **只有 24%**。

回看内核代码，找到此前遗漏的嫌疑：
```cpp
sum=_mm256_add_ps(sum,a);
sum=_mm256_add_ps(sum,b);   // 两条【依赖】的加法，每 16 权重
```
**`sum` 是单条依赖链**，vaddps 延迟约 3–4 周期 ⇒ 每 16 权重约 8 周期 ⇒ **2 MAC/周期**。
**与实测 1.91 几乎完全吻合。**

`src/microbench_accumulators.cpp` 单线程实测（4096×512）：

| 变体 | G MAC/s | 加速 |
|---|---:|---:|
| 1 累加器（现状） | 10.48 | 1.00× |
| **2 累加器** | **15.90** | **1.52×** |
| **4 累加器** | **16.79** | **1.60×** |
| 8 累加器 | 12.95 | 1.24× |

**假说成立。** 8 累加器反而更差：8 累加器 + 8 权重 + alpha = **17 个 ymm > 16 ⇒ 寄存器溢出**。
**4 是甜点。**

数值差 3.45e-04（与 §27 的 AVX-512 同量级：只重排求和，不改语义，**不需重训**）。
**相对 AVX-512 的关键优势：纯 AVX2，无全核频率惩罚。**

### 29.2 端到端：单线程 +15.7%，8 线程归零 —— 与 AVX-512 完全相同的模式

同进程交错 5 轮（`bench_interleaved`）：

**单线程有收益、8 线程归零 —— 与 §27 的 AVX-512 模式完全一致。**
**⇒ 8 线程下内核不是被依赖链限制的。**

### 29.3 工作集扫描：不是缓存/带宽受限

`src/microbench_ws.cpp`，cols=512：

### 29.5 内核路线总账（全部实测否证）

| 路线 | 单线程 | **8 线程（端到端）** | 判定 |

（AVX-512 +12.5% → −4.3%；多累加器 +15.7% → −2.1%。）

**⇒ 8 线程解码处于硬件天花板：约 47 G MAC/s。**
瓶颈是**全核频率 + 8 核争用**，不是内核的指令结构 —— 因此**任何内核改写都无法突破**。

### 29.6 最终结论

**内核层的每一条路线都已实测否证，且模型已无开销可除。**

| 大类 | 状态 |
|---|---|
| 内核改写（宽度/累加器/打包/格式） | **全部否证** |
| 模型层开销（串行/分发/负载） | **无可除**（模型 ≥ 内核速率） |
| 带宽 / 缓存 | **非约束**（工作集 L3 常驻，越大越快） |
| 并行度 | 8 线程已达频率修正理想的 ~76–92%，且 16 线程 SMT 饥饿会崩溃 |

**⇒ 在保持 checksum 不变的前提下，3 209 t/s 是本机的硬上限，无法通过软件改写提升。**

**达到 10 000 t/s 的唯一路径是改变模型本身**（MAC 从 14.68 M 降到约 3 M），
即**架构升级 + 重训**。这不是工程优化问题，是需要训练资源投入的架构决策。

## 三十、重大订正：8 线程是 **L3 内存受限**，不是算力受限（2026-09-11 续）

### 30.1 线索来自 §29 的一个反常

§29 的工作集扫描里有一个我当时没有利用的反常：

```
16384 行:  1acc  1T 10.03 → 8T 39.66  (3.95x)
           4acc  1T 13.24 → 8T 38.25  (2.89x)
```

**4 累加器把单线程提高了 32%，却完全没有提高 8 线程的天花板（38–40 G）。**
**⇒ 8 线程的上限若是「每核算力」，提高每核效率就应当提高总量。它没有。**

### 30.2 判决性实验：固定每线程工作量，只变线程数

`src/microbench_share.cpp`，每线程固定 **512 行（0.26 MB，单核可驻 L2）**：

| 线程 | 总行数 | 总 MB | G MAC/s | **每核 G** | 相对 1T |
|---:|---:|---:|---:|---:|---:|
| 1 | 512 | 0.26 | 7.48 | 7.48 | 1.00× |
| 2 | 1 024 | 0.52 | 21.43 | 10.71 | 2.86× |
| 3 | 1 536 | 0.79 | 26.86 | 8.95 | 3.59× |
| 4 | 2 048 | 1.05 | 38.85 | 9.71 | 5.19× |
| 6 | 3 072 | 1.57 | 57.84 | 9.64 | 7.73× |
| **8** | **4 096** | **2.10** | **69.88** | **8.74** | **9.34×** |

**对照（§29.3）：8 线程 × 16 384 行（8.39 MB）= 39.66 G。**

**同样 8 线程、同样充足的每线程工作量，工作集小 4 倍 ⇒ 吞吐高 1.76×。**

> **⇒ 8 线程的上限是内存系统，不是算力。**
> 每核效率：L2 常驻 **8.74–10.71 G**；L3 常驻 **4.96 G**（39.66/8）。**差 1.8×。**

### 30.3 订正 §28.1：我测错了带宽

§28.1 我测了 **DRAM** 流式带宽（23.91 GB/s），发现解码需要 47 GB/s 却跑得动，
于是断言「权重 L3 常驻 ⇒ 带宽不是约束」。

**这个推理漏了一半**：L3 能提供 47 GB/s，**不等于 L3 带宽无限**。
**真正的约束是 L3→核心的带宽**，而我从未测它。

**⇒ §28.1 的结论「带宽不是约束」错误。正确表述是：「DRAM 带宽不是约束，L3 带宽才是」。**

### 30.4 修正工作集账（§28.1 也算错了）

R3+R4 的 `share=0,0,0,0,4,4,4,4` 意味着 **6 个 Reuse 层读取的是它们 Full 层的那份矩阵**，
**不增加任何字节**。我之前把 6 个 Reuse 层各算了一遍（得出 14.68 MB），是错的。

**实际每 token 读取：2 个 Full 层 3.34 MB + 输出头 8.39 MB = 11.73 MB。**

**⇒ 输出头单独就 8.39 MB，而 8 核 L2 合计只有 8 MB。输出头装不进 L2。**

### 30.5 由此得出的新杠杆：2-bit 打包输出头

若把输出头 2-bit 打包：**8.39 MB → 2.10 MB**，加上层 3.34 MB = **5.44 MB < 8 MB L2** ✓
⇒ **整个工作集进入 L2**，可望吃到 §30.2 那 1.76× 的一部分。

**估算**：head 0.1332 ms ÷ 1.76 ≈ 0.0757 ⇒ token 0.254 ms ⇒ **约 3 940 tps（+23%）**。

### 30.6 订正 §28.2：上轮的 2-bit 否证不成立

§28.2 测得 2-bit 只有 **0.51–0.64×**，我据此把它归入死路。**但那次测试的工作集只有 2.10 MB
（4096 行）——根本不在内存受限区间**，测的是纯指令成本，而解包确实更贵。

**⇒ 该否证在错误的区间上做出。** 2-bit 打包必须在**大工作集（内存受限区间）**下用**快速 SIMD 解包**重测。

**指令成本核算**（说明它有希望）：现有 int8 内核 = 14 条/16 权重 = **0.875 条/权重**；
SIMD 2-bit 解包（4 个位平面 + 交错）= 约 105–110 条/128 权重 = **0.82–0.86 条/权重**。
**指令数相当，而字节数少 4 倍** —— 在内存受限区间这正是所需。

### 30.7 新的优先级

| 项 | 状态 |
|---|---|
| **输出头 2-bit 打包 + 快速 SIMD 解包** | **最高优先级**（唯一有机制支撑且未在正确区间测过） |
| VNNI int8 | 次之（需 int8 激活；且依赖 AVX-512，有频率风险） |
| 其余内核改写 | 已否证 |

**关键实现要点**：2-bit 解包会打乱权重顺序（4 个位平面交错），
但**所有行共享同一个 x**，因此可**每 group 预置换 x 一次**来对齐，
置换成本按 `rows` 摊薄后可忽略。注意这会改变求和顺序（与 AVX-512/多累加器同类）。

## 三十一、订正 §30：L3 带宽假说**被否证**；8 线程微基准不可用（第三次）（2026-09-11 续）

### 31.1 实现并修正了位平面内核

按 §30.7 的计划实现 2-bit 位平面内核：`weight = b0 - b1`（两个位平面），
`sum_j q_j*x_j = Σ_{b0} x − Σ_{b1} x`，用掩码加/减。

**修掉两个 bug**（记录以备后人）：
1. **lane 与权重错位**：用 `_mm256_cvtepi8_epi32` 载入 8 字节后，
   若配 `{7,6,...,0}` 移位向量，lane k 取的是「第 k 字节的第 k 位」，
   与权重顺序不符。正确组织是「每 8 个权重共用一个字节，lane l 取该字节 bit l」。
2. **符号位偏移错误**：`c0 << 7` 把 bit 0 移到 bit 7，而 `srai 31` 看的是 **bit 31**
   ⇒ 掩码恒为 0（相对差恰好 = 1.00，即结果全 0）。
   正确移位是 `31 - l`。

修正后**数值正确**：最大相对差 **1.06e-06（1.05 MB）/ 1.06e-04（8.39 MB）**，
属舍入级（alpha 在末尾统一乘，与逐元素乘的差异）。

### 31.2 结果：4 倍字节削减，8 线程收益为零

同一进程同一轮内对比（`src/microbench_bitplane.cpp`）：

| 工作集 | 内核 | 1T | 8T | 8T 对比 |
|---|---:|---:|---:|---:|
| 2048 行（int8 1.05 MB → 位平面 0.26 MB） | int8 | 6.41 | 17.64 | — |
| 同上 | 位平面 | 5.29 | 17.23 | **0.98×** |
| 16384 行（int8 8.39 MB → 位平面 2.10 MB） | int8 | 10.54 | 23.01 | — |
| 同上 | 位平面 | 6.16 | **22.83** | **0.99×** |

**⇒ §30 的「L3 带宽受限」假说否证。** 若真是 L3 带宽受限，4 倍字节削减应有显著收益。

### 31.3 订正 §30.2 的实验：它被重复次数混杂

复查 §30.2 那个「判决性实验」，发现**混杂因素**：

| 组 | 每线程行数 | 工作集 | **重复次数** |
|---|---:|---:|---:|
| 小工作集组 | 512 | 2.10 MB | **40** |
| 大工作集组（§29.3） | 2048 | 8.39 MB | **3** |

**冷缓存成本在总时间中的占比相差 13 倍。** 小工作集组有 40 次重复，
首次冷读被摊薄到 1/40；大工作集组只有 3 次，冷读占 1/3。

**我把这个差异误读成了「工作集效应」。** §30.2 的 1.76× 是测量假象。

### 31.4 第 9 条教训：8 线程微基准的方差使其不可用（第三次被咬）

同一形状（16384×512）的 int8 内核，8 线程吞吐在不同轮次测得：

| 出处 | 8T G MAC/s |
|---|---:|
| §29.3（microbench_ws） | **39.66** |
| §31.2（microbench_bitplane） | **23.01** |
| §28.3（kernel_scaling） | 38.40 / 47.40（同一程序两轮） |

**同一形状、同一内核，轮次间相差最高达 2 倍。** 单线程则稳定（8.60/8.69，差 1%）。

> **第 9 条教训**：8 线程微基准的方差（~2×）**大于任何待测效应**，
> 因此**在结构上不可用于判断优化是否有效**。
>
> 这已是第三次被咬：
> - §27 AVX-512：微基准说 +25%，端到端说 −4.3%
> - §29 多累加器：单线程 +32%，8 线程微基准与端到端都归零
> - §30/§31 工作集：微基准说 1.76×，位平面实测 0.99×
>
> **唯一可信的测量是 §18.7 起的「同一二进制内交错 A/B 取中位数」。**
> 任何 8 线程微观结论都必须回到端到端验证，否则不得写入结论。

## 三十二、VNNI 端到端：单线程 1.965×，8 线程 +2.5%（首个正面内核结果）（2026-09-11 续）

### 32.1 实现

`y[r] = alpha[r]·sx·( Σ_j q[r][j]·xu[j] − 128·rowsum[r] )`

其中 `xu[j] = round(x[j]/sx)+128 ∈ [0,255]`（dpbusd 的无符号操作数），
`rowsum[r] = Σ_j q[r][j]` 装载时预计算。
`_mm512_dpbusd_epi32` **一条指令算 64 个乘加** ⇒ 0.047 条/权重（对比 int8 的 0.875，**18× 指令削减**）。
**改变数值**（激活量化到 int8）⇒ 默认关闭。

### 32.2 过程中修掉两个真 bug（记录备查）

1. **并发堆损坏（0xC0000374）**：`quantize_input()` 原本在 `dot_vnni()` 内部按需调用，
   而 `group<>` 的 **8 个工作线程会同时**对**同一个** `PipelineRows` 调 `dot`
   ⇒ 并发 `xu_.resize()` ⇒ 堆损坏。
   **修法：量化必须在 `dispatch_rows` 之前完成**，每个矩阵一次。
2. **贪心头遗漏（0xC0000005）**：`greedy_head_observe`（第 249 行）**直接调 `p.dot`**，
   不经过 `group`/`linear`，因此从未量化 ⇒ `xu_` 为空 ⇒ 访问违例。
   **教训：给内核加"有状态前置步骤"时，必须穷举所有调用点。** 用全文搜索确认了
   `group` / `linear` / `greedy_head_observe` 三处是全部调用点。

量化缓存的正确性依据：每次分发前显式重量化，
**不依赖指针比较判断内容是否变化**（`s` 等状态会原地修改而指针不变）。

### 32.3 端到端结果（同进程交错 5 轮）

| 配置 | 中位 tps | IQR | 对比 |
|---|---:|---:|---|
| R3+R4 t1 | 687.6 | 7.7 | — |
| **R3+R4 t1 + vnni** | **1 351.2** | 86.7 | **1.965×** ✓ 显著 |
| R3+R4 t8 | 2 817.7 | 51.4 | — |
| R3+R4 t8 + vnni | 2 881.5 | 47.5 | 1.023×（Δ=63.8 < 2IQR=102.8，**不显著**） |
| R3+R4 t8 + fast_act | 3 309.2 | 30.9 | — |
| **R3+R4 t8 + act + vnni** | **3 390.6** | 17.9 | **1.025×**（Δ=81.4 > 2IQR=61.8，**显著**） |
| R3+R4 t8 + act + macc | 3 359.8 | 45.7 | 1.015× |
| R3+R4 t8 + avx512 | 2 652.0 | 25.2 | 0.94× |

**⇒ 单线程 1.965×（几乎翻倍），8 线程仅 +2.5%。**

**这是本项目第一个正面的内核级结果**，虽然幅度小。
**新纪录 3 390.6 tps**（8 线程，act+vnni）。

### 32.4 它再次确认了 8 线程的性质

| 内核改写 | 单线程 | 8 线程端到端 |
|---|---:|---:|
| 多累加器 | 1.32–1.60× | 0.98–1.01× |
| AVX-512 | 1.18–1.62× | 0.94× |
| **VNNI** | **1.965×** | **1.025×** |

**单线程收益越大，8 线程收益并不随之增大。**
VNNI 把每权重的指令数削减 18 倍（0.875 → 0.047），8 线程只换来 2.5%。

> **⇒ 8 线程的解码瓶颈与内核的指令效率基本无关。**
> 1 线程时内核确实是指令受限（VNNI 近 2× 可证）；
> 8 线程时另有一个约 40 G MAC/s 量级的上限，且**已排除**：
> 指令数（VNNI）、依赖链（多累加器）、向量宽度（AVX-512）、
> 字节数（位平面 2-bit）、缓存驻留（float 权重）、
> 并行扩展（8 线程已达频率修正理想的 ~76–92%）。

**该上限的具体机制仍未确定**，但可以确定：**它不是上述任何一条**。

### 32.5 建议采纳

VNNI 的 +2.5% 虽小，但：
- 是**唯一**在 8 线程为正的内核改动
- 与 `fast_act` 正交，可叠加（3 309.2 → 3 390.6）
- 默认关闭、可回退，符合约束

**若后续决定重训**，VNNI 可与新架构一起评估（反正要重训，量化的数值影响可与新激活一并考量）。

### 32.6 本轮的一次测量环境提示

本轮 `R0_t8` 测得 **1 415.4**（此前各轮为 990–1 020，+40%），
而 `R3+R4_t8` 为 2 817.7（+3~5%）。**两者变化幅度不一致**，说明后台负载或频率状态有变化。

**⇒ 再次印证：跨轮次的绝对值不可比，只有同轮交错比值可用。**

## 三十三、频率不是瓶颈；§18 的频率惩罚在 8 线程下不适用（2026-09-11 续）

### 33.1 方法

在 `benchmark_noffn_s3.cpp` 内植入**占空比频率探针**：
- 依赖 `mulsd` 链（Zen4 延迟 3 周期）⇒ 周期数 = 3 × 迭代数
- **占空比 2 ms 运行 / 8 ms `sleep` 让出核心** ⇒ 扰动极小
- **只在奇数轮启用** ⇒ 同一进程内就有「有探针 / 无探针」的交错 A/B

**探针对测量的扰动（同进程交错验证）**：

| 线程 | 无探针轮中位 tps | 有探针轮中位 tps | 扰动 |
|---:|---:|---:|---:|
| 1 | 476.3 | 481.8 | 1.011× |
| 8 | 1 099.9 | 1 072.8 | 0.975× |

**±2.5% 以内，探针可用。**

### 33.2 结果：8 线程频率**不低于**单线程

| | 1 线程 | 8 线程 |
|---|---:|---:|
| 探针频率 | 4.148 / 4.033 GHz | **4.282 / 4.271 GHz** |

> **⇒ 8 线程解码运行时核心频率约 4.27 GHz，与单线程的 4.15 GHz 基本相同（甚至略高）。**
> **⇒ 那个约 40 G MAC/s 的 8 线程上限不是频率/功耗墙。**

### 33.3 订正 §18：1.346× 频率惩罚不适用于 8 线程

§18 用 **14 个燃烧线程**（占满 16 个逻辑核）测出全核频率惩罚 1.346×。
**但 8 线程只占 8 个物理核、不触发 SMT，封装功耗仍在预算内**，
因此包频率维持在 ~4.27 GHz。

**⇒ §18 的 1.346× 不能在 8 线程场景套用。**

**由此，§19–§32 中所有「频率修正后的理想加速比 5.94×」的计算都偏高（惩罚被高估），
真实差距比原先记录的更大。** 后续引用应改用本节的直接测量值。

### 33.4 新谜题：同频率下 1→8 线程只有 2.35×

本轮 `benchmark_noffn_s3` 运行的是**未做层共享**的模型（该基准不调用 `set_layer_share`）：

| 模型 | 1 线程 tps | 8 线程 tps | 加速比 |
|---|---:|---:|---:|
| **未共享**（`benchmark_noffn_s3`） | 480.4 / 476.3 / 470.8 | 1 127.4 / 1 099.9 | **2.35×** |
| **R3+R4 共享**（`bench_interleaved`） | 687.6 | 2 817.7 | **4.10×** |

**核心频率相同的前提下，8 个物理核只换来 2.35×。**

**⇒ 并行扩展效率仅约 29%（2.35/8），这是目前最大的单一缺口。**
若能提到 6×，即约 2 900 tps（未共享基准）；提到 7× 即约 3 400 tps。

### 33.5 两条候选机制的粗算

| 模型 | 每 token 字节 | 8 线程 tps | 折算带宽 |
|---|---:|---:|---:|
| 未共享 | 8 层 × 1.67 + 头 8.39 = **21.8 MB** | 1 127 | **24.6 GB/s** |
| R3+R4 | 2 层 × 1.67 + 头 8.39 = **11.73 MB** | 2 818 | **33.0 GB/s** |
| R3+R4 + fast_act | 11.73 MB | 3 309 | **38.8 GB/s** |

## 三十四、定位到真正的瓶颈：层栈的**小分发并行度**；§28.3「无开销」是错的（2026-09-11 续）

### 34.1 先排除一个我自己制造的测量陷阱

本轮开始时，`benchmark_noffn_s3` 在同配置下测到 **1395 tps**，
而 `bench_interleaved` 测到 **3309 tps** —— **2.4× 差异**，若不解开则此前所有结论都不可信。

用 `config_dump()` 自证，抓到：

```
benchmark_noffn_s3 : share=0,1,2,3,4,5,6,7   ← 层共享没生效
bench_interleaved  : share=0,0,0,0,4,4,4,4   ← 生效
```

**根因：`cmd /c` 会把引号原样传给程序**，于是 `argv[4]` 是 `"0,0,0,0,4,4,4,4"`（**含引号**），
`strtoul` 在 `"` 上失败 ⇒ `parseLayerShare` 走 `return identitySource(n)`。

判据是：`config_dump` 里 **`reuse_mv` 是有的** ⇒ `if(argc>4)` 确实执行了 ⇒ 只能是解析失败。

**改用模型本来就支持的 `TAO_LAYER_SHARE` 环境变量**（无引号）后，两个基准完全对上：

| 基准 | 8 线程 tps（R3+R4+fast_act） |
|---|---:|
| `bench_interleaved` | 3 209 ~ 3 390 |
| `benchmark_noffn_s3`（修正后） | **3 112** |

> **教训（第 10 条）**：**分层配置必须自证**。
> 这正是 `set_cpu_threads(1)` 那次教训的同类复发 —— 当时靠 `config_dump()` 才抓出
> 「t1 静默变成 2 线程」。**任何经由 argv/字符串的配置传递都要打印生效值。**

### 34.3 结论：瓶颈是**层栈的小分发**，不是内存也不是算力

**输出头是一整块 16 384 × 512 的矩阵，一次分发、每线程 2 048 行 ⇒ 扩展到 6.05×。**
**层栈由大量 512 行 / 128 行的小矩阵组成，每次分发每线程只有 16–64 行 ⇒ 只到 3.52×。**

`norm` **完全不扩展（1.01×）** —— 它是 512 维向量上的串行代码（且每次都做字符串键的 `w.at(name)` 查表）。

> **⇒ 真正的瓶颈是模型层的「分发粒度 / fork-join 屏障」，与 §29–§33 追查的
> 指令效率、字节数、缓存驻留、频率**全部无关**。**

### 34.4 订正 §28.3

§28.3 曾断言「模型无可除开销」，依据是
**模型有效吞吐 47.1 G MAC/s ≥ 微基准 8 线程内核 38.4–47.4 G MAC/s**。

**这个判据是错的**：它只比较了**吞吐总量**，而**串行化恰恰表现为吞吐总量看起来正常**——
因为瓶颈相位（body）不扩展，但整体 MAC 数没变，比值自然「正常」。

**⇒ 「模型吞吐 ≈ 内核吞吐 ⇒ 无开销」是一个无效推理。**
正确做法是看**相位各自的扩展比**（本节的表）。

### 34.5 订正 §28.4 与目标杠杆①

**目标里的杠杆①「分发融合（每 token 32 次分发降到 8 次）」当初被我判为「可能无用」，
依据就是 §28.3。现在看，杠杆① 是正确的方向。**

**上界估算**（把 body 的扩展比从 3.52× 提到什么水平）：

| 8.0×（理想） | 0.0791 | 0.2134 | 4 686 | +51% |

**⇒ 「分发融合」一项就有 +35~50% 的空间，且不需要重训、不改变任何数值。**

### 34.6 下一轮的具体做法

1. **查清 `group<N>` 的负载划分方式。** 当前是
   `dispatch_rows(offsets[N],1,...)` —— 按**拼接后的行空间**均分。
   若各矩阵 `cols` 不同（512 与 128 混用），
   **等行分 ≠ 等工作分**，会产生真实的不均衡。
   候选改法：**按 MAC 数加权划分**，或**对每个矩阵各自按行划分、所有矩阵共用同一划分**。
2. **`norm` 串行**：2.9% 且不扩展。候选改法：去掉 `w.at(name)` 字符串查表（改为索引）、

3. 一切改动仍按纪律：**同一二进制内交错 A/B 取中位数**，

## 三十五、真正的瓶颈是**串行占比 49.3%**；通往 10 000 tps 的路线图（2026-09-11 续）

### 35.1 先否证 §34.6 的两个候选

**候选一：负载划分不均衡。** 读代码发现 **划分已经是按 MAC 数加权的**：

```cpp
offsets[i+1]=offsets[i]+p.rows*p.cols;   // 不是 +p.rows
```

且注释明确「No dot is split: each side differs from half-cost by less than one row cost」。
**⇒ 均衡没问题，该假说不成立。**

**候选二：屏障开销（即 §34 的「分发融合」）。** 用 `mincost` 扫描直接测：

| mincost | tps | body | head | wall |
|---:|---:|---:|---:|---:|
| 1 | 3 350.1 | 0.1721 | 0.1273 | 0.3011 |
| 4 096 | 3 315.9 | 0.1697 | 0.1262 | 0.2977 |
| 16 384 | 3 315.9 | 0.1699 | 0.1284 | 0.3007 |
| 65 536 | 3 115.2 | 0.1711 | 0.1409 | 0.3144 |
| 131 072 | 2 940.0 | 0.1791 | 0.1627 | 0.3450 |
| 262 144 | 2 272.5 | 0.2761 | 0.1676 | 0.4451 |

`mincost` 越高 ⇒ 越多的分发退化为串行 ⇒ 分发次数越少。
**1 → 16 384 完全平坦（3 350 → 3 316），之后单调变差。**

> **⇒ 减少分发次数（= 降低屏障开销）没有收益，屏障开销不是瓶颈。**
> **§34.5 中「分发融合可带来 +35~50%」的推算因此不成立，予以撤回。**

### 35.2 正确的诊断：串行分量（Amdahl）

对第 34 节相位数据做 `T(n) = S + P/n` 拟合（用 1 线程与 8 线程两点）：

| 相位 | S 串行 ms | P 并行 ms | 串行占比 @1T | **串行占比 @8T** |
|---|---:|---:|---:|---:|
| norm | 0.0092 | 0.0001 | 98.8% | **99.8%** |
| s_upd | 0.0355 | 0.1059 | 25.1% | **72.8%** |
| read | 0.0400 | 0.2151 | 15.7% | 59.8% |
| m_upd | 0.0303 | 0.1967 | 13.4% | 55.2% |
| body | 0.1150 | 0.5178 | 18.2% | **64.0%** |
| head | 0.0375 | 0.7747 | 4.6% | 27.9% |
| **整体** | **0.1560** | **1.2827** | — | **49.3%** |

（拟合自洽性检查：body 预测 4 线程 = 0.1150 + 0.5178/4 = 0.2445，实测 0.2593 ✓）

> **⇒ 8 线程解码时，整个 token 有 49.3% 的时间花在无法并行化的串行代码上。**
> 这就是「并行扩展只有 4.55×、body 只有 3.52×」的全部原因。

**串行代码分布在**：512 维向量上的 `norm()`（含字符串键 `w.at(name)` 查表）、
`add()` 标量逐元素循环、每层的状态更新、以及输出头的收尾。

### 35.3 这解释了 VNNI 为何在 8 线程只有 +2.5%

VNNI 把**并行部分**的内核加速 **1.965×**（单线程实测）。

| 情形 | wall（8 线程） | 预测 tps |
|---|---:|---:|
| 现状 | 0.3163 ms | 3 112 |
| **A 只去串行** | 0.1603 ms | **6 238** |
| B 只把并行部分换 VNNI（1.965×） | 0.2376 ms | 4 209 |
| **C 去串行 + 并行部分 VNNI** | **0.0816 ms** | **12 255** |

> **⇒ 并行部分本来就不是瓶颈，所以 VNNI 的 1.965× 在 8 线程被稀释成 2.5%。**
> **必须先去掉串行，VNNI 的收益才会释放出来。**

### 35.4 路线图

**目标 10 000 tps 需要 wall ≤ 0.100 ms。** 由 §35.3：

1. **第一步（必需）：消除串行分量**，0.156 ms → 尽量接近 0。可望达到约 **6 200 tps**。
2. **第二步（必需）：并行部分启用 VNNI**，释放单线程已证的 1.965×。
   两步齐备可望达到约 **12 200 tps**，即达标。

**单独任一步都不够**（A 6 238 < 10 000；B 4 209 < 10 000）。

**注**：以上为理想估算，未计串行消除本身的成本、VNNI 量化的单线程开销、
以及 8 线程下并行部分可能达不到 1.965× 的风险。**须逐步实测验证，不可当作承诺。**

### 35.5 下一步

**优先攻串行分量，按占比排序**：

| 串行项 | 量级 | 候选做法 |
|---|---:|---|
| `read`/`m_upd`/`s_upd` 中的 `norm()` 与 `add()` | ~0.10 ms | **并入相邻分发**（在同一批线程上顺手做完），或去掉字符串查表 |
| 每层状态更新 | 0.0355 ms | 已在 `candidate` 线程做，考虑并入分发 |
| 输出头收尾（bias + argmax） | 0.0375 ms | 考虑在分发的最后一个 chunk 内完成 |

**纪律不变**：同一二进制内交错 A/B 取中位数；`config_dump()` 自证配置；
每步写入本文档。

## 三十六、分配次数已测（176/token），但更大的缺口仍未解释（2026-09-11 续）

### 36.1 已确认的事实：每 token 176 次堆分配

用**全局 `operator new` 覆写**统计（`TAO_ALLOC=count`）：

```
S3 threads=8 ALLOC per_token=176.0 bytes_per_token=146304
```

**每 token 176 次分配、143 KB。** 在 3 347 tps 下即 **约 59 万次分配/秒**。
来源清楚：`group<N>` 返回 `std::array<Vec,N>`（每层 4+6+2 个 Vec），
`norm()` 与 `linear()` 各返回一个 Vec，另有 `p+"read.norm"` 之类的**临时 std::string**
（"layer.0.read.norm" 17 字符 > MSVC 的 15 字符 SSO 上限 ⇒ **每次都堆分配**）。

### 36.2 但分配很可能不是主要瓶颈

做了一个三模式分配器 A/B（同一二进制，`TAO_ALLOC` 环境变量）：

| 模式 | 做法 | 8 线程 tps 中位 |
|---|---|---:|
| `plain` | 原生 malloc/free | 3 129.1 |
| `count` | malloc/free + **每次分配两次争用原子自增** | 3 341 ~ 3 414 |

**`count` 比 `plain` 每次分配多做两次跨线程争用的原子 RMW（352 次/token），
吞吐却没有变慢（差异在轮次噪声内）。**

> **⇒ 分配路径对争用不敏感，说明它多半不是那个大的串行瓶颈。**

（`pool` 模式——线程本地空闲链表——以 **0xC0000374 堆损坏**崩溃。
**原因：`thread_local` 不能安全地用在全局 `operator new` 里** —— 线程启动/退出阶段
TLS 可能尚未初始化或已析构。记为一条实现陷阱。）

### 36.3 真正未解释的缺口：相位实测 vs 矩阵乘理论时间

用 §34.2 的 8 线程相位值，与「该相位内矩阵乘的 MAC 数 ÷ 8 线程 ÷ 约 2 MAC/周期 ÷ 4.2 GHz」对比：

| 相位 | 8 线程实测 | 矩阵乘理论 | 差距 | 粘合代码量 |
|---|---:|---:|---:|---|
| ms_s | 45.7 µs | 9.8 µs | **4.7×** | 4 个 512 维 `add` + 1 次 128 维状态更新 |
| ms_m | 54.9 µs | 17.6 µs | **3.1×** | 6 个 512 维 `add` + 1 次 512 维状态更新 |
| **ms_read** | **66.9 µs** | **4.9 µs** | **13.7×** | 2 个 512 维 `add` + 1 次 `norm` |

**ms_read 的粘合代码总共约 1 536 个标量元素操作，按每个 10 周期算也只有 3.7 µs，
而实测缺口是 62 µs —— 相差约 17 倍。**

**⇒ 这个缺口用「分配次数」「屏障开销」「负载不均」「频率」都无法解释，
是目前最重要的未解问题。**

### 36.4 剩余的具名嫌疑（按可能性排序）

1. **`w.at(name)` 字符串键查表 + 临时 `std::string` 构造。**
   每层 6 次（`input.norm`、两个 `s` bias、两个 `m` bias、`read.norm`），**每 token 48 次**。
   17 字符的键超出 MSVC SSO 上限 ⇒ 每次都堆分配 + `std::map` 的红黑树查找（约 5–6 次字符串比较）。
   这解释了 §36.1 中相当一部分分配。
2. **`add()` 是标量逐元素循环**（无 SIMD、无展开），每 token 约 96 次 × 512 元素 = 4.9 万次标量操作。
3. **`norm()` 的实现**（是否需要两次遍历、是否用 sqrt 逐元素）。
4. **`std::vector` 的零初始化**：`Vec o(dv,0)`、`out[i].resize(rows)` 等会写零。

### 36.5 下一轮：先做细粒度子相位计时，再动手

**上一轮的教训是「先量再做」。本轮 §36.3 的 17 倍缺口说明我仍然不知道钱花在哪。**

**做法**：在层循环内插入子相位计时器，分别计量
`norm` / `add` / `w.at` 查表 / 状态更新 / `group` 分发本身，
在 1 与 8 线程下各跑一次。

**只有当子相位数据指明主项之后，才动手优化。** 优先级最高的候选改法（若数据支持）：

- **把字符串键改成编译期索引**（`packed` 用索引数组而非 `std::map<std::string,...>` 查找）
- **预先算好带前缀的键向量**，避免每层构造 `std::string`
- **`add()` 向量化（AVX2）并展开**

**纪律不变**：同一二进制内交错 A/B；`config_dump()` 自证；每步写入本文档。

## 三十七、决定性归因：瓶颈在 `group<>` 内部的串行开销，**不在粘合代码**（2026-09-11 续）

### 37.1 方法：子相位计时

在模型里加 `SubTimer` 与表达式计时宏 `TAO_T(acc,expr)`，
分别计量 **`group<N>` 调用本身**、**`add`+`w.at` 查表**、**`norm`**，其余归入残差。
三者和与 `s_upd+m_upd+read` 严格对账。

### 37.2 结果（R3+R4 + fast_act，mincost=1）

| 项 | 1 线程 ms | 8 线程 ms | 扩展比 |
|---|---:|---:|---:|
| **`group` 分发本身** | **0.5765** | **0.1430** | **4.03×** |
| `add` + `w.at` 查表 | 0.0125 | 0.0122 | 0.98× |
| `norm` | 0.0189 | 0.0198 | 0.95× |
| 残差 | −0.0008 | −0.0009 | ≈ 0 |

（8 线程 `group` 占 s_upd+m_upd+read 总和的 **82%**，占整个 token 的 **45%**。）

> **⇒ 粘合代码根本不是问题。`add` + 查表 + `norm` 合计仅 0.032 ms，
> 只占 token 的 10%。**
>
> **§35.5 与 §36.4 把 `norm()`/`add()` 列为头号串行嫌疑，这个判断是错的，予以撤回。**

### 37.3 真正的串行来源：`group<>` 内部的查找与分配

`group<>` 除了并行分发，还做两件**串行**的事：

```cpp
const auto& p=packed.at(names[i]);   // std::map<std::string,PipelineRows> 红黑树查找

```

**调用次数**：每层 `group<4>`(4) + `group<6>`(6) + `group<2>`(2) = 12 次 `packed.at`，
另有 `add` 块里 6 次 `w.at` ⇒ **每层 18 次、每 token 144 次字符串键查找**。
且 `p+"m.candidate.x"` 这类临时 `std::string` 长 17 字符 **超出 MSVC 的 15 字符 SSO 上限**
⇒ 每次都堆分配（§36.1 的 176 次/token 中相当一部分来自这里）。

**对 `group` 的 1/8 线程两点做拟合**：S = 0.0811 ms，P = 0.4954 ms。
**⇒ `group` 的串行分量 0.0811 ms，占全 token 串行总量（约 0.151 ms）的 54%，是最大单项。**

### 37.4 预期收益

| 项 | 现状 | 若消除 `group` 串行 |
|---|---:|---:|
| wall（8 线程） | 0.3177 ms | 0.2366 ms |
| tps | 3 124 | **约 4 227（+35%）** |

### 37.5 已试并失败的路线

**把 `std::map` 换成 `std::unordered_map`**（最小改动、不改语义）：
编译失败，错误指向 `std::pair<const std::string, Vec>` 无法构造。

> **原因**：`std::map` 是节点式容器，插入不需要重哈希；
> **`std::unordered_map` 要求值类型可移动**，而 `Vec`/`PipelineRow` 不满足。
> **⇒ 该路线被类型性质挡住，已回退（`checksum=259` 未受影响）。**

### 37.6 下一轮的候选做法

**目标：把 `group<>` 的 144 次字符串键查找与临时字符串全部移出热路径。**

| 方案 | 思路 | 风险 |
|---|---|---|
| **A. 预解析指针表** | 模型构造时（或首次调用时）把每层每组需要的 `PipelineRows*` 解析好，存成索引数组，热路径只做数组下标 | 低；不动容器类型 |
| **B. 预生成键字符串** | 每层只构造一次 `p+"..."`，缓存复用 | 低；只省临时字符串 |
| C. 换哈希容器 | 需先把 `Vec`/`PipelineRows` 改成可移动 | 中；改动面大 |

**推荐先做 A + B**：既不移出字符串查找，也不改容器类型，改动局部、可回退。

**纪律不变**：同一二进制内交错 A/B 取中位数；`config_dump()` 自证；每步写入本文档。

## 三十八、【已撤回】`group<>` 拆解：~~真正的矩阵乘只占 3%，查表+分配占 38%~~（**本节结论是插桩 bug 造成的假象，见 §39**）（2026-09-11 续）

### 38.1 方法

把 `group<>` 内部再拆成两段计时：

- **`pre`** = 前置循环（每矩阵一次 `packed.at(names[i])` + `out[i].resize(rows)`）
- **`dispatch`** = `group` 总计 − `pre`（即 `dispatch_rows` 调用本身）

（实现陷阱：`group<N>` 是**模板成员函数**，MSVC 按两阶段查找在**定义点**解析非依赖名，
因此子相位成员**必须声明在 `group<>` 定义之前**，否则报 “未声明的标识符”。
另外 `build_s3.bat` 还会编译带 `/DTAO_NO_PHASE_TIMING` 的 `_plain` 版本，
`SubTimer` 需在 `#else` 分支提供空实现。）

### 38.2 结果（R3+R4 + fast_act，mincost=1）

| | 1 线程 ms | 8 线程 ms |
|---|---:|---:|
| `group` 总计 | 0.5888 | 0.1413 |
| **`pre`（查表 + resize）** | **0.5826（占 99.0%）** | **0.1315（占 93.0%）** |
| **`dispatch`（真正的矩阵乘）** | **0.0061** | **0.0099** |

**8 线程 token 预算（wall 0.3424 ms）：**

| 项 | ms | 占比 |
|---|---:|---:|
| **head（输出头）** | 0.1567 | 45.8% |
| **`group` 的 `pre`（查表+分配）** | **0.1315** | **38.4%** |
| `norm` | 0.0093 | 2.7% |
| `add` + 查表 | 0.0130 | 3.8% |
| **`group` 的 `dispatch`（真矩阵乘）** | **0.0099** | **2.9%** |
| 其余/记账误差 | 0.0220 | 6.4% |

> **⇒ 真正的矩阵乘只占 token 的 2.9%。**
> **而 `packed.at()` 字符串键查表 + `resize()` 堆分配占 38.4%，
> 且几乎完全不随线程数扩展（1 线程 0.5826 → 8 线程 0.1315，仅 4.4×）。**

**这就是 §35–§37 反复追查的那个「串行 40%」的真身。**

### 38.3 为什么这么贵

每 token 的 `pre` 工作量：每层 `group<4>`+`group<6>`+`group<2>` = **12 次查表 + 12 次 resize**，
× 8 层 = **96 次查表 + 96 次 resize**。

1 线程下 0.5826 ms / 96 ≈ **6.1 µs 一次**，远超「一次红黑树查找 + 一次 2 KB 分配」的合理量级（约 0.3–0.5 µs）。

**推测机制**（本轮未单独测量）：
`packed` 是约 50 个重型 `PipelineRows` 的红黑树，每个内含独立的 `q` 向量，
**树遍历会跨越多条缓存行**；8 线程同时遍历时互相驱逐，
再加上每次 `resize` 的 malloc 与**零初始化**（512 个 float 写 2 KB）。

### 38.4 预期收益

| 项 | 现状 | 若 `pre` 归零 |
|---|---:|---:|
| wall（8 线程） | 0.3424 ms | 0.2110 ms |
| tps | 2 967 | **约 4 740（+60%）** |

**这是本项目迄今找到的最大单项可优化点，且：**
- **不需要重训**
- **不改变任何数值**（`checksum` 必须仍是 259）
- 改动局部、可回退

### 38.5 下一轮的具体做法

**方案 A：预解析指针表。**
模型构造/首次调用时，把每层每组需要的 `PipelineRows*` 解析进数组（如
`std::array<const PipelineRows*, 12> layerPtrs[8]`），热路径只做数组下标，
彻底消除 `packed.at()`。

**方案 B：输出缓冲复用。**
`group<>` 的 `out[i]` 改为写进**预分配并复用的缓冲**（每线程一份，避免竞争），
消除 96 次/token 的 `resize`+零初始化。

**验收标准**：`PRELOOKUP` 的 `pre` 从 0.1315 ms 降到 0.02 ms 以下，
端到端 tps 提升，**且 `checksum` 仍为 259**。

**纪律不变**：同一二进制内交错 A/B 取中位数；`config_dump()` 自证；每步写入本文档。



## 三十九、**§38 的结论是插桩 bug 造成的假象**；真因是带宽（2026-09-11 续）

### 39.1 先做合理性检验，发现 §38 反了

§38 报出「`dispatch`（真矩阵乘）1 线程仅 0.0061 ms」。但 group<4> 的
`p.rows == c.s == 128`，工作量 = 128×(512+128+512+128) = **163 840 MAC**，
1 线程按 2 MAC/周期、4.2 GHz 下限也要 **19.5 µs**。

> **实测比理论下限快 3 倍 —— 不可能。⇒ §38 的拆分点有 bug。**

**原因**：`{SubTimer _tp(ms_pre);` 打开的 scope **一直没关闭** ——
第 131 行的 `}` 关的是 `for` 循环，下一个 `}` 已经是 `if(fast)` 的。
**⇒ `pre` 把 `dispatch_rows` 也算了进去，`pre` 与 `dispatch` 完全颠倒。**
**§38.2/§38.4 的「查表+分配占 38%、预期 +60%」全部作废，予以撤回。**

（顺带修掉一个**第 14 轮插桩引入的多余右括号**：它把 `if(fast)` 提前关闭，
使 `dispatch_rows` 变成无条件执行、第 161 行的标量回退不可达。
因 `bool fast=true;` 恒真，数值上从未暴露。）

### 39.2 修正后的 `group<>` 拆分

| | 1 线程 ms | 8 线程 ms | 扩展比 |
|---|---:|---:|---:|
| `group` 总计 | 0.6041 | 0.1605 | 3.76× |
| **`pre`（查表 + resize）** | 0.0138 | **0.0112** | 1.24× |
| **`dispatch`（真正的矩阵乘）** | **0.5902** | **0.1494** | **3.95×** |

**⇒ 查表+分配只占 token 的 3.2%，可以忽略。
真正的矩阵乘分发占 43%，且只扩展 3.95×。**

### 39.3 屏障开销：实测 0.505 µs，**杠杆①不是答案**

新微基准 `microbench_dispatch.cpp` 用**空 lambda**测纯 fork-join 开销：

| 线程 | spin 空分发 µs | sleep 空分发 µs |
|---|---:|---:|
| 1 | 0.042 | 0.044 |
| 2 | 0.217 | 0.486 |
| 4 | 0.345 | 9.883 |
| **8** | **0.505** | **15.195** |

**自旋 0.505 µs，睡眠 15.195 µs** —— 后者正好印证池头文件注释里
「at ~32 dispatches per token the sleep path costs ~15 us per barrier」。

> **每 token 约 25 次分发 × 0.505 µs = 12.6 µs，仅占 token 的 3.6%。**
> **⇒ 屏障不是瓶颈；目标里的杠杆①（分发融合）收益上限只有约 3.6%。**
> （这也与 §35 的 mincost 扫描「1→16384 平坦」一致。）

**所以 §39.2 中 `dispatch` 的串行分量 0.0864 ms 不是屏障，而是矩阵乘本身扩展不动。**

### 39.4 真因：带宽已饱和

`microbench_bandwidth.cpp`，256 MB 流式读：

| 线程 | 1 | 2 | 4 | 8 |
|---|---:|---:|---:|---:|
| GB/s | 24.55 | 36.34 | 40.11 | **43.18** |

**带宽只扩展 1.76×（单线程已拿到 24.55 GB/s）。**

而模型当前需求（微基准自身记账）：

```
R3+R4 (2 Full + 6 Reuse)   14.68 MB/token x 3209 tps = 47.11 GB/s
```

> **需求 47.11 GB/s > 实测可达 43.18 GB/s ⇒ 当前已处于带宽受限。**

**这同时解释了矩阵乘为何只扩展 3.95×**：工作集 11.73 MB 部分命中 L3（16 MB），
所以略好于纯流式的 1.76×，但远达不到 8×。

### 39.5 结论：杠杆③（字节缩减）才是主线

**每 token 流量构成：输出头 8.39 MB（57%）+ 层权重 6.29 MB（43%）。**

| 动作 | 每 token 字节 | 3209 tps 时带宽 | 判断 |
|---|---:|---:|---|
| 现状 | 14.68 MB | 47.11 GB/s | **已超上限** |
| **2-bit 打包三元权重** | **3.67 MB** | **11.78 GB/s** | 远离上限，理论 4× 空间 |

**⚠ 但注意**：§早先的 bit-plane 2-bit 端到端实测只有 0.98–0.99×。
**原因是那个内核用指令换带宽，净收益抵消。**
⇒ **正确的做法是「减字节**且**不显著增加指令数」**，而不是单纯打包。

### 39.6 下一轮的候选（按预期收益排序）

1. **输出头字节缩减**（8.39 MB，占 57%）。优先考虑**在不改变算子语义的前提下**
   降低 head 权重的存储宽度，并保持 VNNI 可用。
2. **重新审视 2-bit 打包**：这次的目标是**带宽**而非算力，
   要在带宽已饱和的背景下重测；若内核指令数增加不超过约 2×，理论上应转为正收益。
3. **验证带宽假说**：把 head 换成一次不读权重的占位实现，
   看吞吐是否按字节比例上升（这能直接证伪/证实带宽受限）。

**⚠ 上述 3 条已被 §40 否证，见下。**

## 四十、**§39 的「带宽受限」被否证**：字节相同而吞吐差 1.48×（2026-09-11 续）

### 40.1 先自查 §39：一个对不上的数字

§39 用「需求 47.11 GB/s > 实测 43.18 GB/s」判定带宽受限。但同一份数据里：

- R0（8 层独立）21.76 MB/token → 990 tps = **21.5 GB/s**
- R3+R4 14.68 MB/token → 3209 tps = **47.1 GB/s**

**若真是 43 GB/s 带宽受限，R0 应能跑到约 1976 tps，实测只有 990。**
⇒ 两个配置的「受限类型」不同，不能用单一带宽上限解释。**该判据不成立。**

### 40.2 层数扫描：两种受限都不是

`TAO_LAYER_LIMIT=k`，8 线程，恒等共享：

| 层数 | 字节/token | tps | GB/s |
|---:|---:|---:|---:|
| 1 | 10.06 MB | 1991.3 | 20.04 |
| 2 | 11.73 MB | 1976.3 | 23.19 |
| 4 | 15.07 MB | 1813.7 | 27.34 |
| 6 | 18.42 MB | 1317.2 | 24.26 |
| 8 | 21.76 MB | 1423.5 | 30.98 |

**GB/s 不恒定（20→31），G MAC/s 也不恒定。⇒ 纯带宽或纯算力都解释不了。**

### 40.3 决定性判据：字节相同、MAC 不同

**同一二进制内交错 A/B，各 15 个样本：**

| 配置 | 读取字节 | tps 中位 |
|---|---:|---:|
| R3（共享权重，8 层全算） | 21.75 MB/token | 2 058.5 |
| **R3+R4（共享权重 + 复用 v/g）** | **21.75 MB/token（完全相同）** | **3 051.0** |

> **⇒ 读取字节完全相同，吞吐差 1.482×。**
> **【否证】§39 的「带宽受限」结论。算力才是主导。**
>
> （隐含带宽：R3 = 44.8 GB/s，R3+R4 = 66.4 GB/s —— 同一字节数对应两个不同带宽，
> 本身就说明字节不是决定量。）

**§39.4 / §39.5 的「杠杆③是主线、2-bit 打包有 4× 空间」据此撤回。**

### 40.4 但缓存足迹确实有实质影响

| 对比 | MAC 数 | 唯一足迹 | tps（8 线程） | 比值 |
|---|---:|---:|---:|---:|
| R0 vs R3 | **相同** | 13.37 → 3.34 MB | 1 415 → 2 058 | **1.45×** |

**⇒ MAC 数相同、仅减少唯一足迹，就有 1.45× 收益。**

### 40.5 当前的综合判断（待下一轮直接验证）

- **算力是主导**（§40.3）
- **缓存足迹是次主导**（§40.4）
- **屏障可忽略**（§39.3：25 × 0.505 µs = 3.6%）
- **查表/分配可忽略**（§39.2：3.2%）
- R3+R4 隐含 L3→核心流量 **66.4 GB/s**，而 DRAM 流式上限 43.2 GB/s（§39.4）——
  **66 GB/s 很可能接近本机 L3 的实际上限**，这能同时解释「算力受限」与「足迹敏感」

**⇒ 若 L3 带宽约 66 GB/s 是硬顶，矩阵乘扩展 3.95× 就说得通了：
它同时受算力与 L3 供给约束，而非单一瓶颈。**

### 40.6 下一轮：直接测「减少头部字节但不改算子语义」

**做法**：加一个**仅用于诊断**的开关 `TAO_HEAD_LIMIT=k`，把输出头的行数临时截到 k
（会改变 checksum，仅用于分离变量；默认关闭、不进生产）。

| 观察 | 结论 |
|---|---|
| tps 随 k 近似**反比**上升 | 头部带宽受限 |
| tps 随 k 变化**平缓** | 头部算力受限 |

**这是分离「头部 8.39 MB 是算力还是带宽」的最直接办法**，
能一次判定杠杆③是否值得投入。

**纪律不变**：同一二进制内交错 A/B 取中位数；`config_dump()` 自证；每步写入本文档。
**任何相位拆分的结论，先过一遍「是否快于理论下限」的合理性检验。**

## 四十一、修复潜伏 bug：内核开关从未生效；位平面大优化被否证（2026-09-11 续）

### 41.1 先修一个让此前一批测量作废的 bug

**症状**：同轮交错 A/B 测出 `TAO_VNNI=1` 相对基线只有 0.995×，
与 §32 记录的「单线程 1.965×」严重矛盾。

**根因**（早先已记录、一直未修）：四个内核开关的环境变量应用
**发生在 `packed` 表填充之前**：

```cpp
if(std::getenv("TAO_VNNI"))set_vnni(true);   // 此刻 packed 还是空的
for(auto&t:schema(c)) ... packed.emplace(...);  // 权重在这之后才装进来
```

而 `set_vnni` / `set_multi_acc` / `set_avx512` / `set_bitplane` 的实现都是
`for(auto&kv:packed){...}` —— **遍历空 map，等于什么都没做。**

> **⇒ 所有靠环境变量开启 `TAO_VNNI` / `TAO_MACC` / `TAO_AVX512` /
> `TAO_FLOAT_W` / `TAO_BITPLANE` 的端到端测试，测的都是基线。**

**已修**：把这段应用移出构造函数参数区，改为在 schema 循环**之后**执行（两个构造函数都改）。
`config_dump()` 现在能正确显示 `vnni=on` ✓。

**修复后的验证（每 token 5 轮）**：

| 配置 | 1 线程 | 8 线程 | dump |
|---|---:|---:|---|
| 基线 | ~670 | ~2 590 | `vnni=off` |
| **VNNI** | **~1 231（1.84×）** | **~2 558（0.99×）** | `vnni=on` ✓ |

**VNNI 单线程 1.84× 与 §32 记录的 1.965× 一致 ⇒ 开关确实生效了，
而 8 线程仍然只有 0.99×，与 §32 的结论一致。**

**注意**：`bench_interleaved.cpp` 是直接调用 setter 的，**它此前的结论不受此 bug 影响**；
受影响的是用环境变量开内核的那些运行。

### 41.2 大优化尝试：AVX-512 掩码加法位平面内核

**动机（定量）**：目标 10 000 tps ⇒ 100 µs/token。

| 资源 | 需求 | 本机能力 | 余量 |
|---|---:|---:|---|
| 指令 | 4.37 MAC/周期/核 | AVX2 float 约 16；VNNI 约 64 | 4–14× |
| 字节 | 217 GB/s | DRAM 43；L3 约 66 | **差 3–5×** |

**⇒ 断定「字节是硬墙」，于是实现三元权重的无损 2-bit 打包。**

**为什么这次与早先的 bit-plane 不同**：旧内核每 8 个权重需要
`sllv`+`srai`+2×`and`+`sub`+`add` ≈ 7–8 条指令 ⇒ **约 1.1 MAC/指令，与 int8 AVX2 的 1.14 持平**
——省了字节却完全没省指令。

新内核用 AVX-512 掩码加法，每 16 个权重仅 3 条指令：

```cpp
const uint32_t m = load32(o + (j>>2));          // [uint16 pos][uint16 neg]
const __m512 xv = _mm512_loadu_ps(x + j);
acc = _mm512_mask_add_ps(acc, __mmask16(m & 0xFFFF), acc, xv);
acc = _mm512_mask_sub_ps(acc, __mmask16(m >> 16),   acc, xv);
```

**⇒ 5.33 MAC/指令（比 int8 AVX2 好 4.7 倍），字节 0.25 字节/权重（好 4 倍）。**

**实现**：`PipelineRows::build_bitplane()`（每 16 权重打包成 4 字节）+ `dot_bp512()`，
由 `TAO_BITPLANE` 开启，默认关闭。**`checksum` 仍为 259（无损）✓**

**结果（同一二进制内交错 A/B，各 15 样本）**：

| 内核 | tps 中位 | 相对基线 |
|---|---:|---:|
| 基线 | 3 101.8 | 1.000× |
| VNNI | 3 087.1 | 0.995× |
| **位平面（新，AVX-512 掩码）** | **3 017.8** | **0.973×** |
| 位平面 + VNNI | 3 014.9 | 0.972× |

**（顺序测量时曾出现「位平面 +22%」的假象 —— 那一次基线恰好跑在慢时段。
同轮交错后归零。这是同一类错误的第 11 次，再次确认「同轮交错」纪律的必要性。）**

> **⇒ 【否证】位平面大优化。4 倍更少字节 + 4.7 倍更少指令，8 线程收益为零。**

### 41.3 由此确立的关键事实

把「有效」与「无效」的手段并列，结论非常明确：

| 手段 | 改变了什么 | 8 线程效果 |
|---|---|---|
| VNNI | 指令数 ÷18 | 0.99×（**无效**） |
| 位平面（新） | 指令 ÷4.7，字节 ÷4 | 0.97×（**无效**） |
| R4 复用 v/g | **MAC 数 −57%** | **1.48×（有效）** |
| R3 共享权重 | **唯一足迹 ÷4** | **1.45×（有效）** |
| fast_act | 状态更新函数变便宜 | 1.20×（有效） |
| 屏障优化 | 分发开销 | 3.6% 上限（无空间） |
| 查表/分配 | 96 次查表/分配 | 3.2%（无空间） |

> **⇒ 8 线程下，单纯提高内核效率（更少指令、更少字节）完全没有用；
> 只有减少总工作量、缩小唯一足迹才有效。**
>
> **⇒ 瓶颈既不是「朴素意义的算力」，也不是「朴素意义的带宽」。**

### 41.4 下一轮：判定「每行固定开销」假说

上面那张表与「每行固定开销主导」的假说一致：
`dot()` 是**按行调用**的，VNNI 与位平面都**没有改变调用行数**，
所以两者都无效；而 R4 直接**删掉了整批行**（6 层 × 512 行 × 2 矩阵），R3 让同一批行命中缓存。

**验证办法（一次即可判定）**：`TAO_HEAD_LIMIT=k` 把输出头行数截到 k
（诊断专用，会改 checksum，默认关闭）。

| 观察 | 结论 |
|---|---|
| tps 与 k 近似**反比** | 每行固定开销主导 ⇒ 应做**行级批处理/多行合一内核** |
| tps 对 k **不敏感** | 假说否证，需另找 |

**纪律不变**：同一二进制内交错 A/B 取中位数；`config_dump()` 自证；每步写入本文档。
**任何相位拆分的结论，先过一遍「是否快于理论下限」的合理性检验。
任何内核改动的结论，必须来自同轮交错 A/B —— 本轮已因此避免一次 +22% 的误判。**

## 四十三、【转向】从零训练的架构设计：吞吐预算（2026-09-11）

> **用户决定：不再迁就现有权重，后续从零训练。**
> 因此本目标原有的「checksum 不得变化」约束解除，可以按吞吐预算自由设计架构。
> 论文迁移判定仍以 01 号文档为准；本节的职责是**给出量化设计目标**。

### 43.1 关键测量：61% 的时间与层计算量无关

用 §24 的同轮交错数据（8 线程）：

| 配置 | 层 MAC | tps | 每 token 时间 |
|---|---:|---:|---:|
| R3（8 层全算，共享权重） | 13.37M | 1 821 | 549 µs |
| R3+R4（2 Full + 6 Reuse） | 6.29M | 2 619 | 382 µs |

两点拟合 `T = a + b × 层MAC`（两点两参数，必然精确，**需要第三点验证**）：

> **b = 23.6 µs / M MAC，a = 234 µs**

**⇒ 每 token 有 234 µs 与层 MAC 无关的固定项，占 382 µs 的 61%。**

而 §16 实测 head = **140 µs**，故**固定项中还有约 94 µs 未归因**。

**⚠ 这是本项目定位到的最终瓶颈：不是算力、不是内核效率、不是带宽，
而是「每 token 与规模无关的固定开销」。** 它同时解释了 §41.3 那张表的全部现象：
减少 MAC（R4）与减少足迹（R3）有效，而提高内核效率（VNNI / 位平面）无效——
**后者不改变固定项。**

### 43.2 反推目标架构

目标 10 000 tps ⇒ 100 µs/token；目标 14 000 ⇒ 71 µs/token。

| 项 | 现状 | 10 000 目标 | 手段 |
|---|---:|---:|---|
| 输出头 | 140 µs | **≈ 5 µs** | **两段式候选池词表头（01 号文档 #2）** |
| 其它固定 | 94 µs | **≈ 40 µs** | **待归因**（见 43.4） |
| 层计算 | 148 µs | **≈ 55 µs** | 层 MAC 减半 |

### 43.3 架构提案（待验证）

| 项 | 现架构 | 提案 | 依据 |
|---|---|---|---|
| 层数 L | 8（2 Full + 6 Reuse） | **6（1 Full + 5 Reuse）** | 层 MAC 与 Full 层数近似线性 |
| d | 512 | **448 ~ 512** | 层 MAC ∝ d 左右 |
| 状态 s / m | 128 / 512 | 不变 | 不变量 I1 的形态 |
| **输出头** | **16384 × 512 = 8.39M MAC** | **两段式** | 见下 |
| 词表 V | 16 384 | 不变 | 由语料决定 |

**两段式词表头**（论文 Hierarchical Sparse Indexer 的迁移）：

| 阶段 | 规模 | MAC |
|---|---:|---:|
| 阶段 1：簇心打分 | G = 512 簇 × d_c = 128 | 0.065M |
| 阶段 2：候选簇内全维打分 | top-4 簇 × 32 = 128 token × 512 | 0.065M |
| **合计** | | **0.13M** |

**⇒ 输出头 MAC 从 8.39M 降到 0.13M（64×）。**

**训练纪律（论文原话，必须遵守）**：候选限制在**训练与推理中完全一致地施加**。
即训练时也只在候选域内算 loss，并用辅助损失训练簇心打分器把正确 token 所在簇排进 top-C。

### 43.4 必须先解决的未知：那 94 µs 是什么

**在动手设计之前必须先归因**，否则新架构会在同一个固定项上撞墙。
候选：每 token 的 8 次层循环开销、norm/add 粘合、dispatch 固定成本（25 × 0.505 µs = 12.6 µs，已排除大部分）、
状态读写、以及**未被 §37 子相位覆盖的部分**。

**做法**：把 `a` 拆开量。已有工具：§37 的 `TAO_T` 子相位计时。

### 43.5 纪律

- 本节所有数字都来自同轮交错 A/B 或已记录的相位计时，**未做任何新的探索性猜测**
- 两点拟合的 `a`/`b` **必须用第三点（例如 L=6 或 d=384 的实测）验证后才能作为设计依据**
- 架构提案中的每一项都要有对应的实测支撑

## 四十四、【定论】真正的瓶颈：层栈的 dispatch 粒度（2026-09-11）

> 本节用**可靠的量**（整 token tps、头行数扫描的线性拟合）取代了此前反复出错的相位计时器。
> **相位计时器已被证伪**：8T 时子相位之和 264.9 µs > `body_total` 200.1 µs，说明计数器重复计数。

### 44.1 头行数扫描（残差 ±5 µs，可信）

在 `noffn_fresh/step_1512`（8 线程，默认架构）：

| 头行数 | tps | µs/token |
|---:|---:|---:|
| 1 | 5 048 | 198.1 |
| 1 024 | 4 795 | 208.5 |
| 4 096 | 4 596 | 217.6 |
| 16 384 | 4 021 | 248.7 |

> **T(µs) = 202.9 + 0.002849 × 头行数**  ⇒ 头边际 46.7 µs，截距 202.9 µs。

### 44.2 纯层栈的线程扩展（头压到 1 行，整 token tps）

| 线程 | tps | µs/token | 加速比 |
|---:|---:|---:|---:|
| 1 | 3 675 | 272.1 | 1.00× |
| 2 | 3 472 | 288.0 | **0.94×** |
| 4 | 5 018 | 199.3 | 1.37× |
| 8 | 5 021 | 199.2 | **1.37×** |
| **对比：head** | | | **3.45×** |

**⇒ 层栈在 4 线程硬饱和；2 线程比 1 线程更慢。**

### 44.3 已排除的三条解释

| 假设 | 证伪方式 | 结果 |
|---|---|---|
| **L3/DRAM 带宽** | 实现真正的权重去重，足迹 20.95 MB → **11.29 MB（进 16 MB L3）** | 层栈 199.2 µs **不变**，整 token 4089 tps **不变** |
| **屏障次数** | §21 空 lambda 微基准：8T 0.505 µs × 24 = 12.6 µs | 只占 6% |
| **内核指令效率** | VNNI / AVX-512 位平面 / 2-bit 打包 | 单线程有效，8 线程全部归零 |

### 44.4 定论：每 MAC 速率由 dispatch 粒度决定

单个 4096×512 内核的多线程扩展（`microbench_kernel_scaling`）：

| 线程 | int8 G MAC/s | 2bit | AVX512 | 扩展比 |
|---:|---:|---:|---:|---:|
| 1 | 10.45 | 7.81 | 13.54 | 1.00× |
| 8 | 44.78 | 23.57 | 53.85 | **4.28×** |

**模型内两个极端：**

| | 每次 dispatch 的 MAC | 次数 | 速率 |
|---|---:|---:|---:|
| 输出头 | 8.39M | **1** | **180 G MAC/s** |
| 层栈 | 262k（均值） | **24** | **31.6 G MAC/s** |

**⇒ 相差 5.7 倍。层栈的每个 dispatch 只分到「每线程 32 768 MAC」，
小到内核无法进入稳态；而 VNNI 的输入量化又无法在这种粒度上摊薄
（实测：关掉 VNNI 层栈反而快 20 %，而头慢 2.6×）。**

**⇒ 目标杠杆①（层间串行拆解）是对的，但机理不是「屏障太贵」（3.6 %），
而是「小矩阵的每 MAC 效率只有大矩阵的 1/5.7」。**

### 44.5 顺带修复与发现的缺陷

1. **权重重复存储（真 bug）**：`layerSource` 只做了访问重映射，加载器仍存了全部 8 层。
   新增 `dropDuplicatedLayers()`，**矩阵 97 → 25，足迹 20.95 MB → 11.29 MB**。
   （R3 此前 1.45× 的收益来自「被触及」的足迹变小，不是常驻足迹。）
2. **`TAO_LAYER_LIMIT` 是死代码**：`layer_limit` 只声明和使用，从未从 env 读入 ⇒ 此前的「层扫描零斜率」是假象。
3. **checkpoint 缺失时崩溃而非报错**：以 0xC0000409 零输出退出。应修。
4. **`build/arch_A_ds3/step_150/final.dsb` 在本会话期间消失**，全部测量改用 `noffn_fresh/step_1512`。

### 44.6 达成 10 000 tps 的路径（有测量支撑）

按 60 G MAC/s 聚合速率，10 000 tps（100 µs）需要 **≤ 6M MAC/token**。

| 项 | 现在 | 目标 | 手段 |
|---|---:|---:|---|
| 输出头 | 8.39M | **0.13M** | **两段式候选池（01 号文档 #2）** |
| 层栈 | 6.29M | 6.29M（不变） | — |
| **合计** | **14.68M** | **6.42M** | |

**但只减 MAC 不够——层栈的 24 次小 dispatch 必须合并**（33 → 100+ G MAC/s）：

| 目标 | 手段 |
|---|---|
| 层栈 199 µs → **60~80 µs** | **把 24 次 dispatch 融合成 6~8 次**（mHC 式依赖错位，01 号文档 #6） |
| 头 46.7 µs → **~1 µs** | 两段式候选池 |

**⇒ 预计 70~85 µs/token ⇒ 12 000~14 000 tps，达标。**

## 四十五、§44.4 被自己的实验证伪——瓶颈指向自旋池本身（2026-09-11）

### 45.1 已实施的改动

1. **权重去重**（真 bug 修复）：`dropDuplicatedLayers()`，矩阵 97 → 25，足迹 20.95 → **11.29 MB**（进 16 MB L3）。
   **吞吐不变** ⇒ **证伪「L3/DRAM 带宽」假设。**
2. **层栈 dispatch 融合**（01 号文档 #6，mHC 式依赖错位）：
   - 泛化 `group<N>` 使组内各矩阵可有不同 rows（原先强制 `p.rows==rows`，导致 s(128) 与 m(512) 无法合并）
   - m 分支改读本层更新前的 s，消除 s→m 串行依赖
   - 每层 dispatch 数 **3 → 2**
   - 开关 `TAO_FUSE_SM`（默认开）

### 45.2 实测结果：融合无效

| | tps | µs |
|---|---:|---:|
| 融合 ON（默认） | 3 914 | 255.5 |
| 融合 OFF | 3 950 | 253.2 |
| **比值** | **0.991×** | n=20/20 同轮交错 |

纯层栈：4T 197.5 µs / 8T 206.3 µs —— **仍卡在 4 线程。**

> **⇒ §44.4 的「每 MAC 速率由 dispatch 粒度决定」被证伪。
> 把 3 次 dispatch 合成 2 次、并让单次 MAC 量变大，完全没有改善。**

### 45.3 关键矛盾：模型比裸内核单线程快、多线程慢

| | 1 线程 | 8 线程 | 扩展比 |
|---|---:|---:|---:|
| 微基准内核（4096×512，裸 `std::thread`） | 10.45 G MAC/s | **44.78 G MAC/s** | 4.28× |
| **模型层栈（走自旋池）** | **23.1 G MAC/s** | **31.6 G MAC/s** | **1.37×** |

**单线程：模型 23.1 > 微基准 10.45（VNNI 的功劳，符合预期）。**
**8 线程：模型 31.6 < 微基准 44.78 —— 模型的并行路径反而更差。**

**⇒ 瓶颈既不在内核、也不在字节、也不在 dispatch 次数，
而在 `CpuRowParallelPool` 的并行路径本身。**

### 45.4 下一步的假设（待验证，不得当结论用）

- `run()` 每次 dispatch 都取 `std::lock_guard<std::mutex> caller(callers_);`
- 自旋路径每次：写 slots → `spin_gen_.fetch_add(release)` → 调用方自算 1/n → 自旋等 `spin_done_==workers_used`
- **调用方承担 1/n 的工作，同时还要负责扇出与栅栏** ⇒ 调用方是关键路径
- 需验证：把整条层栈的 dispatch 折叠成**一次**（用一个 dispatch 跑完 8 层）能否恢复扩展比

**在验证之前，不得再基于「粒度」做任何优化。**

### 45.5 纪律记录

本轮两个假设（带宽、粒度）都是**我自己的实验直接证伪**的。
§44.4 的结论已被本节推翻，**该节的「44.6 路径」随之作废**，只剩两段式词表头一项仍然成立
（它减的是绝对 MAC 量，与并行无关）。

| 4 | 53.84 | 54.33 | 0.991× |
| 8 | **63.36** | 62.60 | 1.012× |

**⇒ 自旋池与裸线程在全部线程数下相差 ≤1 %。池不是瓶颈。§45.4 假设作废。**

### 46.2 同一份数据给出的新事实

- **512×512 负载在 8 线程可达 63.36 G MAC/s**（1T 14.12 → 4.49×，这就是本机该尺寸的实际上限）
- **模型的层栈只有 31.6 G MAC/s** —— 矩阵形状相同、线程数相同，**差 2 倍**

**⇒ 缺口在 `group<>` 的 dispatch 体内部**，候选（按嫌疑排序）：

1. **VNNI 的 `quantize_input` 在调用线程上串行执行，每个矩阵一次**
   （实测：关掉 VNNI 层栈反而快 20 %，而头慢 2.6× —— 与此一致）
2. 逐行 `p.dot(r, x)` 的函数调用与行内开销（微基准是内联的整行循环）
3. dispatch 之间的串行胶水：norm / add / gated_update

### 46.3 本轮累计证伪的三个假设

| 假设 | 证伪实验 | 结果 |
|---|---|---|
| L3/DRAM 带宽 | 权重去重 20.95 → 11.29 MB | 吞吐不变 |
| dispatch 粒度 | s/m 融合，每层 3 → 2 次 | 0.991× |
| 自旋池并行路径 | 池 vs 裸线程 | ≤1 % 差异 |

**三个都是我自己提出、又用实验直接推翻的。**
每次证伪都缩小了范围：现在只剩「dispatch 体内部」这一个方向。

### 46.4 下一步（唯一剩余方向）

在**模型内实测**（而非微基准）dispatch 体的三个候选：
- 用 `TAO_VNNI=0` 与 `TAO_FLOAT_W` 等已有开关做同轮交错 A/B，看层栈的每 MAC 速率
- 若确认是 `quantize_input`，则把量化改为**每 token 一次**（输入向量在整层栈中不变的部分可复用），
  而不是每个矩阵一次

**在定位到具体项之前，不再做任何结构性改动。**

## 四十七、定位到 dispatch 体内部：VNNI 按矩阵规模分档（+21%）（2026-09-11）

### 47.1 纯层栈的内核路径同轮交错 A/B（8 线程，头压到 1 行）

| 配置 | tps | µs/token | 相对 |
|---|---:|---:|---:|
| 默认（VNNI 全开） | 4 753 | 210.4 | 1.000× |
| **VNNI=0** | **6 143** | **162.8** | **1.293×** |
| AVX512=1 | 4 786 | 209.0 | 1.007× |
| VNNI0+AVX512 | 5 448 | 183.5 | 1.146× |
| FLOAT_W=1 | 3 511 | 284.9 | 0.739× |

**⇒ VNNI 在层栈上是净损失 29 %**（29.9 → 38.6 G MAC/s）。
机理：`quantize_input` 在**调用线程上串行**执行，且每个矩阵一次；
层内矩阵只有 128×128 ~ 512×512，这点开销摊不薄。
而输出头在 VNNI 上是 **2.6× 收益**（实测 head 相位 124.2 → 47.5 µs）。

**⇒ 结论：VNNI 应按矩阵规模分档，不是全局开关。**

### 47.2 实施

`set_vnni` 改为按 `rows*cols >= 1e6` 分档：

```cpp
p.vnni_=v&&size_t(p.rows)*size_t(p.cols)>=1000000u;
```

阈值 1e6 使**只有输出头（16384×512 = 8.39 M）达标**，
层内最大矩阵（512×512 = 262 k）不达标。

### 47.3 实测（同轮交错，8 线程）

| | tps | µs/token |
|---|---:|---:|
| **分档 VNNI（头开层关）** | **4 913** | **203.5** |
| VNNI 全关 | 3 496 | 286.1 |
| 对照：改动前（VNNI 全开） | ≈4 050 | ≈245 |

**⇒ +21 %。** 纯层栈 160.2 µs（改动前 210 µs）。
`FLOAT_W` 是 0.739×，确认「权重展开为 float32」是死路（§死路清单一致）。

### 47.4 数值影响

VNNI 会把输入量化到 int8，层内改走精确 float 路径后**数值比改动前更准**，
但输出会变（checksum 变化）。这与「从零训练」的既定方向一致，不作回退。

### 47.5 剩余差距

| | 现在 | 目标 |
|---|---:|---:|
| 整 token | **203.5 µs（4 913 tps）** | 100 µs（10 000 tps） |
| **还差** | | **2.04×** |

**已定位的两个剩余项：**

1. **层栈 39.3 G MAC/s vs 同形状微基准 63.4 G MAC/s（差 1.61×）**
   微基准内核是内联的整行 AVX2 循环；模型是逐行 `p.dot(r,x)` 调用，
   且 int8→float 转换比 float 加载多 2 条指令/8 元素。
2. **输出头 46.7 µs**（VNNI 已开，仍然是单次 8.39 M MAC 的 dispatch）
   → 两段式候选池可砍到 ~0.13 M MAC（01 号文档 #2，尚未实施）

**两项都做，预计 203.5 → ~110 µs ⇒ ~9 000 tps；再叠加层内核的 1.61× ⇒ 达标。**

## 四十八、内核指令数也被证伪——只剩「每次 dispatch 的固定开销」（2026-09-11）

### 48.4 剩余假设：`group<>` 每次 dispatch 的固定开销

`group<N>` 每次调用（每 token 共 ~16–24 次）都在做：

for(i<N){ const auto& p=packed.at(names[i]);   // std::map<std::string,...> 树查找 + 字符串比较
          out[i].resize(rows); }                // 每个输出向量一次堆分配

**在此之前不再改内核。**

## 四十九、【重大】层栈只占 4%——存在 165.6 µs 的每 token 地板（2026-09-11）

### 49.1 修好死代码后拿到的层数扫描

`TAO_LAYER_LIMIT` 此前是死代码（`layer_limit` 从未从 env 读入）。修好后
（`limit=1` 时 checksum 变为 0，证明生效），头压到 1 行，8 线程，同轮交错：

| 层数 | tps | µs/token |
|---:|---:|---:|
| 1 | 6 064 | 164.9 |
| 2 | 5 924 | 168.8 |
| 4 | 5 872 | 170.3 |
| 8 | 5 799 | 172.4 |

> **T(µs) = 165.6 + 0.9 × 层数**（残差 −1.7 / +1.3 / +1.0 / −0.6 µs）

**⇒ 每层边际成本只有 0.9 µs；8 层合计 7.2 µs，占整个 token 的 4 %。**

**⇒ 存在一个 165.6 µs 的每 token 地板，且它与会话中所有其他量都无关。**

### 49.2 地板不是仪表

| 配置 | 仪表版 µs | plain 版 µs |
|---|---:|---:|
| 层 1 头 1 | 172.7 | **168.3** |
| 层 8 头 1 | 171.3 | 164.8 |
| 层 1 头全 | 231.9 | 299.4 |
| 层 8 头全 | 219.4 | 302.9 |

**⇒ `/DTAO_NO_PHASE_TIMING` 的 plain 版地板同样在 168 µs。不是仪表。**

### 49.3 这推翻了本会话此前的一切结论

- §43 的「每 token 234 µs 固定项」= 这个地板
- §44 的「截距 202.9 µs」= 这个地板
- §44.4 的「层栈每 MAC 效率只有头的 1/5.7」= **其实是头(46.7 µs) 与地板(165.6 µs) 的对比，与层栈无关**
- **所有架构 A/B（R3 / R4 / fast_act / VNNI / 位平面 / 融合）测出的差异，都叠加在这个地板之上**

**修正后的真实账（8 线程）：**

| 项 | µs/token |
|---|---:|
| 8 层 | **7.2** |
| 完整输出头 | **46.7** |
| **模型合计** | **≈ 54** |
| **地板** | **≈ 166** |
| 实测总计 | ≈ 220 |

**⇒ 若地板消失，模型自身是 54 µs/token ⇒ 18 500 tps，已超过 14 000 的目标。**

### 49.4 已排除的地板候选（本轮五个假设全部证伪）

| # | 假设 | 证伪实验 | 结果 |
|---|---|---|---|
| 1 | L3/DRAM 带宽 | 权重去重 20.95→11.29 MB | 不变 |
| 2 | dispatch 粒度 | s/m 融合，每层 3→2 | 0.991× |
| 3 | 自旋池并行路径 | 池 vs 裸线程 | ≤1 % |
| 4 | 内核指令数 | alpha 外提 + FMA，−29 % 指令 | 0.995× |
| 5 | `std::map<std::string>` 查找 | `microbench_string_map` | **6.9 µs/token = 2.98 %** |

### 49.5 下一步（唯一正确的方向）

**不要再优化模型。先找出这 165.6 µs。**

方法：在 `greedy_step` 内部二分计时 —— `recurrent` 单独 vs `recurrent + greedy_head_observe`，
再与一个空循环对照。已知：
- `recurrent` 在 limit=1 时只跑 1 层
- `greedy_head_observe` 在 head_limit=1 时只算 1 行（`dispatch(1,512,...)` 走串行路径）

**两者都不可能花 165 µs。所以地板在 `greedy_step` 之外、或被重复计入。**

⚠ **在找到它之前，本会话关于「层栈是瓶颈」的全部中间结论都已作废。**

## 五十、【撤回 §49】基准 bug 修好后的第一个有效层扫描（2026-09-11）

### 50.1 §49 作废——第三次栽在同一个地方

`benchmark_noffn_s3.cpp` 第 109 行：

```cpp
for(int k=0;k<n;++k){ ... model.set_layer_limit(0); ... }   // 无条件清零
```

**基准在每次线程配置前把 `layer_limit` 显式清零**，我设的 `TAO_LAYER_LIMIT` 被抹掉。
⇒ §49 的「层扫描」四次测的是同一配置，`0.9 µs/层` 是噪声，`165.6 µs 地板` 就是 8 层本身。

> **任何"某个开关没效果"的结论，必须先证明开关真的生效**（用 checksum 变化或 config_dump），

**⇒ 差 1.61×，且单层即如此 ⇒ 与层间串行无关，是每层的 dispatch 结构。**

| 层数 | tps | 是否需要改架构 |

| 2 | 17 195 | |

**⇒ 单纯把深度从 8 降到 4，就是 11 934 tps（2.06×），已经超过 10 000 的目标。
再加两段式词表头可达约 10 600 tps 且更稳。**

这**正是 `06-capability-roadmap.md` §四 C3 早就写明的**：

> **这是本项目唯一能同时提高速度与保留质量的旋钮**（少算层数 = 少读权重）
> 做法：训练期随机丢弃 Reuse 层（让它对「少用几层」鲁棒），部署时 8/6/4 层三档
> 前置条件：C3 依赖 03 号文档的层维复用（有 Reuse 层才谈得上丢）—— **该前置条件现已满足（R3/R4 已固化）**

**⇒ 正确路径不是继续优化内核，而是：**
1. **训练期随机丢弃 Reuse 层**（doc 06 C3），使部署时 4/6/8 层三档都保持质量
2. **两段式候选池词表头**（doc 01 #2），把 46.7 µs 降到 ~1 µs
3. 部署默认取 **4~6 层**

**内核层的 1.61× 差距（38.8 vs 63.4 G MAC/s）留作后续，不是达标的必要条件。**
