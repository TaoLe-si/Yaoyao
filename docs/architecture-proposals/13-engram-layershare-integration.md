# 13 · Engram + 层维复用的整合设计（夭夭版）

> 本文把 03 号（层维复用）与 04 号（Engram 条件记忆）两份建议书**合并成一个架构**，
> 并回答一个它们各自没回答的问题：**这两件事对"泛化"是加分还是减分。**
>
> **一句话结论**：它们在**吞吐**上是互补的（一减稠密字节、一加稀疏容量），
> 但在**夭夭当前的数据规模上，Engram 对泛化的收益预计为零**——
> 这是论文自身的判据可证伪的预测，不是我的猜测。本文给出可判定的实验。

---

## 一、论文原文事实（已核对，V4.1 技术报告）

### 1.1 Engram（§2.4.2 / §3.1.3）

| 项 | 论文值 |
|---|---|
| 定位 | **conditional memory module**，把「记忆」与「计算」解耦 |
| 设计要素 | tokenizer 压缩、**多头哈希**、**上下文感知门控**、多分支融合 |
| 相对原始 Engram 的两处修改 | ①去掉短因果卷积（收益不值复杂度）②嵌入用**动量 + Sinkhorn 平衡**更新 |
| 规模 | 196B 参数，**2 个模块** |
| N-gram 阶数 | **{2, 3, 4}** |
| 哈希头 | **8**，每阶总维 **2048**（⇒ 每头 **256** 维） |
| 每头表长 | **约 16M 项**，各表取**互不相同的素数** |
| 精度 | 嵌入表与 key/value 投影均 **FP8** |
| 放置层 | **第 1 与第 14 层**（0-indexed），为均衡各流水级显存 |
| 关键性质 | **"lookup indices depend solely on the input token sequence"** —— 地址确定性，故可后台 RDMA 预取 |

**参数核对**：3 阶 × 8 头 × 16M 项 × 256 维 = 98.3B/模块，×2 = **197B ≈ 论文的 196B** ✓
（这反过来说明"总嵌入维 2048"指的是 8 头合计，每头 256。）

### 1.2 层维复用（§2.3.1）

CSA2 沿**三个可乘维度**压缩 KV 与注意力计算：条目大小（GQA/MLA）、序列维（压缩）、**层维**。
每层**静态指派**三种模式之一：

| 模式 | 本层自算 | 复用上层的 |
|---|---|---|
| **Full** | main KV、indexer K、Top-K 索引 | — |
| **Reindex** | 重新打分产生 Top-K | main KV、indexer K |
| **Reuse** | 仅 main Q + SWA KV | main KV、indexer K、**Top-K 索引** |

两条设计纪律：**缓存共享与选择复用解耦**；**静态指派**（无运行时路由，训练/推理路径一致）。
收益：Reuse 层前填只需 **15 个 kernel**、解码 **11 个**。

## 二、为什么不能逐字移植（诚实标注）

| 论文机制 | 夭夭现状 | 结论 |
|---|---|---|
| KV cache、indexer K、Top-K 索引 | **无注意力、无 KV cache**（不变量 I3：固定状态） | **"Reindex" 没有对应物**；只能迁移"层维复用的思想"，不是移植 |
| Engram 16M 项/头 | 语料仅 **3,217** 个不同 3-gram | 表规模需按本项目重定 |
| FP8 嵌入表 | 三值 + 行缩放（不变量 I2） | 表单独一套量化，见 §四 |

**因此本设计的两条线都是"思想迁移"**，与 03 号文档的标注一致。

## 三、核心判断：Engram 在夭夭当前规模上**不会**改善已实测的泛化缺陷

### 3.1 已实测的缺陷是什么

| 缺陷 | 实测（`bench_v1` 前身 / 长度扫描） | 性质 |
|---|---|---|
| 列表复制 | 2 项 50% → 3 项 33% → **≥4 项 0%**；元素部分取回但**顺序崩、塌回高频先验** | **从当前上下文读出这个具体实例** |
| 事实绑定 | 交叉 13/18；held-out 非颜色喜好 0/6 | 同上：绑定**当前上下文里的新组合** |

### 3.2 Engram 为什么救不了它

Engram 的键 = **输入 token 的 n-gram 哈希**（地址只依赖 token id，§1.1）。
对一个固定 n-gram，查出来的是**训练中学到的一张固定向量**。

- 列表复制：`苹果、香蕉、` 在语料里后面接过几十种不同元素 →
  学到的向量是这些续接的**平均**，**无法**指向"本例中真正跟着的那个"。
- 事实绑定：`名字叫小何，我喜欢` 在语料里对应 **361 种**不同配对 → 同样无法消歧。

**这不是实现问题，是寻址方式的必然结果。** 要救这两项，需要的是**内容寻址**（按当前上下文的值检索），
而 Engram 按定义是**静态寻址**——这正是它能预取的原因，也是它救不了复制的原因。

### 3.3 那 Engram 在本项目还有意义吗——有，但**条件性**

Engram 的价值 = **在不拖慢解码的前提下增加记忆容量**。
其价值随**语料规模**增长，而夭夭现在**没有记忆压力**：

| 量 | 值 | 含义 |
|---|---:|---|
| 训练 position 数 | 37,736 | 全部 n-gram 实例约 11 万 |
| 去重 n-gram（2/3/4-gram） | 1,726 / 3,217 / 4,581 | 合计 **9,524** |
| 稠密参数 | 21.76 MB / 13.37 M 元素 | **足够背下这 9,524 个 n-gram 若干遍** |

**所以：当前规模下 Engram 是纯成本、零收益；它的收益要等语料规模上来才出现。**
我在前几轮已实测：语料从 probe2 的 **19 篇** 增到 probe3 的 **361 篇**，
同一个未改动算子的绑定率从 **0/18 变成 10–16/18**。**数据量是本项目唯一被证实的巨大杠杆。**

**建议的取舍**：Engram 作为**语料扩容的配套**引入，而不是作为当前的泛化手段。
若现在就要做，本文 §六 给出一个**能在当前规模上给出确定结论**的实验。

## 四、整合设计

### 4.1 总图

```
输入 token ids ──┬──> [Engram 查表] ── 门控 ──> 注入第 1 层
                 │      (键只依赖 token id；确定性；可预取)
                 └──> 骨干 8 层，静态指派 2 组 × (1 Full + 3 Reuse)
                              Reuse 层复用组内 Full 层的输入投影/递归矩阵
```

**这正是 Engram 的原始动机**：稠密骨干变小并被共享（减字节），记忆交给稀疏表（加容量）。

### 4.2 两条线的具体参数（按夭夭规模重定）

**线 A — Engram（首版）**

| 项 | 值 | 依据 |
|---|---|---|
| 放置层 | 第 1 层 | 04 号 §3.2 首版 |
| N-gram 阶数 | {2, 3} | 同上（论文用 {2,3,4}） |
| 哈希头 | 4 | 同上 |
| 每头表长 | 2^18 = 262,144 行 | 04 号首版；对 3,217 个 3-gram 是 **81×** 余量（碰撞极罕见） |
| 条目布局 | 4 头 × dim16 int8 = **64 B**，交错存放 | 04 号 E1：一个 n-gram = 一条 cache line |
| 表大小 | 2 阶 × 2^18 × 64 B = **33.5 MB** | 04 号首版 |
| 门控 | `g = sigmoid(W_g [x_norm; e])`，残差加 `g ⊙ (W_o e)` | 04 号 §3.2；**必须上下文相关**，否则退化为静态查表 |
| 优化器 | Nesterov 动量 + Sinkhorn 平衡，**只更新本步被访问的行** | 论文 Algorithm 1；K=11, τ=1e-3, ε=1e-20, γ=0.18 |

**线 B — 层维复用（R3）**

| 项 | 值 |
|---|---|
| 分组 | 2 组 ×（1 Full + 3 Reuse）；层 0/4 为 Full，层 1–3、5–7 为 Reuse |
| 组内共享 | 输入投影 + 递归矩阵 + 读出投影（**层间权重完全共享**） |
| 唯一元素数 | 3,342,336（现状 13,369,344） |
| 常驻 int8（含 embedding 8.39 MB） | **11.74 MB** ← 进 16 MB L3 |

### 4.3 算子与产物

- 新算子 id：`dual-state-5-noffn-engram-layershare-r3`
- **schema 必须显式表达**：表长/阶数/头数/放置层/分组/共享关系
- 表走**独立文件 + mmap**，DSB 只存 backbone（04 号 §四）
- **旧产物一律不可复用**（不变量 I5）

### 4.4 必须同步的路径（不变量 I4 的代价）

| 路径 | 文件 | 说明 |
|---|---|---|
| CPU 推理 | `greedy_pipeline_grouped_model.hpp` | **我的全部评测都跑在这里**——不做这条线，训练出来的东西我测不了 |
| 训练前向/反向 | `train_yaoyao_graph_gpuval.cu` | 稀疏梯度：记录 (row, grad)，backbone 反向后 scatter |
| CUDA 批处理 tape | `batch_tape.cuh` | 与 I4 一致 |
| 序列化 | `dual_model_bundle.hpp` | 共享张量只存一次 |

**工程上最大的两处**：①大表的稀疏梯度与稀疏更新；②共享组的梯度必须**累加到同一 master buffer**（03 号 §四第 5 条），否则要么编译期报错、要么静默只更新最后一个使用者。

### 4.5 学习率

共享组有效梯度 ≈ 组内层数之和（4 层）→ 更新幅度近似 ×4。
**必须按组内层数缩放 lr**，并写入日志（03 号 §四第 6 条）。

## 五、消融矩阵

**必须先跑"有没有"的判定，再跑调参。**

| 轮 | 变量 | 对照 | 判据 |
|---|---|---|---|
| **B0** | 基线：层维复用 R3，无 Engram | — | NLL / `bench_v1` |
| **B1** | R3 + Engram | B0 | **训练 n-gram NLL** 与 **held-out n-gram NLL 分开报** |
| B2 | 关掉 Engram 门控（退化为静态查表） | B1 | 门控是否真的在起作用 |
| B3 | 表长 2^14 / 2^18 | B1 | 表长是否有影响（碰撞假说） |
| B4 | 共享组 lr 缩放 1.0 / 0.5 / 0.25 | B0 | 训练稳定性 |
| B5 | 组大小 2 vs 4 | B0 | 容量-速度曲线 |
| B6 | 无层维复用 + Engram | — | 分离两条线的贡献 |

### 5.1 B1 的判据（这是本设计的核心可证伪点）

论文自己点名的失败模式：**表可以"背下"训练语料而验证集无收益**（04 号 §五）。
因此 B1 必须**分开报两组数**：

| 指标 | 若 Engram 真有效 | 若只是背下来 |
|---|---|---|
| 训练 n-gram 上的 NLL | 明显下降 | 下降 |
| **held-out n-gram 上的 NLL** | **同样下降** | **不降** |
| `bench_v1` 的 `E_list` / `F_repeat` | 不变（§3.2 预测） | 不变 |

**我的预测**：held-out n-gram 不降。若如此，则在本项目当前数据规模上 Engram 的价值被证伪，
结论应在**扩容语料之后**重测，而不是继续调表长。

## 六、落地顺序（每步都能独立止损）

| # | 步骤 | 产出 | 止损点 |
|---|---|---|---|
| 1 | ~~**纯 CPU 查表微基准**~~ **✅ 已完成** | `build/microbench_engram_lookup.exe`：2 GB 表仅 **85.9 ns/token**（无预取）；预取增益 1.05–1.13×；大页零收益 | **未触发止损**。原"预取是先决条件"的判断被推翻，见 04 号 §二修正 |
| 2 | **CPU 前向原型**（随机初始化） | 每 token 字节数与 token/s 增量 | 增量 >5% 则放弃大表路线 |
| 3 | **层维复用 CPU-only 提速验证**（03 号 §六 缓解措施） | 用脚本把现有 DSB 的 Reuse 层权重替换为组内 Full 层权重，先测速度 | 速度无收益则不做训练侧 |
| 4 | **训练接入 + B0/B1 对照** | held-out n-gram NLL 分组报告 | 见 §5.1 |
| 5 | 放量（表长 / 第二模块 / 组数） | — | 仅在 4 通过后 |

**第 1 步的实测结果（改变了后续风险画像）**：

| 表规模 | 无预取 | 软件预取 | 预取增益 |
|---|---:|---:|---:|
| 32 MB | 42.8 ns/token | 40.7 | 1.05× |
| 512 MB | 73.1 | 66.3 | 1.10× |
| 2 GB | 85.9 | 76.3 | 1.13× |
| 2 GB + 大页 | 87.7 | 79.9 | 1.10× |

- **每 token 成本比 04 号原估低 30–50 倍**（86 ns vs 2.4 µs）→ 相对 CPU 解码（约 ms/token）占比 **约 0.01%**，表规模**不是**约束。
- **预取从"先决条件"降级为优化项**，大页从 E4 硬性规范降级为可选项 → **实现门槛降低**。
- 因此**表长度可以直接取大**（碰撞假说 B3 更可能被排除），重心应移到 §5.1 的能力判定上。

**第 3 步值得优先**：它不需要动训练侧，能在几小时内判定层维复用值不值得做。

## 七、与不变量的相容性核对

| 不变量 | Engram | 层维复用 | 判定 |
|---|---|---|---|
| I1 无 FFN | 查表 + 门控，不是 FFN | 不涉及 | ✓ |
| I2 三值 + 行缩放 | 表单独一套 int8/FP8 量化（**例外，须登记**） | 共享张量仍三值 | ⚠ 需显式记录例外 |
| I3 固定状态、无 KV | 查表无状态 | 复用权重，非激活 | ✓ |
| I4 训练/推理同算子 | **必须**同步 CPU 路径 | **必须**同步四条路径 | ⚠ 主要工作量 |
| I5 产物身份 | 新算子 id + 表独立文件 | 新算子 id + schema 显式共享关系 | ✓ |

## 八、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **Engram 无用**（最可能） | 见 §3.3：当前规模无记忆压力 | §5.1 的 held-out n-gram 判据直接判定，不靠感觉 |
| **层维复用降容量** | 8 层只剩 2 份独立参数 | B5 组大小消融；先做短训练看曲线是"平移"还是"变平" |
| **共享组梯度冲突** | 4 层梯度累加后可能互相抵消 | lr 缩放 + 分组梯度范数监控 |
| **实现面广**（最确定） | schema/manifest/CPU/CUDA/训练器五处联动 | §六 分步止损，第 3 步不动训练侧 |
| **表与三值体系的例外扩散** | 一旦表用 int8，I2 不再全局成立 | 例外写入算子 id 与文档，检查器按算子分支 |
