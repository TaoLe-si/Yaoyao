# 层维复用建议书（CSA2 语义的夭夭版）

> 一句话：论文在**条目大小 × 序列维 × 层维**三个可乘维度上压缩；夭夭的条目大小（2 bit/元素）与序列维（0 字节 KV）都已到极限，**唯一完全没用过的是层维**。层维复用是本报告里唯一能直接减少 CPU 每-token 字节的机制，而 CPU 解码正是字节受限（见 02 号文档）。

---

## 一、论文依据（转述）

CSA2 用**静态指派**的三种模式跨层复用：

| 论文模式 | 复用对象 |
|---|---|
| Full | 本层自算 main KV、indexer K、Top-K 索引 |
| Reindex | main KV 与 indexer K 复用最近 Full 层，但**重新打分**（选择随层变化） |
| Reuse | main KV、indexer K、Top-K 索引全复用，本层只算 main Q + SWA KV |

关键设计纪律有两条：**缓存共享与选择复用被解耦**；**静态指派**（不做运行时动态路由，训练与推理路径完全一致）。V4.1 的指派模板：encoder 3 组 ×（1 Full + 5 Reuse）、decoder 5 组（1 组 Full + 4 组 Reindex，每组后 3 层 Reuse）。

> **诚实标注**：夭夭没有 KV、没有索引器，因此**不存在「Reindex」的对应物**。下面是把「层维复用的思想」迁移成权重/中间量共享，不是 CSA2 的逐字移植。

---

## 二、可复用的三种对象（对应三档共享强度）

每层参数结构（实测，元素数）：

| 张量组 | 元素/层 | 说明 |
|---|---:|---|
| 输入投影 `2×(s·d + m·d)` | 655,360 | s/m 的 candidate 与 gate |
| 递归矩阵 `2·s² + 2·(m·s + m²)` | 688,128 | s、m 的状态转移 |
| 读出投影 `d·(s + m)` | 327,680 | 回到 d 维 |
| **合计** | **1,671,168** | 8 层 = 13,369,344 |

| 档位 | 组内共享什么 | 唯一图层元素 | 常驻 int8（含 embedding 8.39 MB） | 是否进 16 MB L3 |
|---|---|---:|---:|---|
| 现状 | 不共享 | 13,369,344 | 21.76 MB | ✗ |
| **R1** | 输入投影 | 9,436,416 | 17.83 MB | ✗（勉强） |
| **R2** | 输入投影 + 递归矩阵 | 5,308,416 | **13.70 MB** | ✓（余量小） |
| **R3** | 再加读出投影（= 层间权重完全共享） | 3,342,336 | **11.74 MB** | ✓（余量充足） |
| **R4**（激进） | R3 + 组内复用 Full 层算出的 **m 候选向量**（类比论文的 main KV 复用） | 3,342,336 | 11.74 MB | ✓，且省 MAC |

> R1–R3 只减**唯一字节**（提高 L3 命中率），**不减 MAC**；只有 R4 会减 MAC（每层 `m·d = 262,144` MAC × 组内 3 层 ≈ 786 k MAC/组）。这是与论文收益路径的差别：论文省 HBM，我们省带宽+L3 压力。

计算口径：位组为「2 组 ×（1 Full + 3 Reuse）」，即层 0/4 为 Full，层 1–3、5–7 为 Reuse；组内 Reuse 层的共享张量只存一份。

---

## 三、为什么先做 R2/R3 而不是 R1

L3 是 16 MB。R1 的 17.83 MB 仍未进 L3（还会有相当比例走 DRAM），而 R2/R3 都能装下——**能不能装进 L3 是「DRAM 带宽墙」与「L3 + 多核」的分水岭**，比省多少字节更重要。因此建议第一轮直接试 **R3**（收益最大、实现最简单：一个组内共享的参数表），R2 作为质量回退档。

---

## 四、改动点（逐项）

1. **配置与 schema**（`src/dual_state_config.hpp`）：新增 `group` 字段（如 `layers_per_group=4`、`share={input,recur,read}`）；层 → 张量名的映射从「每层独立」变为「Full 层独立 + Reuse 层指向组内 Full 层」。**必须写入 operator id**（`TAO_OPERATOR_ID`，例如 `dual-state-4-noffn-layershare-r3`）。
2. **序列化**（`src/dual_model_bundle.hpp`）：共享张量在 manifest 与 DSM1 载荷中**只存一次**（schema 必须显式表达「谁共享谁」）；DSB 从 5.65 MB 降到约 3.0 MB。
3. **CPU 解码路径**（`greedy_pipeline_grouped_model.hpp`）：层循环里查表取共享矩阵；分组融合（`group<4>`/`group<6>`）需要按新的张量归属重排。
4. **CUDA 路径**：串行 CUDA、批处理 tape、固定 GPU 验证三条路径必须同步（不变量 I4）。
5. **梯度累加（最关键的工程细节）**：共享权重意味着 4 个 Reuse 层的梯度必须**累加到同一 master buffer** 再做一次更新。当前 autograd 是「每张量一份 grad」，需要为共享组增加聚合步骤；否则要么编译期报错、要么静默只更新最后一个使用者。
6. **优化器**：共享组的有效梯度是 4 层之和 → 更新幅度近似 ×4。建议按组内层数**缩放学习率**（或对共享组单独设 lr）作为第一轮超参，并写入日志以便复现。
7. **检查点身份**：新算子 → 新 DSB/SCP；**禁止把旧 checkpoint 加载进新算子**（不变量 I5）。

## 六、风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| **容量下降** | 8 层只剩 2–4 份独立参数 → 有效深度/容量降低，可能表现为长程记忆更差 | 先做 R3 的短训练（500 步）看曲线是否只是「平移」而不是「变平」；必要时回退 R2 |
| **共享组梯度冲突** | 4 层的梯度需求不同，累加后可能互相抵消 | lr 缩放 + 梯度范数按组监控 |
| **实现面广** | schema/manifest/CPU/CUDA/训练器五处联动 | 先做 **CPU-only 推理版**（用一个手写的小脚本把现有 DSB 的 Reuse 层权重替换成组内 Full 层权重）来**先测速度收益**，确认值得后再动训练侧 |
| **算子膨胀** | 每档一个 operator id | 保持 id 命名规则统一，文档登记（本目录） |

## 七、验收

1. **速度**：常驻唯一字节 ≤14 MB；token/s 达到 02 号文档 S4 区间（8 000–15 000，与 S1/S2/S5 叠加）。
2. **数值**：CPU↔CUDA 一致性（新算子自比对）；无 NaN/Inf（沿用 `project()` 的健康检查）。
3. **质量**：固定验证集 **BPB 相对基线劣化 ≤5 %**，固定对话探针不出现新的退化模式。
4. **产物**：新 DSB/SCP + 新 operator id + 消融日志三件套入档。

## 八、首次执行结果（2026-09-11，速度验证，无训练侧改动）

按 §六 的缓解措施执行：**不改算子、不改训练**，只在 CPU 解码路径加入「层→源层」权重映射。

### 8.1 实现（`src/greedy_pipeline_grouped_model.hpp`，4 处）

| 位置 | 改动 |
|---|---|
| 成员 | 新增 `std::vector<uint32_t> layerSource`，**默认恒等映射**（默认路径行为与字节完全不变） |
| 构造 | 解析环境变量 `TAO_LAYER_SHARE="0,0,0,0,4,4,4,4"`；缺省或格式不符即回退恒等 |
| 层循环 | `auto p="layer."+std::to_string(layerSource[l])+"."` —— **唯一改动点**，其余算子零改动 |

因为 Reuse 层解析到的是**同一个 `PipelineRows` 对象**，物理地址相同，工作集才真正减半。
（**注意**：把 Reuse 层权重"复制"进 DSB 不会省任何字节——缓存按地址索引，同值不同址仍是两份。）

### 8.2 正确性验证（映射确实生效）

用 `diag_binding_rate.exe` 对 `build/arch_A_ds3/step_150/final.dsb` 比对：

| 配置 | 两者都对 |
|---|---:|
| 恒等 | 13/18 |
| R3 共享 | **0/18** |

输出**确实改变** → 映射生效。
**R3 归零是预期的**：这是拿**未按共享训练**的权重直接套共享，属于速度实验；质量结论必须来自**按共享训练**的 A1/A2。

> **踩过的坑**：首次用 `diag_binding_rate.exe` 验证时输出完全相同，误判为"映射未生效"。
> 真实原因是**该 exe 是 2026-09-10 的旧二进制，没有随头文件重编译**。头文件改动必须重建**每一个**包含它的可执行文件。

### 8.3 速度结果（同一二进制内交替 A/B，各 3 次）

| 配置 | 3 次 tps | 平均 |
|---|---|---:|
| 恒等 R0 | 730, 738, 664 | **710.6** |
| R3 共享 | 849, 852, 845 | **848.7** |

**提速 = 1.194×**（每 token 常驻字节 21.09 MB → 11.53 MB）。

### 8.4 关键否证：远低于带宽模型预测

若解码纯受 DRAM 带宽限制，字节降到 54.7% 应给出 **1.830×**。
**实测 1.194×，只兑现了理论增益的 23%。**

**推论**：层部分（13.37 → 3.34 MB，4× 压缩）并没有换来 4× 提速，
说明**解码并非全程压在 DRAM 带宽墙上**——共享后仍有别的封顶（指令吞吐 / L3 带宽 / 2 线程执行器）。
这与 02 号文档 §2.3「tps = 带宽墙 ÷ 每 token 常驻字节」的恒等式**不完全一致**，该恒等式需要限定适用范围。

### 8.5 一个必须记录的观测

R3 的 3 次测量**极稳定**（849/852/845，±0.4%），恒等映射则明显抖动（730/738/664）。
稳定本身说明 R3 触到了另一个稳定的瓶颈——**这更像"换了个瓶颈"而不是"移除了带宽墙"**。

### 8.6 尚未验证 / 下一步

| # | 事项 | 说明 |
|---|---|---|
| 1 | **绝对基线在构建间会漂移** | 旧二进制 870 tps、HEAD 版 771、工作区版 731 —— 跨构建的绝对值不可比，**必须用同一二进制内的 A/B** |
| 2 | **R3 质量必须重训后测** | 共享权重改变了模型，13/18→0/18 不能作为质量结论 |
| 3 | 其余档位 R1/R2/R4 未测 | R4 会减 MAC（每层 `m·d`），可能触到不同的瓶颈 |
| 4 | 输出头 8.39 MB 未动 | 占每 token MAC 的 38.6%，是剩余字节的大头 |

## 九、瓶颈定位与 §八 结论的**否证**（2026-09-11 同日续测）

### 9.1 用带线程控制与相位分解的基准复测

工具：`build/benchmark_noffn_s3.exe <ckpt> <threads>`（相位计时默认开启，`benchmark_noffn_s3.cpp`）。
检查点：`build/arch_A_ds3/step_150/final.dsb`。

| 线程 | R0 恒等 | R3 共享 | 比 |
|---:|---:|---:|---:|
| 2 | 842 tps | 886 tps | 1.053× |
| 4 | 1111 tps | 1076 tps | **0.969×** |
| 8 | 1098 tps | 1107 tps | 1.008× |

（R0 checksum=259，R3 checksum=546 → **映射确实生效**，不是没接线。）

> **§8.3 的 1.194× 未能复现。** 那是用 `benchmark_noffn_decode.exe` 测的（该基准不设置线程数）。
> 换用带显式线程控制的基准后，收益落在 0.97–1.05×，即**噪声内、且方向不定**。
> **结论：§8.3/8.4 的"1.194×"作废**，不得引用；R3 的提速效应**未被证实**。

### 9.2 相位分解（每 token 毫秒，R0 恒等）

| 线程 | norm | s_update | **m_update** | read | **head** | body 合计 |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 0.009 | 0.131 | **0.504（60.8%）** | 0.185 | 0.341 | 0.829 |
| 4 | 0.008 | 0.129 | **0.405（55.7%）** | 0.184 | 0.206 | 0.727 |
| 8 | 0.008 | 0.129 | **0.365（52.6%）** | 0.193 | 0.162 | 0.695 |

**`m_update` 是最大单项**（52–61%），第二是 `head`。

### 9.3 R3 下各相位并未变快（这是否证的核心）

| 线程 | m_update R0 → R3 | head R0 → R3 |
|---:|---|---|
| 2 | 0.504 → **0.636**（更慢） | 0.341 → 0.459（更慢） |
| 4 | 0.405 → 0.401（不变） | 0.206 → 0.238 |
| 8 | 0.365 → 0.379（不变） | 0.162 → 0.181 |

**把层权重的唯一字节压掉 4×（13.37 → 3.34 MB），`m_update` 相位一点没快。**

### 9.4 由此得出的否定结论

若 02 号 §2.3 的恒等式 `tps = 带宽墙 ÷ 每 token 常驻字节` 成立，
R3 把字节从 21.09 MB 降到 11.53 MB 应给出 **1.83×**。实测 **约 1.0×**。

**⇒ 「CPU 解码受 DRAM 带宽限制」这一判断，在 R3 已把工作集压进 L3 之后，不再成立。**
层维复用**没有**把 DRAM 带宽换成 L3 带宽，因为**瓶颈本来就不在 DRAM 带宽上**。

### 9.5 线程扩展的旁证

R0：2→4 线程 **1.32×**，4→8 线程 **0.99×**（饱和）。
若纯带宽受限，2→4 不应有 1.32×；若纯指令受限，4→8 应继续涨。**两者都不是**——
更像**每层的递归状态依赖链**造成的延迟受限：`m` 的更新依赖上一层 `m`，层间无法并行，
线程只能并行**层内**的行，因此 4 线程后饱和。

### 9.6 这对 03 号文档（层维复用）意味着什么

| 原判据（§七 验收） | 实测 | 判定 |
|---|---|---|
| 常驻唯一字节 ≤14 MB | 可达（R3 = 11.74 MB） | ✅ |
| token/s 达到 S4 区间（8 000–15 000） | R3 ≈ 886–1 107 | ❌ **未达成** |

**层维复用作为 CPU 提速手段，其前提（带宽墙）已被本次实测削弱。**
在重做 §9.1 的对照并得到满意结论之前，**不建议推进训练侧的 A1–A5 消融**。

### 9.7 下一步应查什么

1. **延迟受限假说**：测「层内并行度」与「层间串行」的相对贡献——例如临时把层数从 8 降到 4/2，看吞吐是否近线性。若近线性 ⇒ 层间串行是主因，压字节无用。
2. **`m_update` 为什么这么大**：它是 `group<6>`（1.18 M 元素/层）+ 逐元素状态更新（m=512）。拆开量这两部分各占多少。
3. **输出头 `head`（8.39 MB，38.6% MAC）**：线程 2→4 时 0.341→0.206（1.65×），是扩展最好的一块。
4. **不要再跨二进制比较绝对 tps**：本次已出现 710 / 842 / 870 / 1111 等互不一致的基线，**必须同一二进制内交替 A/B**。

## 十、交错重复测量（4 线程，同日 22:10）

§9.1 是单次采样，噪声与效应同量级。改为**同进程外交错 6 轮 × 3 配置**（每轮按 R0 → R3 → R-all 顺序固定），取中位数。

| 配置 | 6 次采样（tps） | 中位数 | 校验 |
|---|---|---:|---|
| R0 恒等 | 1178, 1207, 1119, **916, 886, 895** | 1119.1 | 259 |
| R3（2 组） | 1306, 1238, 1242, 1124, 1175, 1196 | 1238.2 | 546 |
| R-all（1 组，全部 8 层共享第 0 层） | 1269, 1286, 1282, 1219, 1206, 1220 | **1268.5** | 6469 |

| 比较 | 中位数比 | 配对中位数比 |
|---|---:|---:|
| R3 / R0 | **1.106×** | ≈1.17× |
| R-all / R0 | **1.134×** | ≈1.24× |

### 10.1 两个必须记录的干扰因素

1. **热漂移**：R0 的后三次（916/886/895）明显低于前三次（1178/1207/1119）。
   整机在持续负载下变慢，而三个配置**在同一轮内按固定顺序**执行，因此顺序与漂移耦合。
   配对比较（同一轮内相比）比中位数比较更能抵消漂移，故并列给出。
2. **跨二进制绝对值不可比**：本次会话内 `benchmark_noffn_decode.exe` 与 `benchmark_noffn_s3.exe`
   对同一配置给出 710 / 842 / 987 / 1119 / 1178 等互不一致的基线。**任何结论必须来自同一二进制内的交错 A/B。**

### 10.2 结论

**层维复用对 CPU 解码的实测增益约 1.1×（区间 1.0–1.24×），远低于「字节减半应得 1.83×」的带宽模型。**

- 把层权重压 4×（R-all：13.37 → 3.34 MB，等效 0.25×）只换来约 1.13–1.24×，
  **远未出现「字节数接近反比」的带宽墙行为**；
- 因此 **02 号文档 §2.3 的恒等式 `tps = 带宽墙 ÷ 每 token 常驻字节` 在减少字节后不再成立**——
  该恒等式描述的是**当时的** 22.1 MB 配置，不能外推到更小工作集；
- 这与 §9.5 的线程饱和（2→4 = 1.32×，4→8 = 0.99×）一致：**存在一个与字节数无关的封顶**，
  最可能是**层间递归状态依赖链造成的延迟受限**（`m` 的更新依赖上一层 `m`，层不能并行）。

### 10.3 对 03 号文档结论的最终判定

| 项 | 判定 |
|---|---|
| 层维复用能否减少常驻字节 | ✅ 能（R3 = 11.74 MB） |
| 层维复用能否显著提高 CPU 解码吞吐 | ❌ **不能**（实测约 1.1×，目标 8 000–15 000 tps 未接近） |
| §八 首次测得的 1.194× | 与 §十 的 1.106× 同区间，**并非错误，但当时是单次采样、不能作为证据** |

### 10.4 应立即转向的方向

既然瓶颈与字节数无关（§10.2），继续沿「压字节」这条线（R1/R2/R4、Engram 大表）
**都不会有显著收益**。应改为攻**层间串行**：

1. **量化层间串行占比**：把层数从 8 降到 4/2（临时改 config 或加 `TAO_LAYER_LIMIT`），
   看吞吐是否近线性。近线性 ⇒ 层间串行是主因。
2. **降低层间临界路径**：`m` 更新中 `beta*(v-acc)` 依赖当前层输入，
   能否重排为「先读后写」以减少依赖链深度。
3. **输出头**（8.39 MB，38.6% MAC）是线程扩展最好的一块（2→4 线程 1.65×），
   值得单独优化。

## 十一、R4 与层数扫描：瓶颈的最终答案（2026-09-11 续）

### 11.1 交错 5 轮 × 5 配置（4 线程，同二进制）

| 配置 | 5 次采样（tps） | 中位数 | 校验 |
|---|---|---:|---|
| R0 恒等 | 1204, 874, 933, 932, 984 | 932.8 | 259 |
| R3（2 组共享权重） | 1205, 1173, 1183, 1220, 1152 | 1183.2 | 546 |
| **R3 + R4**（再复用 m 候选/门控向量） | 1630, 1705, 1622, 1696, 1637 | **1637.0** | 259 |
| L=4（只跑前 4 层，计时用） | 1882, 1909, 1861, 1758, 1916 | 1882.4 | 697 |
| L=2（只跑前 2 层，计时用） | 2724, 2866, 2792, 2664, 2779 | 2779.4 | 697 |

| 比较 | 倍数 |
|---|---:|
| R3 / R0 | 1.269× |
| **(R3+R4) / R3** | **1.384×** |
| **(R3+R4) / R0** | **1.755×** |
| L=4 / R0 | 2.018× |
| L=2 / R0 | 2.980× |

### 11.2 层数扫描：耗时与层数近线性 ⇒ 瓶颈在层内的串行计算

若时间由「每层固定开销 × 层数」构成，则 8→4 应得 2.0×，8→2 应得 4.0×。
实测 **2.018×** 与 **2.980×**——8→4 **几乎完全线性**。

用 Amdahl 反推固定开销占比 `f`（`T = f + (1-f)·(L/8)`）：

| 由 | 反推 f |
|---|---:|
| 8→4 | ≈ **0.00** |
| 8→2 | ≈ 0.11 |

⇒ **CPU 解码的时间几乎全部花在层循环里，且层之间不可并行**（`m` 的更新依赖上一层的 `m`，形成纯串行依赖链）。
这与 §9.5 的线程饱和（2→4 = 1.32×，4→8 = 0.99×）**完全一致**：线程只能并行"层内行"，层间串行无法并行。

### 11.3 由此得到的因果链（本次会话的最终结论）

| 现象 | 解释 |
|---|---|
| 压字节 4×（R-all）只值 ~1.13–1.24× | 瓶颈**不是** DRAM 带宽，压字节无效 |
| 层数减半 → 吞吐 ×2.02 | 瓶颈是**层内串行计算量** |
| **R4 砍掉 Reuse 层 `group<6>` 的全部 MAC → +38.4%** | **减 MAC 直接见效，且接近按比例** |

**⇒ CPU 解码提速的正确杠杆是「减少每 token 的 MAC」，不是「减少常驻字节」。**
这也同时解释了为什么 02 号文档的字节恒等式在减少字节后失效——它当时只是**恰好**成立（1 字节权重 ↔ 1 次 MAC，两个数在 22.1 MB 配置下数值重合），并不是因果。

### 11.4 R4 的实现（`greedy_pipeline_grouped_model.hpp`）

新增开关 `TAO_LAYER_REUSE_MV=1`：Reuse 层不再执行 `group<6>`，而是直接复用组内 Full 层算出的
候选向量 `v` 与门控向量 `g`，仅用自己的 `m` 状态做更新。省掉每层 `2×(m·d + m·s + m·m) = 1,179,648` MAC，
6 个 Reuse 层共省 **7.08 M MAC / 21.76 M = 32.5%**——与实测 +38.4% 量级吻合。
