# Engram 式条件记忆的 CPU 落地建议书

> 结论：**纳入**。它是把「参数量增长」与「解码速度」解耦的唯一通路——增长放在稀疏表里，每 token 成本几乎不变。但它**不是**速度杠杆：它不加速，只是**不拖慢**，同时换来解决「固定状态记忆不足」这一能力瓶颈的机会。

---

## 一、成本模型：为什么「表很大」不等于「解码很慢」

| | 每 token 字节 | 随参数增长 |
|---|---:|---|
| dense 权重（现状） | **22.1 MB** | **线性增长**（每个参数每 token 都要读） |
| Engram 表 | **约 128 B – 1.5 KB** | **常数**（每 token 只读 O(阶数×头数) 个条目） |

具体算：3 阶 × 8 头 × 每条目一条 64 B cache line = **1.5 KB/token**，相对 22.1 MB 是 **0.007 %**。表从 33 MB 长到 6.4 GB，每 token 字节数**一点不变**。

> 我此前用「表必须进 L3」当判据，得出 Engram 负面的结论；该判据是错的——正确判据是**每 token 触碰的字节数及其延迟**。按正确判据，Engram 在一个「模型最终常驻内存」的部署形态下是**最划算的参数增长方式**。

## 二、真正的风险：随机访问延迟与 TLB（**本节模型已被实测推翻，2026-09-11**）

> **下文原有的估算（2.4 µs/token、上限 400 token/s、预取是先决条件、必须大页）经实测不成立。**
> 实测工具：`build/microbench_engram_lookup.exe`（源码 `src/microbench_engram_lookup.cpp`）。
> 保留原推论以供对照，**修正后的结论见本节末尾**。

**原推论（已作废）**：

- 每 token 有 **阶数×头数**（示例 3×8 = **24**）次互相独立的随机访问；
- 若它们**串行**发生（无预取、无重叠），每次 DRAM 往返约 100 ns → **2.4 µs/token ⇒ 上限约 400 token/s**；
- 若**并行发起/预取**，24 次落在同一次往返窗口内 → **约 100 ns ⇒ 在 1 ms/token 下占比 <10 %**。

**实测（Ryzen 9 7940H，随机键=最坏情况，200 万次/token 对）**：

| 表规模 | 无预取 | 软件预取 | 预取增益 |
|---|---:|---:|---:|
| 32 MB（2^18 行 × 2 阶） | **42.8 ns/token** | 40.7 | 1.05× |
| 512 MB（2^22 行） | 73.1 | 66.3 | 1.10× |
| 2 GB（2^24 行） | 85.9 | 76.3 | 1.13× |
| 2 GB + 2 MB 大页 | 87.7 | 79.9 | 1.10× |

**三条修正：**

1. **原估算悲观了 30–50 倍。** 即使 2 GB 表，也只有 **约 86 ns/token**（上限约 11.6 M token/s），不是 2.4 µs。
   原因是 **E1 的设计本身**：同一 n-gram 的多头条**交错存放于同一条 64 B cache line**，
   于是每 token 只有 **阶数**（示例 2–3）次独立访问，而非 阶数×头数，且 CPU 乱序引擎会跨迭代重叠它们。
2. **预取不是先决条件**，增益仅 1.05–1.13×。它是优化项。
3. **大页零收益**（2 GB 表：普通页 85.9 vs 大页 87.7，在噪声内）。
   "4 KB 页导致 TLB 抖动"的担忧在这个规模上**未获支持**；E4 可降级为可选项。

**修正后的结论**：Engram 的每 token 成本**比原判断更低**，但**理由不同**——
不是"预取把延迟藏起来了"，而是**条目交错布局（E1）让并行度问题根本不成立**。
因此 §六 的落地顺序中，**第 1 步（微基准）已完成**，且它可以**降低**而非提高实现门槛。

三个让它成立的事实与手段：

1. **地址确定性**：n-gram 的键只由 token id 组成，**不依赖隐状态**——prompt 阶段全部 token id 已知（可整段预取），decode 阶段在新 token id 产生后（argmax 之后、下一 token 第 0 层之前）即可发起预取，而词表头计算本身有充足的时延窗口。
   （论文用后台 RDMA 预取与第一个 Transformer 块重叠，是同一条思路的分布式版本。）
2. **软件预取**：`_mm_prefetch` 或专职 lookup 线程 + ring buffer；把 24 次访问摊平到上一 token 的计算期间。
3. **大页**：GB 级表在 4 KB 页下是几十万页，TLB（L2 TLB 数千项）必然抖动，每次 miss 追加一次页表遍历。用 2 MB 大页（Windows `VirtualAlloc` + `MEM_LARGE_PAGES`，需 SeLockMemoryPrivilege）或按页分区对齐，把页数降三个数量级。

## 三、设计规范

### 3.1 硬性五条

| # | 规范 | 理由 |
|---|---|---|
| E1 | **一个 n-gram 一次访问 = 一条 64 B cache line**：同一 n-gram 的多个哈希头条目**交错存放成连续 64 B**（如 4 头 × dim16 int8 = 64 B） | 避免「一头一页」的 4 倍随机访问 |
| E2 | **地址只依赖 token id，确定性** | 训练/推理一致（不变量 I4）＋ 可预取 |
| E3 | **预取流水线**（见 §二） | 否则上限 ~400 token/s |
| E4 | **大页或页对齐分区** | 否则 TLB 抖动吃掉全部收益 |
| E5 | **去掉短因果卷积** | 论文也去掉；CPU 上顺序算子尤其不划算 |

### 3.2 结构与超参（首版建议）

| 项 | 首版（验证） | 中版 | 大版（内存形态） |
|---|---|---|---|
| 放置层 | 第 1 层 | 第 1、5 层 | 第 1、5 层 |
| N-gram 阶数 | {2,3} | {2,3,4} | {2,3,4} |
| 哈希头数 | 4 | 8 | 8 |
| 每头表长 | 2^18 = 262,144（**不是素数**；论文用的是约 1,600 万个**互不相同的素数**做散列模数，本项目若要照搬需改为素数表长） | 2^20 | 2^22 |
| 条目布局 | 4 头 × dim16 = **64 B** | 8 头 × dim8 交错 / 2 行 | 同左 |
| 表大小 | **33.5 MB** | **1.6 GB** | **6.4 GB** |
| 每 token 表字节 | 128 B | 512 B | 1.5 KB |
| 表精度 | int8（每行/每块 scale） | int8 | FP8/int8 |

门控（**必须上下文相关**，否则退化成静态查表）：`e = concat(heads)`；`g = sigmoid(W_g [x_norm; e])`；残差加 `g ⊙ (W_o e)`。每模块额外 MAC ≈ `(d+e_dim)·e_dim + d·e_dim ≈ 0.4 M`（对 21.76 M 是 **约 2 %**）。

**优化器**：表用 **Nesterov 动量 + Sinkhorn 平衡**（论文 Algorithm 1：K=11、τ=1e-3、ε=1e-20、γ=0.18，lr ×5），**只更新本步被访问的行**。理由：给大表挂 Adam 需要 m 与 v 两份缓存（表 1.6 GB ⇒ 优化器状态 12.8 GB），动量 + Sinkhorn 只要一份，且论文经验更好。

## 四、必须先解决的基础设施（否则表规模下无法训练/加载）

| 现状（源码事实） | 问题 | 改造 |
|---|---|---|
| `SortedGpuTrainer::update()` 对**每个**张量做 `graph.w.at(t.name)->grad.host()` 全量回读做非有限值检查 + 范数计算 | 每步 O(参数) 的 D2H 拷贝与主机分配 | 改为 GPU 侧归约（代码已有 `health` 归约骨架）；表只做**被访问行的稀疏更新** |
| `project()` 里 `master->host()` / `scales->host()` 全量扫描 | 同上 | 移到 GPU 侧或降低频率（每 N 步） |
| 每个三值参数持有 float32 master + moment + variance（**12 B/参数**） | 表规模下优化器状态远超权重本身 | 表：单份动量；dense：按论文做优化器分工 |
| 梯度是稠密 buffer，且只有被访问行非零 | 1.6 GB 表的稠密梯度 = 6.4 GB（float32） | 稀疏梯度：记录 (row, grad) 对；backbone 反向后统一 scatter |
| `read_compact_bundle` 硬编码 `count>100000000` 抛错、DSB >512 MB 抛错 | 内存规模模型直接加载失败 | 放开上限；表走**独立文件 + mmap**；DSB 只存 backbone |
| 检查点每 50–100 步整体落盘 | 1.6 GB 表 × 20 次 = 32 GB I/O | 表：增量/稀疏保存（或更长周期 + 单独 sidecar），与 backbone 检查点解耦 |
| 内存上限：`Config.validate()` 与加载器的 layers/d/s/m 界限 | 需要新的 schema 维度（表长、阶数、头数） | 扩 schema 并写入 operator id |

## 五、评测与验收

| 维度 | 指标 | 通过条件 |
|---|---|---|
| 能力 | 固定验证集 **BPB / NLL** | 相对同 backbone 基线**不劣化且更优**（目标：held-out NLL 降低 ≥3 %） |
| 泛化 | **held-out n-gram** 子集（训练集未出现的 n-gram） | 增益不能只来自「背下训练语料」 |
| 速度 | 每 token 延迟增量（有/无预取两组） | 预取开启时 **≤5 %**；关闭时应能观察到显著劣化（证明确实隐藏了延迟） |
| 一致性 | 训练/推理使用同一寻址与受限域 | 固定探针输出一致率 |
| 退化 | 重复/循环退化率（配合 05 号文档） | 不高于基线 |

**必查反例**：表可以「背下」语料而验证集无收益——这是 Engram 类模块最典型的失败模式，必须用 held-out n-gram 与验证集双指标判定。

## 六、首个实验的落地步骤

1. **微基准（独立小程序，不接入模型）**：33.5 MB 表 + 随机 x，测「有预取 / 无预取」的每 token 延迟差；同时测 4 KB vs 2 MB 页的差异。**这一步决定表规模上限**。
2. **CPU 前向原型（只推理）**：把表与门控接进 `greedy_pipeline_grouped_model`（随机初始化），测 token/s 增量是否 ≤5 %，并确认每 token 字节数不变。
3. **训练接入（新算子 id）**：小语料 + 固定验证集，做「有 / 无 Engram」对照（本轮 6.7 小时/2000 步，可先跑 500 步看趋势）。
4. **放量与放置**：稳定后再决定是否加到第 2 个模块、表长是否升到 2^20。

## 七、与速度目标的关系（一句话）

Engram **不提高** token/s，但把「模型变大」这件事从「拖慢解码」变成「几乎不影响解码」——在一个模型最终常驻内存的形态下，这是唯一可持续的扩展方向；真正的速度收益仍来自 02 号文档的 S1/S2/S4/S5。
